# 完成検査 — 形・文・判断〔手順 8〕

⚠ **board を書き終えてから読む。**主成果物と、承認者へ渡す補助資料のすべてに実施する。

検査は **形・文・判断**の 3 層に分ける。主成果物と、承認者へ渡す補助資料のすべてに実施する。

### 形

選んだ媒体で、幅、overflow、見出し、画像、表、回答操作、狭い画面を確認する。HTML の具体的な検査方法は renderer 分冊に置く。Markdown、端末、PR コメントでは実際の表示先で折り返し、表、リンク、画像、貼り戻し文を確認する。

### 文

**承認者に復元作業をさせる文だけを探す。**文体・語調・言い回しの好みは、この層の対象ではない。

- 主語または目的語がなく、何が何をするか分からない文。⚠ **日本語は主語を省いても文が成立してしまう。**成立することと、承認者が前を読み返さずに読めることは別である。
- 指示語（「これ」「それ」「上記」「同様に」「前述の」）の指す先が、段落をまたいでいて一意に決まらない箇所。**対象を名指しする。**
- 初出なのに単独では意味が分からない語や数。
- 比喩で書かれ、指している対象が本文にない語。
- ⚠ **決定サマリーの 1 行目に「この作業は何のためか」が無い board。**目的の無い board は、結果だけがあって理由の無い資料になる。

### 判断 — 独立 reviewer

⚠ **独立 reviewer は «欠落» の検出器である。«過剰» は検出できない。**reviewer は読む量のコストを負わないので、長い板を長いと感じない。しかも「足りない項目を名指しせよ」型の問いに安全側で答えると、答えは必ず «足す» 側になる。板が太った事故はどれも、reviewer が「決められる」を返した後にユーザが見つけている。**過剰は reviewer に聞かない。**主線を閉じたリストにして、そこに無いものを置かせないことが防ぐ（gate skill の主線固定部）。

⚠ **reviewer は board に載っていないものを見られない。**渡しているのが board だけである以上、**落ちた判断軸・ticket にあって板に来なかった制約・そもそも検討されていない選択肢は、原理的に検出できない。**「決められる」は «渡された材料で閉じているか» であって «正しく決められるか» ではなく、**材料が少ないほど出やすい。**網羅性を担保するのは reviewer ではなく、板を書く前の[洗い出し](../pdh-ticket-decision-board/SKILL.md)（`Open Questions` 全件・未確認語の検索・断定の裏取り・影響レイヤー・合意された添付）と「判断の分類」である。⚠ **この分業を board に書かない** — 承認者が判断に使わない。

**別の engine の独立した reviewer に board だけを渡す。**起動方法、利用できる engine、sandbox、保存先はプロジェクト設定が定める。共有設定に特定 engine のコマンドや広い権限を既定として書かない。

⚠ **«最小の権限で起動する» を検査の条件にしない。**engine によっては広い権限でしか起動できない。**権限を絞れないなら、依頼文で参照範囲を指示する。**起動できないことを理由に検査を省かない。**別 engine がまったく使えない場合**は、そのことを board に書いたうえで書き手が 7 問に答える（機微な情報を扱う board では、これは代わりにならない。上の risk overlay に従う）。

- reviewer へ repo やインターネットを参照させず、承認者と同じ情報だけを渡す。
  ⚠ **依頼文に repo の path・ticket・note・git のコマンドを書かない。**書くと reviewer は
  **board と実装の突き合わせ**を始める。それは 問 3 が «board の中だけで分かるものに限る» と
  定めている範囲の外で、**この検査は終わらなくなる** — 実装の欠陥が出れば実装を直し、
  数が変わり、board を直し、また回す。**実装の検査は別の場所（コードレビュー）の仕事である。**
- board を別形式へ抽出・整形せず、承認者へ渡す形のまま渡す。
- 試験用の注記は board 内ではなく reviewer への依頼文へ置く。
- reviewer の指摘は仮説として扱い、採否と理由を書き手が決める。
- 機微な情報と hotfix には risk overlay を先に適用する。

reviewer に次の 7 問を、番号を変えずに聞く。

1. **決められるか。**最初に「決められる / 決められない」を答え、詰まった場所を示す。
2. **推奨を選ぶと、この ticket のゴール（board が書く Why と AC）に届くと、board から分かるか。**分からないなら、どの記述が足りないか。別の選択肢のほうが届くと読めるなら、それも言う。
3. **誤った判断をしうる箇所**はあるか。⚠ **board の中だけで分かるもの**に限って答える —**board 内の矛盾、過大に読める数値、根拠の書かれていない断定、数の不一致。**⚠ **元の実体（コード・ログ・仕様）と食い違っているかは、この reviewer には分からない**（board しか渡していないため）。**それは書き手が未確定の洗い出しで済ませておく。**
4. 見出しと強調だけを拾っても、判断の筋が通るか。読む手間はどこにあるか。
5. 追加調査なしで決められたか。
6. **書き手が自分で調べたり決めたりできた項目を、承認者へ残していないか。**残っていれば、書き手が何を済ませるべきか。
7. **この board だけを読んで、この作業が何のために始まったか分かるか。**⚠ **前の版・前の会話・ticket を見ずに答える。**分からなければ、どこに何を書けば分かるかを示す。あわせて、**前回からの変化を語っている箇所**が主線にあれば名指しする（base「差分で語らない — Why から、毎回新しく書く」）。⚠ **前回の回答がある board では、その指示に対して何を変えたかの畳みが要る** — 無ければ「承認者が自分の指示の通り具合を確かめられない」と指摘する。

同じ依頼で、文の検査 3 項目も挙げさせる。

### 指摘への応じ方 — 指摘された場所は、直す場所ではない

reviewer の「足りない」に、**指摘された節へ文言を足して応えない。**直す前に置き場所を引く。

1. **置き場所** — gate skill の主線固定部で、その情報が主線・裏付け・畳みのどこに属するかを引く。
2. **統合** — 同じ主張の既存の記述を検索し、足すのではなく 1 か所へまとめる（下の「修正後の一貫性」と同じ検索）。
3. **主線に足してよいのは、その節で承認者が判断に使う結論だけ。**書き手が実行する操作の詳細（コマンド・確認手順・実行フロー）は、承認者は実行しないので畳みへ。

「足りない項目を名指しせよ」型の問い（close gate の [ship-risk.md](../pdh-close-decision-board/ship-risk.md) 問 9〜11）は情報を board へ**引き込む力**しか持たない。応じ方を決めずに周回すると、**指摘が当たった節に情報が堆積して主線が太る** — 承認者が回答を押す手前に、承認者が実行しない書き手の運用手順が並ぶ。

### 抜ける条件 — ゴールが主、欠陥は従

⚠ **合格は «欠陥ゼロ» ではない。**この gate のゴールは 1 つだけ —**承認者が追加調査なしで判断を下せること。**

    問 1 が「決められる」かつ 問 2 が「届く」かつ 問 5 が「はい」  → 出す
      ただし «決められなくする» 指摘が残っていれば、それだけを直してもう 1 周

⚠ **それ以外の指摘は «直さずに出してよい»。**採らないと決めた指摘は、**件数と 1 行理由を note に残す**（`PDH-AGENTS.md`「Reviewer findings are hypotheses, not implementation orders」— 採否は書き手が決める）。

⚠ **«決められなくする» 指摘とは、次のどれかである。**

- 承認者が選ぶ側の事実が間違っている（推奨と別案の得失が入れ替わる）
- 推奨がゴールに届くと board から読めない、または別案のほうが届くと読める（問 2）
- 承認する対象（AC・契約）が board 内で矛盾していて、どちらを承認するのか決まらない
- 書き手が調べれば分かることを、承認者に調べさせている（問 6）
- 読み手が復元作業をしないと判断の筋が通らない（問 4）— 1 文に契約の全文を詰めた推奨、裏付けの全文をそのまま主線に複製した面、指示対象の書かれていない語

⚠ **言い回しの好み・語順・同義の言い換えは、これに当たらない。**note に残して出す。
⚠ **数の不一致も、それが «規模の目安» の側なら当たらない**（ベース「まず、その数は判断を変えるか」）。
board が冒頭で線を宣言していれば、行数・件数のずれは指摘として採らない。読みにくさが止める理由になるのは、上の «復元作業を強いる» に達したときだけである —**読めない文章では判断できない**ので、そこまでを「言い回しの問題」として通さない。

### 止める条件 — 回すコストを必ず数える

⚠ **回るたびに «前より決めやすくなったか» を測る。**次のどれかに当たったら、**その周で打ち切って出す。**

- ⚠ **board が前の周より大きくなった。**読む量が増えて決めやすくなることは、ほとんどない。⚠ **増えた分は «足りなかったもの» ではなく «置き場所を間違えたもの» と見る** — 主線の閉じたリストに無いなら、裏付けか畳みへ移す（上の「指摘への応じ方」）
- ⚠ **同じ 1 点について、連続する周が両立しない処方を返した**（下記「指摘が振動したら」）
- ⚠ **3 周回っても «決められる» が続いている。**その時点でゴールは達成済みである

⚠ **上限の無い検査は、検査ではなく作業である。**

hotfix の往復回数は risk overlay がこの標準を上書きする。

**構成を組み直したら、それまでの指摘は無効になる。**節の順序、判断の数、主線と補足の切り分け、媒体のいずれかを変えると、同じ内容でも**情報の位置と欠落が変わる**。前の構成で「決められる」を得ていても、**新しい構成で 1 周目から数え直す。**部分的に直しただけなら、直した箇所とその影響範囲だけを再検査してよい。

### 指摘が振動したら、そこで打ち切って書き手が決める

**同じ 1 点について、連続する周が «互いに両立しない処方» を返したら、それは欠陥ではなく判断の分かれ目である。**周を重ねても収束しないので、**その時点で reviewer との往復を止め、書き手が決めて、決めた理由を board に書く。**

reviewer は毎周が独立した読み手なので、**同じ資料に対して別の妥当な整理を返しうる。**指摘は仮説であって実行命令ではない。振動を「まだ直っていない」と読むと、**直すたびに前の周の処方へ戻る往復**になる。

**振動かどうかは、処方が両立するかで見分ける。**「AとB両方書け」は両立する（片方ずつ直せる）。「Aに含めよ」と「Aから外せ」は両立しない。**後者が 2 周続いたら振動と見なす。**

打ち切ったら、次の 3 つを報告に書く。**回した周の数・到達しなかったこと・振動した論点と自分の結論。**「レビュー済み」とだけ書かない。

### 書き手が決めてよいかの判定

「これは承認者が決めることか」に迷ったら、次の 3 つを全部満たすかで決める。**満たすなら書き手が決める。**満たさないものが 1 つでもあれば、判断として出す。

- **ticket が約束するものが変わらない**（Why の達成・AC・利用者が見る結果 — 画面・API の応答・出荷物 — が同じ。「判断の分類」の最初の篩と同じ問い）。
- **元に戻せる**（版管理に前の状態が残る）。
- **決めた理由を、後から探せる場所に残す**（作業ノート・記録用の文書）。

⚠ **「安いから」「小さいから」は基準にしない。**小さくても外から見える動きが変われば、それは承認者の判断である。

### 修正後の一貫性

数値、識別子、AC、判断範囲を直す前に、成果物内の出現箇所を安定した識別子で全部出す。同じ主張は別の言い回しで複製されるため、文章全体ではなく数値、AC 番号、節 ID などで検索する。

- AC を直したら、その AC 番号で全表示箇所を出す。
- 判断範囲を直したら、表題、決定サマリー、推奨、承認を求める見出し、返答文を確認する。
- 書き換える前に現在の節を読み、以前に退けた前提を戻さない。
- **規則を足す前に、同じ主題の節が他にないかを探す。**見つけたら、足すのではなく**統合する**。正反対の規則が両方残ると、読み手はどちらに従うか選べず、成果物が書き手ごとに別物になる。
- 構造を一括置換したら、前後の見出し、面、回答項目の数を比較する。

HTML でのクラス確認と AC 番号の具体的な検索は [render-html-common.md](render-html-common.md) に置く。
