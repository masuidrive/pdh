# 出荷して壊れうるもの — 保存されている形と、外部から見える契約〔手順 0 で判定〕

⚠ **当たるかの判定は `SKILL.md`「この gate で承認者が見るもの」で行う。**このファイルは、当たったときに裏付けへ何を足すかだけを書く。

当たるのは、ticket が次のどちらかを変える場合である。

- **保存されている形** — DB の table と column、migration、保存する JSON の形、ファイル形式、cache の key、queue に載せる message、保存する成果物。
- **外部から見える契約** — こちらの都合で変えると、呼ぶ側が壊れるもの。HTTP API の path・method・request と response の形・status code・error の形、SDK の公開関数と型、CLI の引数と出力、webhook や通知の形、設定ファイルのキー、画面上の操作の意味。

この 2 つは、間違えると出荷後に取り返しがつかない。他のコードは直せば済むが、書き換えたデータと、既に呼ばれている API は戻せない。当たる ticket では、**当たる側の節だけ**を裏付けに足す（保存されている形だけが変わるなら、その 1 節）。当たらない側は差分の規模の節の 1 行に含め、節を立てない。決定サマリー「確かめた事実」の行の先頭に 2 つの変更の有無を 1 行ずつ置き、「返す」に「戻せるか」の 1 行（詳細はこの裏付けへ参照）を足す。

## 当たらないと判定する前に — 外へ出る経路をたどる

**「内部の変更だけです」と書く前に、外へ出る経路を実際にたどる。**内部の関数名の変更でも、その値が response や log に載っていれば外から見える。

⚠ **変更したファイルの置き場所で判定しない。**「API のディレクトリを触っていないから契約は動いていない」は、**たどったことにならない。**外へ出る値を返している箇所から遡って確かめる。**削除も同じ**である — 消したものが外から呼ばれていないことを、**呼び出し元を検索して**示す。

たどった結果、外へ出る値が変わっていても、**その値を読む呼び手が repo の中だけで、この差分で追随済み**なら、外部から見える契約は変わっていない — 差分の規模の節の 1 行に、変わった値と、呼び手をどう確かめたかを書いて終える。当たらないと判定した側の節を «無し» の根拠のために書かない。

## 保存されている形の変更

⚠ **契約を «書いた文書» は、この節ではなく «外部から見える契約» に入れる。** API schema、生成した型、SDK は、保存されたデータではなく**約束の記述**である。**この節に入れると 2 箇所へ重複して載り、承認者はどちらを読めばよいか決められない。**

⚠ **「無し」と書くときも、根拠を 1 行付ける** — **何を検索し、どの範囲を見て、無いと判定したか。**根拠の無い「無し」は、承認者が検算できない（外部契約の側と同じ扱い）。

**変更があるなら、次を全部書く。**書けない項目は「未確認」と明記する。⚠ **「未確認」を残したまま close の承認を求めない。**残っているなら、**取得できない理由**と**その状態で出す判断**を、判断（`N`）として承認者に出す。

| 書くこと | 具体 |
|---|---|
| **何を何にしたか** | 追加・変更・削除を分けて。列名・型・既定値・NULL 可否まで |
| **既存のデータはどうなるか** | そのまま残る / 変換する / 消える。**変換できない行の扱い**も |
| **件数** | 本番で何行が対象か。**数えていないなら「数えていない」と書く** |
| **戻せるか** | migration に down があるか。**down があっても、変換で失った値は戻らない**なら、そう書く |
| **止まるか** | 実行に要する時間、その間の利用者への影響、途中で失敗したときの状態 |
| **読む側・書く側の同時性** | 新しいコードが古いデータを読むか、古いコードが新しいデータを読むか。**デプロイ中に両方が同時に動く**なら、そのときの挙動 |

**「戻せる」とだけ書かない。**復旧の記述は次の 3 点を満たす（3 点とも、初実走の close board で reviewer に刺されて直した実測がある — base の [examples.md](../pdh-decision-board-base/examples.md) 2026-08-19）。

- **復旧元は、merge 後も動かない commit ID で書く。**「main の内容へ戻す」は出荷前にしか成立しない — merge した瞬間に main はこの変更を含む側を指し、feature branch は削除される。復旧コマンドが参照してよいのは固定の commit ID だけ。後続変更を上書きする可能性と、その可否を誰が判断するかも書く。
- **「戻せる」は対象を分けて書く。**最低でも「実装ファイル（版管理で戻る）/ 作業記録（戻さない — 何をしたかの履歴そのもの）/ 出荷後に生まれる成果物（発行済み文書・生成物。戻すのか、残すのか）」の 3 つに分け、まとめて「全部戻る」と書かない。
- **復旧操作は、書く前にドライランする。**一時的な作業コピーで実行し、結果（対象の差分が空になる等）を board に書く。実行していないなら「未実行」と明記し、確度を下げる。机上で書いた復旧手順は成立しないことがある — 初実走では 2 案（一括 revert / main への checkout）が両方とも机上の誤りだった。

⚠ **戻す操作があることと、戻せることは別である。**列を落とす `down` があっても、**`up` が既存行の値を書き換えていれば、その値は戻らない。**「形は戻る／中身は戻らない」を分けて書く（実測: 5 列を追加する migration に列を落とす `down` があったが、`up` は既存行のデータ移行も行っており、`down` ではその移行結果が失われる）。

**列を足すだけ・index を足すだけで、既存の値を書き換えないなら、そう書いて短く終える。**危険の大きさに合わせる。**存在しない危険をあるように見せない**のも、この節の仕事である。

**複数の migration が並行して作られた可能性を確かめる。**同じ番号・同じ親を持つ migration が別々の作業で採番されると、合流した時点で適用できなくなる。**この gate で確かめる**（プロジェクトが検査を持つなら、その出力を証拠として貼る）。

## 外部から見える契約の変更

⚠ **「無し」と書くときも、根拠を 1 行付ける**（データ構造の側と同じ）。

**変更があるなら、次を全部書く。**書けない項目は「未確認」と明記する。⚠ **「未確認」を残したまま close の承認を求めない**（データ構造の側と同じ。残すなら判断にする）。

| 書くこと | 具体 |
|---|---|
| **追加・変更・削除** | 3 つを分けて。**削除と «意味が変わった変更» を同じ行に混ぜない**。1 件ごとに **path と method（または関数名・引数）／ 名前 ／ 型 ／ 必須か ／ null を取るか ／ 既定値 ／ 無いときの意味** を書く。**「field が増えた」だけでは、呼ぶ側は何もできない** |
| **呼ぶ側は何をすればよいか** | 何もしなくてよい / 直す必要がある / 直さないと壊れる。**どれかを明記する** |
| **後方互換か** | 互換でないなら、**いつから壊れるか**と**予告したか**。予告していないなら「未予告」と書く |
| **誰が呼んでいるか** | 呼び出し元を数える。**数えられないなら「数えられない」と書き、その理由も** |
| **error の変わり方** | 成功が失敗になる／失敗が成功になる／status code が変わる。**呼ぶ側の分岐が変わる**なら必ず書く |
| **生成物** | schema から作る型・SDK・ドキュメントが追随しているか。**再生成して差分が出ないこと**を確認した出力 |

## reviewer への追加の問い

この分冊が当たる board では、依頼文に次の 3 問を足す。番号はベースの 1〜7 と close gate の 8 に続ける。

⚠ **3 問とも「board に書かれていることだけ」で答えさせる。**reviewer は board しか持たないので、**実物の migration や呼び出し元の網羅性は検査できない**（ベースの問 3 と同じ制約）。**書かれていないことを見つけるのが、この 3 問の役目である。**

9. **データ構造の変更について、この board だけで «出荷後に取り返せるか» を判断できるか。**判断できないなら、**足りない項目**を名指しする。戻せないのに戻せると読める記述も示す。
10. **外部から見える契約の変更について、この board だけで «呼ぶ側が何をすればよいか» を判断できるか。**判断できないなら、**足りない項目**を名指しする。
11. **「無し」「変更なし」と書かれている項目のうち、根拠が書かれていないものはどれか。**

**9〜11 のどれかに指摘が残っている状態で close を承認させない。**指摘を直すか、**直さない理由を board に書いて、それ自体を判断材料にする。**直し方は base final-check の「指摘への応じ方」に従う — 9〜11 は情報を引き込み、close gate の問 8 がそれを正しい場所へ動かす。**対の力として両方使う。**
