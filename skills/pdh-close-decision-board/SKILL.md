# pdh-close-decision-board

このファイルは、**close 前 gate（`PDH-human-review`）の判断ボードだけを扱う。**

**先に [pdh-decision-board-base](../pdh-decision-board-base/SKILL.md) を全文読む。**

⚠ **継承の範囲は «ベースの全部» とする。**節を列挙して絞らない — 列挙は漏れるし、ベースに節が増えたときにここが古くなる。**このファイルは、ベースへ足す差分だけ**を書く。実装前 gate の差分（[pdh-ticket-decision-board](../pdh-ticket-decision-board/SKILL.md)）はこの gate では使わない。下の比較表は、何が違うかを示すためだけに実装前 gate を参照する。

⚠ **同じ主題についてベースと両方に規則があるときは、この skill が優先する。**ベースが gate 側に委ねている 2 つを、この gate では次のとおり定める。

- ベースの `N = 0` は、何の承認を求めるかを gate 側に委ねる。**この gate の承認文は «この達成で ticket を閉じてよいか» であり、AC の承認は求めない**（下記「実装前 gate と何が違うか」）。
- ベースの「主線の構成 — 共通則」は、固定部を gate 側に委ねる。**この gate の固定部は 4 面（決定サマリー / 出来上がりの像 / AC ごとの達成 / 返す）**で、それ以外は裏付けとして「返す」の後ろに置く（下記「主線は 4 面 — 残りは裏付け」）。

媒体を HTML にする場合の renderer も、ベースの[render-html-common.md](../pdh-decision-board-base/render-html-common.md) と[create-doc.md](../pdh-decision-board-base/create-doc.md) /[create-slides.md](../pdh-decision-board-base/create-slides.md) を使う。

## この gate で承認者が見るもの — 想定と出来上がりのずれ

PDH はこの gate の目的を「coding agent がやったこと・達成したことがユーザの想定と合っているかをすり合わせる」と定める（`docs/product-delivery-hierarchy.md`「PDH-human-review」）。承認者が持っている想定は、実装前 gate で承認した ticket — Why・AC・解き方・合意済みの像 — である。board の仕事は、その想定と出来上がりを並べ、**ずれを書き手が先に全部見つけて、承認者にはずれを受け入れて閉じるか、差し戻すかだけを残す**ことである。

したがって主線に置くのは、**何のためだったか・何ができるようになったか・AC ごとに達したか・何を残したか**の 4 つで、承認者はこれで閉じてよいかを決める。差分の規模、テストの出力、直さなかった指摘の 1 件ごと、確かめる手順は、疑ったときに開く裏付けである。

**出荷して壊れうるもの — 保存されている形の変更と、外部から見える契約の変更 — は、それを含む ticket でだけ重点になる。**該当するかは書き手が手順 0 で判定し（判定の仕方は [ship-risk.md](ship-risk.md)「当たらないと判定する前に」）、当たれば同じ分冊を読んで裏付けに節を足す。当たらない ticket では、差分の規模の節の 1 行で終える。**該当しない ticket に «無し» の根拠を節で書かせない** — 承認者が閉じるかどうかの判断に使わない情報である。

## 書き始める前に — 実装が固まっているか

⚠ **board を書き始めるのは、コードのレビューと本番の確認が終わってからにする。**

**実装がまだ動きうる間に board を書くと、board が実装を追いかけ始める。**変更が入るたびに
AC の達成状況・出荷済みかどうかを書き直すことになり、**その書き直しが判断を
良くすることはない。**

⚠ **それでも実装が変わったら、直すのは «事実» だけにする** — 何ができるようになったか、
AC の達成、確かめていないこと（ship-risk が当たる ticket では保存されている形と外部契約も）。**規模やテストの件数は直さない**
（ベース「まず、その数は判断を変えるか」）。

⚠ **gate の直前に scope が増えた（AC が足された）ときは、board を直す前に証拠を作り直す** —
テスト、画面の像、本番の確認。**証拠が固まる前に board を書くと、書いたそばから古くなる。**

## 実装前 gate と何が違うか

**承認する対象が違う。**実装前は「この契約で作ってよいか」、close 前は**「作ったものは想定どおりか。この達成で閉じてよいか」**である。契約（ticket と AC）は既に承認済みなので、**もう一度承認を求めない。**

| | 実装前 gate | **close 前 gate（この skill）** |
|---|---|---|
| 承認するもの | AC と、未確定の判断 | **この達成で ticket を閉じてよいか** |
| AC の扱い | 全件を承認対象として出す | **全件に「達したか」と「その証拠」を付けて主線に置く。承認は求めない** |
| 未確定 | 判断として残す | **残っていること自体が判断材料。直さなかった指摘を全件出す** |
| 既定の判断数 | ticket による | **`N = 0`（承認だけ）が既定。**増える条件は下記「判断の数」 |
| 重点 | なぜ作るか | **達成したか。想定と何がずれたか** |

## 主線は 4 面 — 残りは裏付け

**主線 = 決定サマリー / 出来上がりの像 / AC ごとの達成 / 返す、の 4 面 + 判断の数 `N`**（実装前 gate は固定 5 面 + `N`）。承認者はこの 4 面で閉じるかを決め、残りは**疑ったときに開く裏付け**として「返す」の**後ろ**へ置く。裏付けの先頭に「ここから先は、決めるために読む必要はない」と明記する（base の付録と同じ扱い）。

- **決定サマリー** — base の 6 つの答え。⚠ **1 行目の「この作業は何のためか」は close 板でも省かない** — **この ticket が何を作ろうとしていたか**を書く。close 板は «出来上がったもの» から書き始めたくなるが、**目的が無いと、達成・未達・撤去のどれも «何に対して» なのか分からない。**⚠ **出荷しないで閉じる板ほど要る** — 何も出荷しない結論だけを読まされた承認者は、**そもそも何をしようとしていたのか**を復元できない。「確かめた事実」の行には AC の達成状況（全件達した / n 件が部分・未達）を、「まだ確かめられないこと」の行には直さなかった指摘の件数と未確認の有無を書く。ship-risk が当たる ticket では、保存されている形と外部契約の変更の有無を 1 行ずつ足す。
- **出来上がりの像** — 冒頭に「何ができるようになったか」を利用者の言葉で 1〜2 文（ticket の Why ではなく**終わった結果**。⚠ 利用者の挙動が変わらない ticket では効果を発明せず、誰が・どの場面で・何を新しくできるようになったかを事実で書く。書けるものが無いなら「利用者から見た変化は無い」と書き、裏付けで «無いことの根拠» を示す）。像そのものはベースの承認カードの型のとおり、変更前と変更後を同条件で並べる。実装前 gate で承認した像（合意済みの画像）があれば、実物と並べて一致・不一致を書く。
- **AC ごとの達成** — AC 全件に、**達した / 部分的に達した / 達していない**と、**証拠を 1 行**（テストの名前、実行した操作、画面、出力。**「実装した」は証拠ではない**）。間接的にしか確かめていないなら、そう書く。別の経路の結果から推測しているなら、推測だと書く。証拠の生出力・手順は裏付けへ畳む。**AC の文面は ticket の最新版と一致させる。**実装中に AC が変わったなら、**変わったこと・理由・いつ承認されたか**を書く（承認を得ずに変えた AC があるなら、**それは gate を止める理由である**）。
- **返す** — 承認文・得失・承認が間違いになる条件（観測できる症状）・回答 UI。ship-risk が当たる ticket では「戻せるか」の 1 行を足す（詳細は裏付けへ参照）。⚠ `N = 0` でも «承認する / 承認しない» を選ばせ、コメント欄を置く（ベースの `N = 0` の節）。`N` があるなら AC ごとの達成と返すのあいだに置く。

**裏付けとして必ず含める内容**（順不同。それぞれの書き方は下記の各節が定める）:

- **差分の規模**
- **テストと動作確認** — 出力そのもの。
- **直さなかった指摘** — 全件。件数を先に。**畳まない** — 何を直さなかったかは、直したことと同じ重さの判断材料である。
- **自分で確かめる手順** — 承認者が自分の目でも見たい場合の任意の追体験。
- ship-risk が当たる ticket だけ — **保存されている形の変更**と**外部から見える契約の変更**（[ship-risk.md](ship-risk.md)）。

裏付けの節の中でも、**主文は結論と判断が乗る事実だけ**にし、確認コマンド・生出力・数え上げ・手順詳細は畳む（summary は結論そのもので書く — base「作業経緯は畳む」）。初実走の board はこの階層が無く、全項目を同格の主線に並べて契約と復旧の節に詳細が堆積した（base の examples.md 2026-08-19 / 2026-08-20）。

## 差分の規模

**承認者が「どれくらいのものを承認するのか」を掴むために置く。**行数そのものが良し悪しではないので、**評価を付けない。**

⚠ **ここは «規模の目安» である**（ベース「まず、その数は判断を変えるか」）。**行数を正確に詰めない。**
承認者はソースを読まないので、**行数の誤差で判断は変わらない。**

**書くのは «どこが変わったか» を主にする。**

- **変わったのは何か**を、まとまりごとに 1 行（app 本体 / テスト / DB の移行 / client / 設定 / 文書）。
  ⚠ **DB の移行と、外部から見える契約に触るものは、必ず名指しする** — これは規模ではなく
  «判断が変わる事実» なので、行数と違って落としてはならない。
  触らない ticket では、ここに「保存されている形と外部から見える契約に変更なし — <確かめた範囲>」と
  1 行書いて終える（[ship-risk.md](ship-risk.md) が当たらない ticket で、この 2 つについて書く唯一の記述）。
- **どちらが多いか**（主に足したのか、主に消したのか）。⚠ **削除が追加を上回る ticket では、削除を先に書く。**追加を先に固定すると、主に消す作業の規模が逆に読める。
- **削除だけのファイル**と**新規ファイル**の有無。
- 大きさを添えるなら **おおよその行数**でよい（「およそ +1700 / −850 行」）。**1 行単位で合わせない。**

**次の 2 つは、規模の話から外して読ませる。**混ぜると規模を読み違える。

- **書き手の作業記録** — ticket、note、作業ログ。**プロジェクトがこれをコードと同じ commit に載せる場合、合計の 2 割を超えることがある。**⚠ **これを含む数を board に書くと、board を直すために note を書くたびに数が古くなる**（ベースの「board を書く行為で変わる数を書かない」）。
- **自動生成されるもの** — schema から作る型、SDK、lock ファイル、スナップショット。

⚠ **ただし、生成物のうち «外部から見える契約» を表すものは、規模の話から外しても「外部から見える契約の変更」の節から外さない。**API schema の生成物が動いていることは、**契約が変わった証拠そのもの**である。規模の話で小さく見せ、契約の話で落とす、という二重の取り落としが起きる。

## テストと動作確認

**テストは独立した節を持つ。**裏付けの中でも 1 節で、要約に 1 行で混ぜない（ユーザ指示 2026-08-15）。面のある媒体では**テスト専用の面**を作る。

### 先頭に、合否と、飛ばしたものの有無

節の先頭に置くのは **«全部通ったか» と «飛ばした・実行できなかったものがあるか»** である。
⚠ **件数は目安でよい**（ベース「まず、その数は判断を変えるか」）— **169 か 168 かで判断は変わらない。**
⚠ **合否と «飛ばしたもの» は目安ではない。**ここは正確に書く。

**2 種類のテストを «分けて» 示す。**合算した 1 つの数だけを出さない。

| 種類 | 何を指すか |
|---|---|
| **恒久テスト**（application test） | スイートに常設され、**この ticket が閉じたあとも回り続ける**もの |
| **ticket 固有の一時確認**（ticket test） | この ticket の変更を確かめるためだけのもの。**close 後は回らない**（ドライラン、本番の smoke test、ブラウザでの確認もこれに当たる） |

**片方が無いなら «無い» と書く。**⚠ **「一時確認は 0 件」と書く前に、スイート外で走らせた確認を数え直す** — 手で回した確認は、忘れると 0 件に見える。

続けて、**スイート自身の要約行をそのまま貼る。**「全部通りました」と言い換えない。
⚠ **貼る生出力は目安ではない** — 書き手が主張した数ではなく、**道具が出した合否そのもの**だからである。

- **通らなかったもの、飛ばしたもの、環境の理由で実行できなかったものを明示する。**実行できなかったものは、**失敗と同じ扱い**で書く。
- **再実行で通ったもの**は、通った・落ちた・飛ばしたのどれとも違う 4 つ目として、**件数と名前を出す。**緑の要約に畳まない。
- **環境エラーで test が 1 件も走らないまま失敗した区分**（依存の欠落など）は、再実行で通ったものに数えない — **「初回に実行不能だった区分」という 5 つ目**として名前を出し、環境を直して**全区分を回し直し**、初回と再実行の**両方の要約を貼る**。「retry-pass 0 件」とだけ書くと、初回の失敗表示との食い違いに見える（実測 2026-08-19: 依存欠落で 5 区分が 0 秒 FAIL → 全件回し直しで green。この経緯を独自定義の語で要約して reviewer に 2 周指摘された）。
- **どの commit に対する結果か**を書く。あとで変更したなら、**その結果は無効**である。

### そのあとに、テストの中身

**件数の下に、テストが «何を守っているか» を書く。**1 か所に詰めず、**まとまりごとに分ける**（面のある媒体では複数の面、文書では複数の小見出し）。

まとまりの切り方は、テストファイルではなく**守っている契約**で決める。「この一覧のテスト」ではなく「**この約束が破れたら落ちる**」で書く。

各まとまりに置くもの。

- **何を守っているか** — 1 文。契約の言葉で書く
- **破れたら何が起きるか** — 落ちたときに読み手が気づくこと
- 恒久 / 一時のどちらか。⚠ **まとまりごとの件数は要らない**（規模の目安であって、判断を変えない）

⚠ **数が多い場合も、代表例だけにして «ほか N 件» で畳まない。**畳んだ分は、**承認者から見えないまま承認される。**まとまりの数を増やして分ける。

⚠ **「テストが通った」と「テストが正しいものを見ている」は別である。**わざと壊して落ちることを確かめたなら（変異・mutation）、**その結果も件数で出す** —⚠ **落ちなかった契約があれば、それは «守られていない契約» である。**

## 直さなかった指摘

**直さなかった指摘を全件書く。**処置は 4 つ — **いま直した / 別 ticket にした（その ticket 名）/ 記録だけ残した / 退けた（前提が違う）**。「後で起票する」は処置ではない。**この gate までに起票する。**

⚠ **1 件ずつの一行理由が要るのは、直さなかった 3 つ**（別 ticket / 記録だけ / 退けた）。**この 3 つは «判断が変わる数» なので、件数も中身も正確に書く。****直さなかったものがゼロなら、ゼロと明記する。**

⚠ **いま直したものは、件数すら要らない** — 直っているものの理由も数も、判断材料にならない。
何巡回したか（例:「コードに 2 巡・この board に 3 巡」）だけ書けば足りる。
**総数を合わせようとすると、レビューを 1 巡増やすたびに board の数が古くなる。**

**同じ原因が他の場所にもありうるなら、その場所を数える。**「ほかにもあるかもしれない」のまま承認を求めない（ベースの「大きさの分からないリスクを受容させない」と同じ）。

## 自分で確かめる手順

**承認者が自分で見るための手順**であって、書き手の作業ログではない。

- 画面なら **URL と、押す場所・見るもの**。API なら **コマンドと、期待する status と中身**。
- 認証が要るなら**その取り方**（値そのものは書かない）。
- **agent 用の自動操作コマンドを、承認者の手順として出さない。**
- 手作業の準備が要るなら、**補助スクリプトを置いて path を渡す。**

## 判断の数

**既定は `N = 0`（承認だけ）。**close 前 gate では、判断の材料は出そろっていて、残っているのは「この達成で閉じるか、閉じないか」だからである。

**`N` が増えるのは、書き手が決められないものが残っているときだけ。**指摘に由来するかは問わない。次が該当する。

- 直さなかった指摘のうち、**別 ticket にするか記録だけにするか**が、プロダクトの価値に関わる。
- **部分達成・未達の AC、または「未確認」を残したまま閉じるかどうか。**
- ship-risk が当たる ticket で、**後方非互換をいつ・誰に予告するか**、**不可逆な操作をいつ実行するか**（migration の本番適用、データの削除）。

**書き手が決められることを判断にしない。**ベースの「唯一の検査」と「判断の分類」の最初の篩をそのまま当てる — どちらに決めても ticket の達成が同じなら、それは判断ではない。

## 完成検査

**形・文・判断の 3 層はベースと同じ。**独立 reviewer への 7 問も、量の門もそのまま使う — 問 2 が「出来上がりが Why と AC に届いたと board から読めるか」を聞き、量の門が主線の太りを測る。

⚠ **主線に «承認者が使わない情報» が無いかを、reviewer に聞かない。**以前はこの gate だけ問 8 としてそれを聞いていたが、同じ reviewer が「足りない項目を名指しせよ」の側も答えるため、**足す力が勝って再発した**（[base の examples.md](../pdh-decision-board-base/examples.md) 2026-08-20 と、その後の再発）。判定はベースの[final-check.md](../pdh-decision-board-base/final-check.md)「量の門」が持つ。

ship-risk が当たる ticket では、[ship-risk.md](ship-risk.md)「reviewer への追加の問い」の問 9〜11 を足す。

**問 9〜11 に指摘が残っている状態で close を承認させない。**指摘を直すか、**直さない理由を board に書いて、それ自体を判断材料にする。**直し方は base final-check の「指摘への応じ方」に従う。⚠ **9〜11 は情報を引き込む問いなので、応じた後は必ず量の門を回す。**
