# pdh-close-decision-board

このファイルは、**close 前 gate（`PDH-human-review`）の判断ボードだけを扱う。**

**先に [pdh-decision-board-base](../pdh-decision-board-base/SKILL.md) を全文読む。**

⚠ **継承の範囲は «ベースの全部» とする。**節を列挙して絞らない — 列挙は漏れるし、ベースに節が増えたときにここが古くなる。**このファイルは、ベースへ足す差分だけ**を書く。実装前 gate の差分（[pdh-ticket-decision-board](../pdh-ticket-decision-board/SKILL.md)）はこの gate では使わない。下の比較表は、何が違うかを示すためだけに実装前 gate を参照する。

⚠ **同じ主題についてベースと両方に規則があるときは、この skill が優先する。**ベースが gate 側に委ねている 2 つを、この gate では次のとおり定める。

- ベースの `N = 0` は、何の承認を求めるかを gate 側に委ねる。**この gate の承認文は«出荷してよいか» であり、AC の承認は求めない**（下記「実装前 gate と何が違うか」）。
- ベースの「主線の構成 — 共通則」は、固定部を gate 側に委ねる。**この gate の固定部は 3 面（決定サマリー / 出来上がりの像 / 返す）**で、検証の材料は裏付けとして「返す」の後ろに置く（下記「主線は 3 面 — 残りは裏付け」）。

媒体を HTML にする場合の renderer も、ベースの[render-html-common.md](../pdh-decision-board-base/render-html-common.md) と[create-doc.md](../pdh-decision-board-base/create-doc.md) /[create-slides.md](../pdh-decision-board-base/create-slides.md) を使う。

## 実装前 gate と何が違うか

**承認する対象が違う。**実装前は「この契約で作ってよいか」、close 前は**「作ったものを出してよいか」**である。契約（ticket と AC）は既に承認済みなので、**もう一度承認を求めない。**

| | 実装前 gate | **close 前 gate（この skill）** |
|---|---|---|
| 承認するもの | AC と、未確定の判断 | **出荷してよいか** |
| AC の扱い | 全件を承認対象として出す | **全件に「達したか」と「その証拠」を付ける。承認は求めない** |
| 未確定 | 判断として残す | **残っていること自体が判断材料。直さなかった指摘を全件出す** |
| 既定の判断数 | ticket による | **`N = 0`（承認だけ）が既定。**増える条件は下記「判断の数」 |
| 重点 | なぜ作るか | **何が壊れうるか** |

**この gate で承認者が本当に見るのは 2 つである** — **データ構造の変更**と、**外部から見える契約の変更。**この 2 つは、間違えると**出荷後に取り返しがつかない。**他のコードは直せば済むが、**書き換えたデータと、既に呼ばれている API は戻せない。**

したがって主線は、この 2 つを**先に**置く。

## 主線は 3 面 — 残りは裏付け

**主線 = 決定サマリー / 出来上がりの像 / 返す、の 3 面 + 判断の数 `N`**（実装前 gate は固定 5 面 + `N`）。承認者はこの 3 面だけで判断でき、残りは**疑ったときに開く裏付け**として「返す」の**後ろ**へ置く。裏付けの先頭に「ここから先は、決めるために読む必要はない」と明記する（base の付録と同じ扱い）。

- **決定サマリー** — base の 5 行。「確かめた事実」の行の先頭に、**データ構造の変更の有無と、外部から見える契約の変更の有無を 1 行ずつ**置く。この 2 つは間違えると出荷後に取り返しがつかないので、裏付けを開かなくても有無が見える場所に出す。
- **出来上がりの像** — 冒頭に「何ができるようになったか」を利用者の言葉で 1〜2 文（ticket の Why ではなく**終わった結果**。⚠ 利用者の挙動が変わらない ticket では効果を発明せず、誰が・どの場面で・何を新しくできるようになったかを事実で書く。書けるものが無いなら「利用者から見た変化は無い」と書き、裏付けで «無いことの根拠» を示す）。像そのものはベースの承認カードの型のとおり、変更前と変更後を同条件で並べる。
- **返す** — 承認文・得失・承認が間違いになる条件（観測できる症状）・「戻せるか」の 1 行（詳細はデータ構造の裏付けへ参照）・回答 UI。⚠ `N = 0` でも «承認する / 承認しない» を選ばせ、コメント欄を置く（ベースの `N = 0` の節）。`N` があるなら像と返すのあいだに置く。

**裏付けとして必ず含める内容**（順不同。それぞれの書き方は下記の各節が定める）:

- **データ構造の変更** — 無ければ「無し」と根拠を書く。空欄で飛ばさない。
- **外部から見える契約の変更** — 同上。
- **差分の規模**
- **AC と証拠** — AC 全件に、達したかとその証拠。
- **テストと動作確認** — 出力そのもの。
- **直さなかった指摘** — 全件。件数を先に。**畳まない** — 何を直さなかったかは、直したことと同じ重さの判断材料である。
- **自分で確かめる手順** — 承認者が自分の目でも見たい場合の任意の追体験。

裏付けの節の中でも、**主文は結論と判断が乗る事実だけ**にし、確認コマンド・生出力・数え上げ・手順詳細は畳む（summary は結論そのもので書く — base「作業経緯は畳む」）。初実走の board はこの階層が無く、全項目を同格の主線に並べて契約と復旧の節に詳細が堆積した（base の examples.md 2026-08-19 / 2026-08-20）。

## データ構造の変更 — 重点

**対象は「保存されている形」すべて。**DB の table と column、migration、保存する JSON の形、ファイル形式、cache の key、queue に載せる message、保存する成果物。

⚠ **契約を «書いた文書» は、この節ではなく «外部から見える契約» に入れる。** API schema、生成した型、SDK は、保存されたデータではなく**約束の記述**である。**この節に入れると 2 箇所へ重複して載り、承認者はどちらを読めばよいか決められない。**

⚠ **「無し」と書くときも、根拠を 1 行付ける** — **何を検索し、どの範囲を見て、無いと判定したか。**根拠の無い「無し」は、承認者が検算できない（外部契約の側と同じ扱い）。

**変更があるなら、次を全部書く。**書けない項目は「未確認」と明記する。⚠ **「未確認」を残したまま close の承認を求めない。**残っているなら、**取得できない理由**と**その状態で出す判断**を、判断（`N`）として承認者に出す。

| 書くこと | 具体 |
|---|---|
| **何を何にしたか** | 追加・変更・削除を分けて。列名・型・既定値・NULL 可否まで |
| **既存のデータはどうなるか** | そのまま残る / 変換する / 消える。**変換できない行の扱い**も |
| **件数** | 本番で何行が対象か。**数えていないなら「数えていない」と書く** |
| **戻せるか** | migration に down があるか。**down があっても、変換で失った値は戻らない**なら、そう書く |
| **止まるか** | 実行に要する時間、その間の利用者への影響、途中で失敗したときの状態 |
| **読む側・書く側の同時性** | 新しいコードが古いデータを読むか、古いコードが新しいデータを読むか。**デプロイ中に両方が同時に動く**なら、そのときの挙動 |

**「戻せる」とだけ書かない。**復旧の記述は次の 3 点を満たす（3 点とも、初実走の close board で reviewer に刺されて直した実測がある — base の [examples.md](../pdh-decision-board-base/examples.md) 2026-08-19）。

- **復旧元は、merge 後も動かない commit ID で書く。**「main の内容へ戻す」は出荷前にしか成立しない — merge した瞬間に main はこの変更を含む側を指し、feature branch は削除される。復旧コマンドが参照してよいのは固定の commit ID だけ。後続変更を上書きする可能性と、その可否を誰が判断するかも書く。
- **「戻せる」は対象を分けて書く。**最低でも「実装ファイル（版管理で戻る）/ 作業記録（戻さない — 何をしたかの履歴そのもの）/ 出荷後に生まれる成果物（発行済み文書・生成物。戻すのか、残すのか）」の 3 つに分け、まとめて「全部戻る」と書かない。
- **復旧操作は、書く前にドライランする。**一時的な作業コピーで実行し、結果（対象の差分が空になる等）を board に書く。実行していないなら「未実行」と明記し、確度を下げる。机上で書いた復旧手順は成立しないことがある — 初実走では 2 案（一括 revert / main への checkout）が両方とも机上の誤りだった。

⚠ **戻す操作があることと、戻せることは別である。**列を落とす `down` があっても、**`up` が既存行の値を書き換えていれば、その値は戻らない。**「形は戻る／中身は戻らない」を分けて書く（実測: 5 列を追加する migration に列を落とす `down` があったが、`up` は既存行のデータ移行も行っており、`down` ではその移行結果が失われる）。

**列を足すだけ・index を足すだけで、既存の値を書き換えないなら、そう書いて短く終える。**危険の大きさに合わせる。**存在しない危険をあるように見せない**のも、この節の仕事である。

**複数の migration が並行して作られた可能性を確かめる。**同じ番号・同じ親を持つ migration が別々の作業で採番されると、合流した時点で適用できなくなる。**この gate で確かめる**（プロジェクトが検査を持つなら、その出力を証拠として貼る）。

## 外部から見える契約の変更 — 重点

**対象は「こちらの都合で変えると、呼ぶ側が壊れるもの」すべて。**HTTP API の path・method・ request と response の形・status code・error の形、SDK の公開関数と型、CLI の引数と出力、 webhook や通知の形、設定ファイルのキー、画面上の操作の意味。

⚠ **「無し」と書くときも、根拠を 1 行付ける**（データ構造の側と同じ）。

**変更があるなら、次を全部書く。**書けない項目は「未確認」と明記する。⚠ **「未確認」を残したまま close の承認を求めない**（データ構造の側と同じ。残すなら判断にする）。

| 書くこと | 具体 |
|---|---|
| **追加・変更・削除** | 3 つを分けて。**削除と «意味が変わった変更» を同じ行に混ぜない**。1 件ごとに **path と method（または関数名・引数）／ 名前 ／ 型 ／ 必須か ／ null を取るか ／ 既定値 ／ 無いときの意味** を書く。**「field が増えた」だけでは、呼ぶ側は何もできない** |
| **呼ぶ側は何をすればよいか** | 何もしなくてよい / 直す必要がある / 直さないと壊れる。**どれかを明記する** |
| **後方互換か** | 互換でないなら、**いつから壊れるか**と**予告したか**。予告していないなら「未予告」と書く |
| **誰が呼んでいるか** | 呼び出し元を数える。**数えられないなら「数えられない」と書き、その理由も** |
| **error の変わり方** | 成功が失敗になる／失敗が成功になる／status code が変わる。**呼ぶ側の分岐が変わる**なら必ず書く |
| **生成物** | schema から作る型・SDK・ドキュメントが追随しているか。**再生成して差分が出ないこと**を確認した出力 |

**「内部の変更だけです」と書く前に、外へ出る経路を実際にたどる。**内部の関数名の変更でも、その値が response や log に載っていれば外から見える。

⚠ **変更したファイルの置き場所で判定しない。**「API のディレクトリを触っていないから契約は動いていない」は、**たどったことにならない。**外へ出る値を返している箇所から遡って確かめる。**削除も同じ**である — 消したものが外から呼ばれていないことを、**呼び出し元を検索して**示す。

**利用者から見た挙動が変わらない ticket**でも、この節を空欄にしない。**「変わらないことを、どう確かめたか」**を書く（ベースの risk overlay 「公開された契約が変わらない」と同じ扱い）。

## 差分の規模

**承認者が「どれくらいのものを承認するのか」を掴むために置く。**行数そのものが良し悪しではないので、**評価を付けない。**

- **合計の追加行と削除行**、変更したファイル数。⚠ **削除が追加を上回る ticket では、削除を先に書く。**追加を先に固定すると、主に消す作業の規模が逆に読める（実測: 追加 2570 行に対し削除 4243 行という ticket がある）。
- **主な変更ファイル**を、行数の多い順に。**上限 20 件**（超える分は分類ごとの件数にまとめる。ベースの「巨大な集合には列挙上限を置く」と同じ）。
- **削除だけのファイル**と**新規ファイル**は分けて数える。

**次の 2 つは、合計から分けて出す。**混ぜると規模を読み違える。

- **書き手の作業記録** — ticket、note、作業ログ。**プロジェクトがこれをコードと同じ commit に載せる場合、合計の 2 割を超えることがある**（実測: 追加 4376 行のうち 953 行 = 22%）。
- **自動生成されるもの** — schema から作る型、SDK、lock ファイル、スナップショット。

⚠ **ただし、生成物のうち «外部から見える契約» を表すものは、行数を分けても「外部から見える契約の変更」の節から外さない。**API schema の生成物が動いていることは、**契約が変わった証拠そのもの**である。規模の話で小さく見せ、契約の話で落とす、という二重の取り落としが起きる。

**取得したコマンドを書く。**承認者が同じ数を出せるようにする。

## AC と証拠

AC 全件に、次の 3 つを付ける。

- **達したか** — 達した / 部分的に達した / 達していない。
- **証拠** — テストの名前、実行した操作、画面、出力。**「実装した」は証拠ではない。**
- **間接的にしか確かめていないなら、そう書く。**別の経路の結果から推測しているなら、推測だと書く。

**AC の文面は ticket の最新版と一致させる。**実装中に AC が変わったなら、**変わったこと・理由・いつ承認されたか**を書く（承認を得ずに変えた AC があるなら、**それは gate を止める理由である**）。

## テストと動作確認

**テストは主線に独立した節を持つ。**要約に 1 行で混ぜない（ユーザ指示 2026-08-15）。面のある媒体では**テスト専用の面**を作る。

### 先頭に、件数と概要

節の先頭で**数を先に**出す。⚠ **2 種類の数を «分けて» 出す。**

| 種類 | 何を数えるか |
|---|---|
| **恒久テスト**（application test） | スイートに常設され、**この ticket が閉じたあとも回り続ける**もの |
| **ticket 固有の一時確認**（ticket test） | この ticket の変更を確かめるためだけのもの。**close 後は回らない** |

**この 2 つを合算した数だけを出さない。**片方が 0 でも、**0 と書く。**恒久テストは**この ticket で増えた数と、既にあった数**を分けると、「何を新しく守るようにしたか」が読める。

続けて、**スイート自身の要約行をそのまま貼る。**「全部通りました」と言い換えない。

- **通らなかったもの、飛ばしたもの、環境の理由で実行できなかったものを明示する。**実行できなかったものは、**失敗と同じ扱い**で書く。
- **再実行で通ったもの**は、通った・落ちた・飛ばしたのどれとも違う 4 つ目として、**件数と名前を出す。**緑の要約に畳まない。
- **環境エラーで test が 1 件も走らないまま失敗した区分**（依存の欠落など）は、再実行で通ったものに数えない — **「初回に実行不能だった区分」という 5 つ目**として名前を出し、環境を直して**全区分を回し直し**、初回と再実行の**両方の要約を貼る**。「retry-pass 0 件」とだけ書くと、初回の失敗表示との食い違いに見える（実測 2026-08-19: 依存欠落で 5 区分が 0 秒 FAIL → 全件回し直しで green。この経緯を独自定義の語で要約して reviewer に 2 周指摘された）。
- **どの commit に対する結果か**を書く。あとで変更したなら、**その結果は無効**である。

### そのあとに、テストの中身

**件数の下に、テストが «何を守っているか» を書く。**1 か所に詰めず、**まとまりごとに分ける**（面のある媒体では複数の面、文書では複数の小見出し）。

まとまりの切り方は、テストファイルではなく**守っている契約**で決める。「この一覧のテスト」ではなく「**この約束が破れたら落ちる**」で書く。

各まとまりに置くもの。

- **何を守っているか** — 1 文。契約の言葉で書く
- **破れたら何が起きるか** — 落ちたときに読み手が気づくこと
- **件数**と、恒久 / 一時のどちらか

⚠ **数が多い場合も、代表例だけにして «ほか N 件» で畳まない。**畳んだ分は、**承認者から見えないまま承認される。**まとまりの数を増やして分ける。

⚠ **「テストが通った」と「テストが正しいものを見ている」は別である。**わざと壊して落ちることを確かめたなら（変異・mutation）、**その結果も件数で出す** —⚠ **落ちなかった契約があれば、それは «守られていない契約» である。**

## 直さなかった指摘

**レビューで出た指摘を全件書く。**総数を先に出し、**処置ごとの件数**に分ける。処置は 4 つ — **いま直した / 別 ticket にした（その ticket 名）/ 記録だけ残した /退けた（前提が違う）**。「後で起票する」は処置ではない。**この gate までに起票する。**

⚠ **1 件ずつの一行理由が要るのは、直さなかった 3 つ**（別 ticket / 記録だけ / 退けた）。**いま直したものは件数だけでよい** — 直っているものの理由は判断材料にならない。**直さなかったものがゼロなら、ゼロと明記する。**

**同じ原因が他の場所にもありうるなら、その場所を数える。**「ほかにもあるかもしれない」のまま承認を求めない（ベースの「大きさの分からないリスクを受容させない」と同じ）。

## 自分で確かめる手順

**承認者が自分で見るための手順**であって、書き手の作業ログではない。

- 画面なら **URL と、押す場所・見るもの**。API なら **コマンドと、期待する status と中身**。
- 認証が要るなら**その取り方**（値そのものは書かない）。
- **agent 用の自動操作コマンドを、承認者の手順として出さない。**
- 手作業の準備が要るなら、**補助スクリプトを置いて path を渡す。**

## 判断の数

**既定は `N = 0`（承認だけ）。**close 前 gate では、判断の材料は出そろっていて、残っているのは「出すか、出さないか」だからである。

**`N` が増えるのは、書き手が決められないものが残っているときだけ。**指摘に由来するかは問わない。次が該当する。

- 直さなかった指摘のうち、**別 ticket にするか記録だけにするか**が、プロダクトの価値に関わる。
- **後方非互換を、いつ・誰に予告するか。**
- **不可逆な操作を、いつ実行するか**（migration の本番適用、データの削除）。
- **「未確認」が残ったまま出すかどうか。**

**書き手が決められることを判断にしない。**ベースの「唯一の検査」をそのまま当てる。

## 完成検査

**形・文・判断の 3 層はベースと同じ。**独立 reviewer への 6 問もそのまま使う。

**この gate だけ、reviewer への依頼文に次の 4 問を足す。**

⚠ **3 問とも「board に書かれていることだけ」で答えさせる。**reviewer は board しか持たないので、**実物の migration や呼び出し元の網羅性は検査できない**（ベースの問 3 と同じ制約）。**書かれていないことを見つけるのが、この 3 問の役目である。**

7. **データ構造の変更について、この board だけで «出荷後に取り返せるか» を判断できるか。**判断できないなら、**足りない項目**を名指しする。戻せないのに戻せると読める記述も示す。
8. **外部から見える契約の変更について、この board だけで «呼ぶ側が何をすればよいか» を判断できるか。**判断できないなら、**足りない項目**を名指しする。
9. **「無し」「変更なし」と書かれている項目のうち、根拠が書かれていないものはどれか。**
10. **各節の主線に、承認者がその節の判断に使わない情報は置かれていないか。**とくに、書き手が実行する操作の詳細（復旧のコマンド・確認手順・実行フロー）。あればその情報を名指しし、主線から畳み（または属する節）へ移すべきと指摘する。

**7〜10 のどれかに指摘が残っている状態で close を承認させない。**指摘を直すか、**直さない理由を board に書いて、それ自体を判断材料にする。**直し方は base final-check の「指摘への応じ方」に従う — 7〜9 は情報を引き込み、10 がそれを正しい場所へ動かす。**対の力として両方使う。**
