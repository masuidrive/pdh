# pdh-ticket-decision-board

このファイルは、**実装前 gate（`PDH-ticket-human-review`）の判断ボードだけ**を扱う。

**先に [pdh-decision-board-base](../pdh-decision-board-base/SKILL.md) を全文読む。** CSW の考え方、判断の数え方、決定サマリー、判断カードの型、媒体の選び方、renderer、完成検査は、すべてあちらが持つ。このファイルは、実装前 gate に固有の差分だけを書く。 close 前 gate（`PDH-human-review`）は[pdh-close-decision-board](../pdh-close-decision-board/SKILL.md) が扱う。

## この gate で承認するもの — ticket の Why → What → How

**承認者が承認する契約は ticket である。**ticket の `Why / Intent`（誰の何が困っているか）から `What / Acceptance Criteria`（終わると何ができるか）が決まり、`Constraints / Design Decisions` （解き方）がそれを実現する。この gate の承認は**「この Why を、この AC と解き方で解いてよいか」**であり、board は ticket の別紙解説ではなく、この筋を承認者が追加調査なしで承認または指示できる形に組み直した判断面である。**board の内容を board 用に発明しない** — 語を承認者向けに書き直すだけで、約束の中身は ticket の節から取る。ticket に無い内容を board が語り始めたら、 board ではなく ticket を先に直す（下記「board と ticket の関係」）。

## board と ticket の関係

- board は原則として自己完結させる。ticket の参照だけで内容を省略しない。
- board の選択肢と、選択後の ticket の文面を一対一に対応させる。
- board を書く途中で ticket の欠陥を見つけたら、board で判断を求めず、承認前の ticket を先に直す。
- board に表示する AC は、承認対象となる ticket の最新文面と一致させる。
- ticket へ書き戻せない事情がある場合は gate を止める。「承認後に直す」と約束して進めない。

機微な情報を扱う ticket だけは、自己完結を無条件に適用しない。詳細はベースの[risk-overlay.md](../pdh-decision-board-base/risk-overlay.md) を使う。

## 書き始める前に — 未確定の洗い出しは `PDH-ticket-review` の仕事〔手順 1〕

**未確定の洗い出し（`Open Questions` の全件確認・未確認を表す語の検索・断定の裏取り・影響範囲・合意された添付）は、[pdh-dev の `PDH-ticket-review`](../pdh-dev/_flow.md) が調べる場所と確認内容の表を持っている。**board を書く前に、その洗い出しが済んでいて結果が note にあることを確認する。残っていたら board で判断を求めず、`PDH-ticket-review` へ戻って ticket を先に直す。**表をここへ写さない** — 2 箇所に持つと片方だけが更新される。

あちらの表に無い検索だけ、この gate が足す。

- **英語と記号のマーカー** — `draft`、`TBD`、`TODO`、`FIXME`、`needs-*`、 `[NEEDS CLARIFICATION]`、`(?)`。その repo が使う独自マーカーは、既存 ticket を数件開いて見つける。

洗い出した項目は、ベースの「判断の分類」で 3 つに分ける。測定結果が scope・影響範囲・AC を変えたら、ticket を直してから board を作る。

## 主線の固定部 — 5 面。ticket の節をそのまま充てる〔手順 4〕

**主線の面数 = 固定 5 面（なぜ / ゴール / 解き方 / 決めること / 返す）+ 判断の数 `N`**

1. **なぜ** — ticket の `Why / Intent`。誰が何に困り、直さないと何が起きるか。⚠ **まだ誰も困っていない予防の ticket では、«放置するとどの条件で誰が困るか» に置き換える。** **架空の «いま困っている人» を書かない。**
2. **ゴール** — ticket の `What / Acceptance Criteria`。終わると誰が何をできるか。現在と変更後を示す。
3. **解き方** — ticket の `Constraints / Design Decisions` と `Contract / Data Model Impact`。書き手が確定させた解き方と、退けた案。**承認者は AC だけでなく、この解き方ごと承認する** —解き方を裏付けへ落とすと、承認者は「何ができるか」だけを見て「どう作るか」を見ずに承認したことになる。確定判断の無い ticket では「確定判断なし」と 1 行書く（面ごと省かない）。
4. **決めること** — ticket の `Open Questions` のうち、承認者にしか決められないもの。件数、依存順、推奨を先に示す。⚠ **`N` がいくつでも、ここに «AC 全件を承認して実装に入ってよいか» の承認文と、«承認が間違いになる条件» を置く。**判断はその前後に並ぶが、**承認そのものは判断とは別に、必ずこの面に置く。**権限の依頼があれば、判断とは別の欄としてここに置く。
5. **各判断** — ベースの「主線の構成 — 共通則」のとおり。
6. **返す** — 選択内容または承認文をそのまま返せる文章。

なぜとゴールを裏付けへ落とさない。選択肢を比較する基準そのものだからである。各判断がその基準にどう効くかは、判断カードの「ゴールへの効き」の欄（ベース「判断カードの型」）に、Why / AC の言葉で書く。

### `N = 0` のとき

主線には次だけを置く。

1. なぜこの ticket が要るか。
2. 終わると誰の何が変わるか。
3. 書き手が確定させた解き方と、退けた案。
4. **この AC で実装に入ることを承認してほしい**という承認文、AC 全件、承認が間違いになる条件。
5. 承認・修正指示・差し戻しを返すための文章。

## board に必ず含める内容〔手順 4〕

主線と、主線から 1 手で開ける裏付けを合わせて、次をすべて含める。該当しない項目を空欄で残さず、なぜ該当しないかを明記する。

- この ticket が誰の何を可能にするか。
- Why と、上位の目的とのつながり。
- 承認対象となる AC 全件。
- ticket review 中に変えた内容と理由。**復元できないなら「変更なし」と書かず、「記録が無いため復元できない」と書く。**
- 書き手が決めておいた内容と、退けた案。
- scope 外の内容と、外した理由。
- 未確定の判断、選択肢、推奨。
- 計画を崩しうる既知のリスクと依存。
- 承認者へ返してほしい答え。

`N = 0` では未確定の判断と選択肢を作らず、「判断なし。AC の承認だけ」と明記する。

## 選択肢と ticket を一対一にする〔手順 5〕

各選択肢について、選ばれた後の ticket を具体化する。

- ticket のどの節・どの AC が変わるか。件数が変わるなら変更後の数も示す。
- 変更後に、Why・AC・Design Decisions・Out-of-scope が互いに矛盾しないか。
- 判断どうしの依存。別の判断の内容を変える判断を先に置く。
- 依存がある場合は、順序だけでなく後の判断本文にも依存条件を書く。
- 一括承認か、群ごとの承認かを明記する。

承認された選択肢を ticket へ反映できない状態で board を出さない。

## Open Questions を差し戻さない〔手順 2〕

書き手が決められる Open Question は board の前に決める。各項目について採った案と理由、採らなかった案と退けた理由を示し、承認者には覆す道だけを残す。不可逆な決定、プロダクト価値、費用負担など承認者の権限に属する項目は、推奨を付けた判断として残す。
