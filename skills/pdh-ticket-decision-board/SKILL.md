# pdh-ticket-decision-board

このファイルは、**媒体に依存しない判断ボードの規則**である。
判断ボードを作るときは必ず読み、媒体を選んだ後だけ該当する renderer を読む。

日付つきの事故・実測値を調べる必要がある場合だけ [examples.md](examples.md) を読む。通常は読まない。

## 判断ボードとは何か

**判断ボードとは、承認者に留保された判断について coding agent が作成する Completed Staff Work
（CSW）である。**この skill が扱うのは、ticket を書き終えて実装に入る前の
`PDH-ticket-human-review` だけである。**close 前の gate も、実装の途中で AC を変える承認も、
この skill の対象ではない。**

完成条件は 1 つである。

> **承認者が、書き手自身でできたはずの追加調査をせずに、求められた判断を下せる。**

CSW の中核は、書き手が問題を調べ、解決案を完成させ、承認者には承認または指示だけを残すことにある。
この board では、不承認の後に何をするかも書き手が用意する。

## board を作る前に — 目標へ戻る

**以降の規則は、上の完成条件を満たすための手段である。**規則を全部当てることが目的ではない。
board を組み始める前に、次を確認する。

- **この ticket で、承認者が実際に決めることは何か。**先にそれを 1 行で書く。
- **当てようとしている規則は、その判断に効くか。**効かない規則は当てない
  （「規則は、守る対象から適用範囲を決める」）。
- ⚠ **board そのものより、board の作り方を整える作業が長くなっていないか。**
  なっていたら、**規則を足す側ではなく、board を出す側へ戻る。**

## 唯一の検査 — これは誰が決めることか

board のすべての段落に、次の 1 問を当てる。

> **これは承認者が決めることか、書き手が決められることか。**
> **書き手が決められることが書いてあれば、書き手が決めてから書き直す。**

CSW 違反は内容の種類ではなく、board と承認者の関係に現れる。禁止事項の列挙で代用しない。
次の形は、いずれもこの検査に落ちる。

- 書き手が実行できる測定を、選択肢として承認者に指示させる。
- 書き手が欠陥と診断した箇所を直さず、直してよいかを承認者に聞く。
- 書き手の作業経過を、承認者の判断材料の主線に置く。
- 承認者が持っていない変更前の資料を前提に、差分だけを問う。
- 書き手の作業時間を、承認者が負担するコストとして示す。

**「この board で決められるか」と「書き手の片付け残しがないか」は別の検査である。**
「先に測定するよう指示してください」という board は決められてしまうため、両方を別々に検査する。

## 規則は、守る対象から適用範囲を決める

規則を適用する前に、**その規則が何を守るかを 1 文で言う。**言えない規則を機械的に当てない。
たとえば、本文幅は目が次の行を取り違えないため、表の構造は数を復元するため、組版指定は散文を
読みやすくするためにある。対象が違えば、同じ規則を当てない。

念のために足した要素・語・表示・検査は、実在する必要を確認する。確認していない保険は、
存在しない状況をあたかも存在するように見せる。

## board と ticket の関係

**承認者が承認する契約は ticket である。**board は ticket の別紙解説ではなく、ticket の内容を
承認できる形に組み直した判断面である。

- board は原則として自己完結させる。ticket の参照だけで内容を省略しない。
- board の選択肢と、選択後の ticket の文面を一対一に対応させる。
- board を書く途中で ticket の欠陥を見つけたら、board で判断を求めず、承認前の ticket を先に直す。
- board に表示する AC は、承認対象となる ticket の最新文面と一致させる。
- ticket へ書き戻せない事情がある場合は gate を止める。「承認後に直す」と約束して進めない。

機微な情報を扱う ticket だけは、自己完結を無条件に適用しない。詳細は「risk overlay」を使う。

## 書き始める前に、未確定を全部出す

**この洗い出しは本来 `PDH-ticket-review` で済んでいる。**残っていたら board で判断を求めず、
ticket を先に直す。書き手の記憶だけに頼らず、ticket と関連資料から次を機械的に洗い出す。

| 調べる場所 | 確認すること |
|---|---|
| `Open Questions` | 自覚している未確定を全件出す |
| 未確認を表す語 | 「未確認」「要確認」「見込み」「はず」「思われる」「かもしれない」を検索する。**英語と記号のマーカーも探す** — `draft`、`TBD`、`TODO`、`FIXME`、`needs-*`、`[NEEDS CLARIFICATION]`、`(?)`。**その repo が使う独自マーカーは、既存 ticket を数件開いて見つける** |
| AC の数値・件数・対象 | 現時点で数え直せるか確認する |
| contract / data model の記述 | 「変更なし」「不変の見込み」を実体で確かめる |
| 影響範囲 | 列挙した範囲を検索し、列挙しなかった範囲が本当に無関係か確認する |
| ticket が事実として断定する文 | 識別子・個数・呼び出し関係を元の実体に当たる |
| 合意に使われた画像 | 画像を開き、文言・色・導線・並び順を文字でも確認する |

洗い出した項目を 3 つに分ける。

- **書き手が測れる** — board を書く前に測る。
- **実装しないと分からない** — 未測定と明記し、反証条件と停止条件を付ける。
- **承認者にしか決められない** — board の判断にする。**不可逆な決定、プロダクトとしての価値判断
  （利用者から見た挙動・体裁・語）、費用の負担、既知のリスクを残す決定、信頼境界を動かす変更**が
  該当する。**実装方式の差でも、出力・監視・運用手順が変わるなら承認者の判断にする。**
  **どれにも当たらない実装方式・命名・内部構造は、書き手が決める。**

既定は「書き手が測れる」とする。測定結果が scope・影響範囲・AC を変えたら、ticket を直してから
board を作る。**書き手がアクセス手段を持たず測定できない場合は、対象・範囲・取得項目・取得しない
項目・保存先・削除時期を示して、必要な権限だけを依頼する。**依頼は判断ではないので `N` に数えず、
**断られた場合に書き手が採る次善策**を併記する。

## 判断の数でモードを選ぶ

**`N` は «承認者が独立に返答できる指示の単位» の数である。**選択肢の数でも、成果物の数でも、
未確定の項目の数でもない。**判断数そのものも疑い、書き手が決められる項目を数に含めない。**

⚠ **複数の未確定が «同じ 1 つの文・設定・値» を決めるなら、まとめて 1 件と数える。**
別々に選ばせると、組み合わせの数だけ結果ができてしまい、**承認者が «自分が何を承認したか» を
復元できない。**まとめた場合は、**推奨の組み合わせで完成した文面の全文**と、
**別案を選んだときに完成する文面**を board に置く。⚠ **承認者に文章を合成させない。**

そのうえで、次の 3 モードから選ぶ。

### `N = 0` — 承認だけ

架空の選択肢を作らない。「決めてほしいこと」「別案」「失うもの」を空欄で残さない。
主線には次だけを置く。

1. なぜこの ticket が要るか。
2. 終わると誰の何が変わるか。
3. **この AC で実装に入ることを承認してほしい**という承認文、AC 全件、承認が間違いになる条件。
4. 承認・修正指示・差し戻しを返すための文章。

選択肢の集計、回答済み件数、複数回答の同期は置かない。

### `N = 1〜少数` — 個別判断

判断ごとに推奨、代償、**推奨が間違いになる条件**（下記「推奨の書き方」）、具体的な別案を置く。
材料を読んだ直後に回答できるようにする。
複数の判断がある場合は、回答を失わず、未回答を明示し、選択結果をそのまま返せるようにする。

### `N` が多数 — グループ化して段階承認

**目安は 8 件以上**である。判断を意味のまとまりに分け、依存する判断を先に並べ、グループごとに
段階的に承認する。後の判断内容が前の判断で変わる場合は、後の判断本文にも依存を明記する。

決定サマリーの 5 行へ多数の判断を列挙しない。サマリーにはグループ名、今回承認する段階、
未承認で残る段階を書く。1 回の board で認知負荷を下げられない場合は、ticket の契約を分割せず、
同じ ticket に対する複数回の承認状態として扱う。

## 主線の構成

主線は、書き手が調べた順ではなく、承認者が決める順に並べる。

**主線の面数 = 固定 4 面（なぜ / ゴール / 決めること / 返す）+ 判断の数 `N`**

媒体に「面」がない場合も、この情報単位を見出しまたは段落として保つ。

1. **なぜ** — 誰が何に困り、直さないと何が起きるか。
   ⚠ **まだ誰も困っていない予防の ticket では、«放置するとどの条件で誰が困るか» に置き換える。**
   **架空の «いま困っている人» を書かない。**
2. **ゴール** — 終わると誰が何をできるか。現在と変更後を示す。
3. **決めること** — 件数、依存順、推奨を先に示す。⚠ **`N` がいくつでも、ここに «AC 全件を承認して
   実装に入ってよいか» の承認文と、«承認が間違いになる条件» を置く。**判断はその前後に並ぶが、
   **承認そのものは判断とは別に、必ずこの面に置く。**権限の依頼があれば、判断とは別の欄として
   ここに置く。
4. **各判断** — 材料、推奨、代償、反証条件、別案、回答を同じ情報単位に置く。
5. **返す** — 選択内容または承認文をそのまま返せる文章。

なぜとゴールを裏付けへ落とさない。選択肢を比較する基準そのものだからである。
実測の全表、測定ログ、退けた案の詳細、scope 外、リスク、作業経緯は、主線から 1 手で開ける
裏付けまたは付録へ置く。**事実と、書き手がその事実へ至った経緯を同じ段落に混ぜない。**

## 決定サマリー

冒頭に 1 画面相当で置く。通常は次の 5 行だけにする。

1. 今回決めること。
2. 推奨。
3. 確かめた事実。
4. まだ確かめられないこと。
5. 承認後に実装を止める条件。

`N = 0` では 1 行目を承認文にする。多数モードでは個別判断ではなくグループと承認段階を示す。

## board に必ず含める内容

主線と、主線から 1 手で開ける裏付けを合わせて、次をすべて含める。該当しない項目を空欄で
残さず、なぜ該当しないかを明記する。

- この ticket が誰の何を可能にするか。
- Why と、上位の目的とのつながり。
- 承認対象となる AC 全件。
- ticket review 中に変えた内容と理由。**復元できないなら「変更なし」と書かず、
  「記録が無いため復元できない」と書く。**
- 書き手が決めておいた内容と、退けた案。
- scope 外の内容と、外した理由。
- 未確定の判断、選択肢、推奨。
- 計画を崩しうる既知のリスクと依存。
- 承認者へ返してほしい答え。

`N = 0` では未確定の判断と選択肢を作らず、「判断なし。AC の承認だけ」と明記する。

## approve or direct

返答は **approve or direct** にする。不承認だけを求めず、承認しない場合に進む具体的な道を用意する。
`approve or else` は使わない。結果を示さない脅しとして読め、具体的な指示先を表さないためである。

- 推奨は 1 つに絞り、最初に置く。
- 別案を 1 つ以上、推奨と同じ具体性で書く。何をするか、得るもの、失うもの、次に必要な判断を示す。
- 「差し戻す」だけにせず、差し戻した後に書き手が何をするかを書く。
- 選択肢を同格に並べない。別案は、推奨を採らない場合の指示先として置く。
- `N = 0` では別案を捏造しない。修正指示または差し戻しの文章だけを返答欄に置く。

### 作業時間ではなく、動く対象と次の判断を書く

書き手の「半日」「1 時間」のような所要時間を選択コストとして書かない。代わりに次を書く。

- **動く対象** — この資料、ticket 文書、コード、出荷済みの状態のどれが変わるか。
- **次に承認者の判断が要る時点** — 次の human gate、実装中の停止条件、外部承認待ちなど。

「戻せる」とだけ書かない。不可逆な変更には 4 段階では足りないため、risk overlay を追加する。

## 選択肢と ticket を一対一にする

各選択肢について、選ばれた後の ticket を具体化する。

- ticket のどの節・どの AC が変わるか。件数が変わるなら変更後の数も示す。
- 変更後に、Why・AC・Design Decisions・Out-of-scope が互いに矛盾しないか。
- 判断どうしの依存。別の判断の内容を変える判断を先に置く。
- 依存がある場合は、順序だけでなく後の判断本文にも依存条件を書く。
- 一括承認か、群ごとの承認かを明記する。

承認された選択肢を ticket へ反映できない状態で board を出さない。

## 推奨の書き方

推奨は、書き手が調査と比較を終えた結論として 1 つだけ書く。

- **推奨を採ると何を失うか**を書く。書けない場合は比較が終わっていない。
- **推奨が間違いになる条件**を書く。承認者は推奨全体ではなく、この条件を見て覆せる。
  ⚠ **判断の種類で書き方が違う。**
  - **事実で決まる判断**（速いか / 壊れるか / 足りるか）→ **反証条件。**「この測定でこの値が
    出たら推奨は誤り」と、**観測できる形**で書く。
  - **価値で決まる判断**（体裁・語・どこまで開示するか・何を優先するか）→ **推奨を覆す優先条件。**
    「〇〇より△△を重く見るなら別案のほうがよい」と、**承認者が持っている基準**で書く。
    ⚠ **価値の判断に «客観的な反証条件» を求めない。**求めると、ticket に無い基準を書き手が
    発明することになる。
- 退けた案は、何をする案か、得るもの、動く対象、退けた理由を示す。
- 「安い」「面倒」だけで退けない。
- 書き手が測れることを「先に測る案」として置かない。

## 読み手の仕事を増やさない

### 差分で語らない

承認者が変更前の資料を持つと仮定しない。「何を変えたか」だけでなく、**承認する約束そのもの**を
現在形で書く。ticket review 中に AC を変えた事実は隠さず、判断の枠ではなく検証用の注記として、
変更内容と理由を示す。

AC 番号を単独で置かない。番号を出す場所で、意味または原文を同時に確認できるようにする。

### Open Questions を差し戻さない

書き手が決められる Open Question は board の前に決める。各項目について採った案と理由、
採らなかった案と退けた理由を示し、承認者には覆す道だけを残す。不可逆な決定、プロダクト価値、
費用負担など承認者の権限に属する項目は、推奨を付けた判断として残す。

### 大きさの分からないリスクを受容させない

対象を数え、分類し、書き手が片付けられなかった残りだけを判断に出す。「ほかにもあるかもしれない」
のまま広い受容を求めない。数える権限がなければ、必要なアクセスの安全範囲を具体化して依頼する。

### 開示できる不確実性を限定する

調べれば分かる由来・判定方法・件数・過去の実測値は調べる。**実装しないと分からない達成値や
導入可否だけ**を未確定として開示し、反証条件と停止条件を付ける。「推論」は調査省略の札にしない。

### 作業経緯は畳む

判断を変える結論と未測定の事実は主線に置く。実行条件・生ログ・一覧・commit・調査経緯は、
検証できる形で付録へ置く。見出しは「何を測ったか」ではなく、測定から分かった結論にする。

## Acceptance Criteria の書き方

承認者が理解できる言葉へ AC を書き換え、その直下で ticket の原文を項目ごとに確認できるようにする。

- 書き換えで約束を増減させない。言葉、順序、語彙だけを変える。
- AC の群記号、番号、並び順を組み替えない。
- 原文を末尾へまとめず、対応する書き換えの隣に置く。
- 緩い達成条件は、緩いことも判断材料として明記する。
- ticket review 中に AC を直した場合は、ticket を先に更新し、その最新原文を示す。

## 合意済みの画像

要望、報告、回答案に**添付がある場合は board を書く前に開く。**完成形の mockup、試作、
変更前後の比較、仕様書、実データの標本は、合意した文章と同じ重さで扱う。
⚠ **画像に限らない** — PDF、表計算、設計図、ログの抜粋も同じである。

- board に画像そのものを載せるか、安全な参照を置く。
- 画像が決める文言・色・導線・並び順を、画像の隣で文字にもする。
- 画像と異なる提案は、差異と理由を判断として明示する。黙って上書きしない。
- 合意済みかを保存場所だけで推測しない。書き手が確認できなければ承認者の判断にする。

機微な情報を含む画像は inline にせず、risk overlay の秘匿版を使う。

既定では画像を成果物へ埋め込み、board だけで確認できるようにする。媒体が画像を保持できない場合、
または画像の機微性・容量が発行先の制約を超える場合だけ、安全な参照へ切り替えて理由を書く。

## 数と断定の扱い

### 実際の実行条件で測る

測定前に、設定、実行入口、資源配分、並列・直列の関係を確認する。board には測定値だけでなく、
**実際の実行条件**を書く。条件が異なる数値をそのまま比較しない。

### 読み手が検算できる形にする

- 数を出したら、対象集合を数え直せる形にする。
- 推奨の裏付けを 1 例だけにしない。合計を出すか、合計未測定と書く。
- 断定には board 内の証拠を付ける。証拠を載せられなければ確度を下げる。
- 確度を **実測 / 推論 / 測定できていない** に分ける。
- ticket の主張を証拠として循環利用しない。元の実体を確認する。
- 実証できない不存在は、実証できないと書く。
- ⚠ **「同型は n 箇所だけ」「該当なし」と書くときは、数え直しに使った検索条件も書く**
  （検索した語・対象範囲・除外したもの）。書けない列挙は、読み手が検算できない。
- 合計と内訳の関係が並列か直列かを書く。
- 数値目標は、どの処置がどれだけ寄与する見込みかを積み上げる。
- 比較値は同条件で測る。条件差があれば影響を示すか測り直す。

### 巨大な集合には列挙上限を置く

通常の本文で個別に列挙する上限は **20 件**とする。20 件を超える集合は、分類ごとの件数、
代表例、例外、最大影響を本文に置き、完全な manifest は付録または別の生成物へ置く。
本文の分類別件数を足すと総数を復元でき、manifest の生成条件と安定した識別子を辿れる形にする。
プロジェクト規約がより小さい上限を定めていれば、それに従う。

## 読み手を決める

読み手が repo の持ち主とは限らない。board の冒頭か承認表で、**誰が何を承認するか**を決める。

- 読み手が知っているのは、一般的な技術語と、対象 repo に実在する語の存在までとする。
- この ticket の内容、経緯、調査内容、過去の指示文は思い出していない前提にする。
- repo 固有の語は、対象 repo に実在するかを検索して判定する。勝手な略語を作らない。
- repo 外の読み手には、内部識別子だけで意味を伝えず、一般的な技術語は不必要に言い換えない。
- skill 内部の比喩や呼称を成果物へ持ち出さない。「この資料」「判断ボード」のように定義済みの語を使う。
- 規約を根拠にするときはファイル名だけを指さず、判断に必要な規則本文をその場で引用または要約する。

### 主語と目的語を省かない

動詞を書いたら、その 1 文に主語と目的語があるか確認する。とくに比喩の動詞と、指示対象のない
「もの」「こと」「部分」「ところ」を避ける。見出しと結論行は圧縮で欠落しやすいため、単独で
意味が閉じるか確認する。

### 短さを合否基準にしない

短くした結果、承認者が指示対象や根拠を復元するなら CSW に反する。斜め読みは文を削ることではなく、
見出しと強調だけを拾って判断の筋が通るようにすることで実現する。

## risk overlay

基本規則だけでは不足または過剰になる ticket には、次を上書きしてから board を作る。

### 不可逆な変更

**当てるかどうかは «migration があるか» では決めない。**上の分類 1 と同じ基準
（元に戻せない、または戻すのに同規模の作業が要る）で判定する。
**列を足すだけ・index を足すだけで、既存の値を書き換えず、戻す操作が用意できるなら当てない。**

当たる場合、「動く対象」の 4 段階だけで判断させず、次を判断材料に追加する。

- データを何から何へ変換するか。変換できない行をどう扱うか。
- バックアップの対象、取得時点、保存期間、復元確認。
- 復旧手順、復旧不能になる境界、実行責任者。
- 想定停止時間、停止中の利用者影響、開始・中止条件。

⚠ **判断の «片方の選択肢» だけが不可逆になることがある。**その場合は overlay を board 全体へ
当てず、**その選択肢の本文に上の材料を付ける。**選ばなければ起きない危険を、全体の前提にしない。

### 機微な情報

セキュリティ修正、脆弱性、secret、個人情報では、**自己完結、独立 reviewer への提供、外部発行を
無条件に適用しない。**秘匿版を作る。

- board には判断に必要な影響、選択肢、AC、停止条件だけを書く。
- 攻撃手順、secret、未修正箇所の詳細は、アクセス制御された場所への参照だけを置く。
- reviewer には同じ秘匿区分で渡せる場合だけ詳細を渡す。外部 engine へ送れない場合は、
  プロジェクトが許可する内部 reviewer または人間 reviewer に置き換える。
- **外部への発行を既定で禁止する。**公開 URL、外部ホスティング、社外の共有ツールへは出さない。
  保存先は repo の外・その ticket に関わる人だけが読める・いつ消すかが決まっている場所にする。
- **同じ秘匿区分で渡せる reviewer がいない場合は、gate を止めて承認者に報告する。**
  **書き手が自分で 6 問に答えるのは reviewer の代わりにならない**（書いた人が検査することになる）。

⚠ **この overlay が当たらない board にも効く規則が 1 つある。**発行先が repo の外なら、
**取引先・顧客の実資料、private な場での発言の引用、実在の個人名、secret、本番の認証情報は
載せない。**⚠ **テーブル名・関数名・設定キーのような内部の識別子は含めない** — 含めると
判断材料がほとんど書けなくなる。

### 承認者が複数、または repo 外

「誰が」「どの判断または AC を」「どの順で」承認するかを board に書く。全員の承認が必要か、
役割ごとに独立して承認できるかを明記する。外部の返答待ちは **external pending** として保持し、
沈黙や他の承認者の回答で埋めない。

### hotfix

被害継続を避けるため、gate を縮退できる。なぜ、ゴール、AC、既知リスク、rollback または停止条件、
返答文は省かない。

- 独立 reviewer との往復は最大 1 周にしてよい。
- 次をすべて満たす場合だけ、実装前の独立レビューを省いてよい: 遅延が利用者被害を増やす、
  未解決のプロダクト判断がない、不可逆なデータ変更がない、即時 rollback がある、
  プロジェクト規約が省略を許す。
- 省略理由、承認者、rollback 条件を board に残し、安定化後の review を追跡可能な作業として登録する。

### 差分または生成集合が巨大

本文の個別列挙上限を適用する。分類ごとの件数、代表例、例外、最大影響、生成条件を示し、完全な
manifest を別に置く。要約だけで総数を復元できない場合や、例外が推奨を変える場合は要約してはならない。

### 公開された契約が変わらない

**当たるのは «利用者から見える契約»（API の形・画面・データの意味）が変わらない ticket である。**
どちらの型でも「何ができるようになるか」を空欄にしない。

**型 1 — 説明だけが変わる**（docs、コメント、内部の説明文）。**誰が、どの情報を、どの場面で、
どう読み違えにくくなるか**を書く。承認が間違いになる条件は「変更後の説明が実挙動または
決定済み契約と一致しない場合」。

**型 2 — 実行時に出るものが変わる**（ログ、監視できる値、性能、内部の失敗の扱い）。
**誰が、どの場面で、何を新たに観測・診断・実行できるようになるか**を書く。承認が間違いになる
条件は「変更後も、その場面で観測できないままだった場合」。⚠ **型 1 の問い（読み違えにくさ）を
型 2 に当てない** — 型 2 の価値は観測できることそのものである。

## 媒体を選ぶ

主成果物は 1 つにする。補助資料を添えてよいが、同格の本文を 2 つ作らない。

形式は下の表から選び、**発行先は「発行」の節で別に決める。**
⚠ **形式が Markdown でも、外部の共有先へ置けば外部発行である。**形式で発行先を推定しない。

| 媒体 | 選ぶ基準 | 読む追加ファイル |
|---|---|---|
| **Markdown** | `N = 0`〜少数、表と引用が中心、repo 上で差分管理したい。多数モードの段階表にも使える | なし |
| **端末に出す文章** | `N = 0` または 1、画像なし、回答を同じ会話ですぐ返せる | なし |
| **PR コメント** | diff と結び付く `N = 0`〜少数、承認履歴を PR に残す。機微情報は載せない | なし |
| **HTML 文書** | 表、長い AC、画像、付録を 1 ページで突き合わせる。狭い画面と広い画面の両方で読む | [render-html-common.md](render-html-common.md) と [create-doc.md](create-doc.md) |
| **HTML 2 軸デッキ** | `N = 1`〜少数、スマホで主線を横に読み、必要な根拠だけ縦に開く | [render-html-common.md](render-html-common.md) と [create-slides.md](create-slides.md) |

画像が判断の中心で、端末または PR コメントでは読めない場合は HTML または画像を表示できる Markdown を選ぶ。
多数モードでは、1 画面ずつ送るデッキより Markdown または HTML 文書の段階表を優先する。

**複数の行に当てはまる場合は、上から順に決める。**

1. **機微な情報を含むなら**、外部へ発行しない媒体（Markdown / 端末 / ファイル）を選ぶ。
2. **表・長い AC・付録を突き合わせる必要があるなら**、1 ページで見比べられる文書を選ぶ。
3. **承認者が主に狭い画面で読むなら**、デッキを選ぶ。
4. **どれも決め手にならないなら**、いちばん軽い媒体を選ぶ（Markdown → 端末 → PR コメント → HTML）。

### HTML 以外の回答支援

選択 UI を作れない媒体でも、判断番号、推奨の選択文、自由記述欄、未回答表示を含む
**貼り戻し用テンプレート**を末尾に置く。`N = 0` では承認文、修正指示、差し戻しだけを置く。

## 発行

**発行先はプロジェクト設定が定める。**設定がない場合は、ticket の一時領域または安全な作業領域の
ファイルへ書き、会話に絶対 path を示す。公開 URL や共有ツールへ新しく発行すると取り消せない場合は、
試作やサンプルを発行する前に承認を得る。機微な情報には risk overlay を優先する。

## 完成検査

検査は **形・文・判断**の 3 層に分ける。主成果物と、承認者へ渡す補助資料のすべてに実施する。

### 形

選んだ媒体で、幅、overflow、見出し、画像、表、回答操作、狭い画面を確認する。HTML の具体的な
検査方法は renderer 分冊に置く。Markdown、端末、PR コメントでは実際の表示先で折り返し、表、
リンク、画像、貼り戻し文を確認する。

### 文

成果物から次を名指しで探す。

- 主語または目的語がなく、何が何をするか分からない文。
- 初出なのに単独では意味が分からない語や数。
- 比喩で書かれ、指している対象が本文にない語。

### 判断 — 独立 reviewer

**別の engine の独立した reviewer に board だけを渡す。**起動方法、利用できる engine、sandbox、
保存先はプロジェクト設定が定める。共有設定に特定 engine のコマンドや広い権限を既定として書かない。

⚠ **«最小の権限で起動する» を検査の条件にしない。**engine によっては広い権限でしか起動できない。
**権限を絞れないなら、依頼文で参照範囲を指示する。**起動できないことを理由に検査を省かない。
**別 engine がまったく使えない場合**は、そのことを board に書いたうえで書き手が 6 問に答える
（機微な情報を扱う board では、これは代わりにならない。上の risk overlay に従う）。

- reviewer へ repo やインターネットを参照させず、承認者と同じ情報だけを渡す。
- board を別形式へ抽出・整形せず、承認者へ渡す形のまま渡す。
- 試験用の注記は board 内ではなく reviewer への依頼文へ置く。
- reviewer の指摘は仮説として扱い、採否と理由を書き手が決める。
- 機微な情報と hotfix には risk overlay を先に適用する。

reviewer に次の 6 問を、番号を変えずに聞く。

1. **決められるか。**最初に「決められる / 決められない」を答え、詰まった場所を示す。
2. 決められるなら、どれを選ぶか。その理由は何か。
3. **誤った判断をしうる箇所**はあるか。⚠ **board の中だけで分かるもの**に限って答える —
   **board 内の矛盾、過大に読める数値、根拠の書かれていない断定、数の不一致。**
   ⚠ **元の実体（コード・ログ・仕様）と食い違っているかは、この reviewer には分からない**
   （board しか渡していないため）。**それは書き手が「未確定を全部出す」で済ませておく。**
4. 見出しと強調だけを拾っても、判断の筋が通るか。読む手間はどこにあるか。
5. 追加調査なしで決められたか。
6. **書き手が自分で調べたり決めたりできた項目を、承認者へ残していないか。**残っていれば、書き手が何を済ませるべきか。

同じ依頼で、文の検査 3 項目も挙げさせる。標準 gate は、次の状態が **2 周連続**するまで繰り返す。

- 問 1 が「決められる」。
- 問 3 に事実の食い違いがない。
- 問 5 が「はい」。
- 問 6 に片付け残しがない。
- 文の検査に指摘がない。

問 1 だけ、または問 3 だけで抜けない。hotfix の往復回数は risk overlay がこの標準を上書きする。

**構成を組み直したら、それまでの指摘は無効になる。**節の順序、判断の数、主線と補足の切り分け、
媒体のいずれかを変えると、同じ内容でも**情報の位置と欠落が変わる**。前の構成で「決められる」を
得ていても、**新しい構成で 1 周目から数え直す。**部分的に直しただけなら、直した箇所とその影響
範囲だけを再検査してよい。

### 修正後の一貫性

数値、識別子、AC、判断範囲を直す前に、成果物内の出現箇所を安定した識別子で全部出す。
同じ主張は別の言い回しで複製されるため、文章全体ではなく数値、AC 番号、節 ID などで検索する。

- AC を直したら、その AC 番号で全表示箇所を出す。
- 判断範囲を直したら、表題、決定サマリー、推奨、承認を求める見出し、返答文を確認する。
- 書き換える前に現在の節を読み、以前に退けた前提を戻さない。
- **規則を足す前に、同じ主題の節が他にないかを探す。**見つけたら、足すのではなく**統合する**。
  正反対の規則が両方残ると、読み手はどちらに従うか選べず、成果物が書き手ごとに別物になる。
- 構造を一括置換したら、前後の見出し、面、回答項目の数を比較する。

HTML でのクラス確認と AC 番号の具体的な検索は [render-html-common.md](render-html-common.md) に置く。
