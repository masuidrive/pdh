# Decision Board — 判断材料を 1 枚にまとめる

会話に埋めた報告は流れて読み返せない。**判断が溜まったら 1 枚のページにして、ユーザがそこだけ見て決められる状態にする。**

このドキュメントが定めるのは「何を書くか / 何を書かないか」と「回答をどう受け取るか」である。

**見た目とフォーム機構は `board-kit.tpl`（このディレクトリに同梱）が持つ。**配色・目次・回答フォーム・コピー機構・スマホのドロワーは全部そこに入っているので、**CSS と JS を書き直さないこと。**中身の HTML だけを書いて差し込む（下記「テンプレートの使い方」）。テンプレートを使う限り `artifact-design` skill の load は**不要**。⚠ `Artifact` tool の説明は「ページを書く前に `artifact-design` を必ず load」と要求するが、**board についてはこの skill が優先する**（見た目は既に決まっており、design を考え直す余地が無いため）。**テンプレートから外れた見た目を作る必要が出たときだけ** `artifact-design` を load する。

## 出し方 — 既定はファイル。公開は指定されたときだけ

**既定は 1 枚の HTML をファイルに書き、会話にその path と要約を置く。**
置き場所は ticket の tmp ディレクトリ（`ticket.sh start`/`restore` 出力の `tmp_dir:`。
per-ticket layout なら `tickets/<name>/tmp/board.html`）。ticket に紐づかないものは
scratchpad でよい。**この経路は engine を選ばない。**

**⚠ path は必ずフルパスで書く。**ターミナル側にフルパスをクリックして開く機能があるため、
相対パスや「scratchpad の board.html」のような書き方では**開けない**。

**page 公開サービス（Claude の Artifact など）を使うのは、`CLAUDE.md` / `AGENTS.md`
でそう指定されている場合だけ。**指定が無いなら勝手に外へ出さない — board には
未公開の ticket 情報・本番の実測値・社内の人の発言が載る。

発行先が指定されている場合も、board 側の作りは変えない。テンプレートは
**CSS / JS / 画像を全部 inline した 1 枚の HTML** なので、ファイルでも公開でも同じものが動く。
ただし発行先は次の 2 つを満たしていること。満たさないなら**ファイル経路に落とす。**

- **JS が動く** — 選択 → 集計 → コピーが JS。静的な文書では board にならない
- **同じ場所を更新できる** — 訂正版を出しても、渡した URL / path が生き続ける

**「gate の判断材料を 1 枚にまとめて先に出す」という要求は engine 中立である。**
`PDH-AGENTS.md`「Human Gate Materials」が定めるのは材料とその読みやすさであって、
発行手段ではない。**発行機構が無いことを、gate 材料を省く理由にしてはならない。**

## 使うとき / 使わないとき

| 状況 | 手段 |
|---|---|
| 判断が 2 件以上溜まっている | **decision board** |
| 1 件でも背景の説明が要る（仕組み・履歴・トレードオフ） | **decision board** |
| 画面を見てから決める（UI / 比較） | **decision board**（スクショ込み） |
| 判断 1 件・選択肢が単純・背景を共有済み | `AskUserQuestion` のほうが速い。board を作らない |
| 事実の報告だけで判断が要らない | 会話に書く。board を作らない |

**board を作ったら、会話には要約と path（または URL）だけ置く。**同じ内容を両方に書かない。

**⚠ path / URL は会話の «末尾» に置く。**本文の途中に混ぜると探すことになる。**未回答の board が複数あるなら全部を末尾に並べ、決めてほしい順に番号を振る。****回答が来たら «その board を末尾のリストから外す»** — 惰性で貼り続けると、決着済みの判断を «未決» として提示し続けることになる（実際にやった）。board を作ったこと自体より、**開くための場所が探さずに見つかること**のほうが重要である。

`AskUserQuestion` との併用は**しない**。テンプレートの回答フォームが選択の入口を兼ねるので、二重に聞くことになる。

## テンプレートの使い方

`board-kit.tpl` に 4 つの置換マーカーがある。**全部 replace すること**（省くとページに文字列が出る）。

| マーカー | 入れるもの |
|---|---|
| `__TITLE__` | `<title>…</title>` タグごと |
| `__BOARDTITLE__` | 回答テキストの見出しに入る board 名（タグ無し） |
| `__CONTENT__` | `<main>` の中身。`<header>` と `<section>` を並べる |
| `__MERMAID__` | 図の描画機構。**図が無いなら空文字**（下記「図」の節） |

やることは**この 4 つを置換して 1 ファイルに書き出す**だけ。同梱の `build-board.sh` を使う。

```bash
sh <skill_dir>/build-board.sh <tpl> <content.html> "<title>" [mermaid.html] > board.html
```

**必要なのは `sh` / `awk` / `grep` / `head` / `tail` / `cat` / `mktemp` だけ**で、言語ランタイムは要らない。
本文（`__CONTENT__`）と図の描画機構（`__MERMAID__`）は**ファイルとして渡す**。

**⚠ `sed 's///'` で置換しない。**`__MERMAID__` には 1.5 MB の minified JS が入り、
最長行は 30 万文字ある。`&`（マッチ全体）・`\`・区切り文字を sed が**解釈して壊す**。
`build-board.sh` は「短い置換は awk / 大きい置換は head+cat+tail の «挟み込み»」に
分けてあり、**大きいファイルはどのツールにも解釈されずに素通りする。**
（自分で書き直す場合も、この 2 分割と «短い置換を先にやる» 順序は保つこと。
逆にすると 30 万文字の 1 行が awk を通り、実装によっては行長制限に当たる。）

**⚠ 内容を «直して作り直す» 手順は必ず残す。**配色変更・不具合修正で
**同じ board を何度も作り直す**ことになる（実際 1 日に 6 回あった）。

**`<meta charset="utf-8">` は `build-board.sh` が自動で入れる。**テンプレートは `<head>` を持たないので、
自分で組む場合は忘れないこと（忘れると日本語が化ける）。

### section の書き分け

| 種類 | 書き方 |
|---|---|
| 読む場所 | `<section>` + `<h2><span class="kicker read">資料</span>見出し</h2>` |
| **判断する場所** | `<section class="decide" data-q="N" data-label="回答に出る見出し" data-tk="どの ticket か">` + `.dhead`（下記） |
| 提出欄 | 下記の HTML を**そのまま**（`#out` の有無が下端バーと警告の生成条件になっている） |

**`data-q` は 1 から連番、`data-label` は回答テキストに出る名前。**入力の `name` は `q1` `q2` … と対応させる。目次・進捗・集計はこの属性から自動で組まれるので、**目次を手書きしないこと。**

**⚠ 提出欄は自動生成されない。書き手が次をそのまま置く。**`#out` `#copy` `#reset` `#flash` は
JS が探しに行く id で、**`#out` が無いと下端の回答バーも「手編集で自動更新停止」警告も出ない。**

```html
<section>
  <h2><span class="kicker">提出</span>回答をまとめてコピー</h2>
  <div class="card">
    <p style="font-size:14.5px;color:var(--ink-2);">選んだ内容が下に溜まります。<strong>コピーして会話に貼り付けてください。</strong>1 件ずつ返しても構いません。</p>
    <textarea id="out" spellcheck="false" aria-label="回答のまとめ"></textarea>
    <div class="bar">
      <button type="button" id="copy">クリップボードにコピー</button>
      <button type="button" class="ghost" id="reset">選択をクリア</button>
      <span class="flash" id="flash" role="status" aria-live="polite"></span>
    </div>
  </div>
</section>
```

**`<header>` も書き手が用意する。**`<h2>` に日付、`<h1>` に board 名、`<p class="lede">` に
1〜2 文の趣旨。**JS は `main > header` の有無で先頭の一覧の挿入位置を決める**ので、
header を置かないと一覧が本文の先頭に割り込む。

**⚠ 目次に出るのは、`<h2>` を持つ資料セクションと、`data-q` を持つ判断セクションだけ。**
`<h2>` の無い資料セクションは**目次から消える**（判断セクションは `data-label` を使うので
`<h2>` は要らない）。

**`data-tk` には ticket の «症状ベースの呼び名» を入れる**（`.dtk` に出すものと同じ文字列）。同じ値を持つ判断がまとめられ、**「この ticket のぶんだけコピー」ボタンが自動で生える。**2 種類以上あるときだけ出る。

### テンプレートが勝手に作るもの — 手書きしない

以下は `board-kit.tpl` の JS が **本文から生成する**。HTML には書かない。書くと二重になる。

| 出るもの | 何をするか | 依存 |
|---|---|---|
| **先頭の一覧** | 判断の `.sym` と `.askwhy` の種別を 1 行ずつ並べる。答えると ✓ になる | `section[data-q]` |
| **この判断だけコピー** | `.dhead` の右端。**決まったものから順に返せる** | `.dhead` |
| **ticket ごとのコピー** | 提出欄の下。`data-tk` が 2 種類以上あるときだけ | `data-tk` |
| **下端の回答バー** | `3 / 5 回答済み` ＋ コピー ＋ 出力欄へジャンプ。**常に見える** | `#out` |
| **自動保存** | 選択とメモを URL ごとに保存し、開き直すと復元して知らせる | — |
| **目次の現在地** | いま読んでいる節を目次で反転する | — |

**部分コピーがあるので、判断が揃うまで board を出し惜しみしない。**1 件でも決まれば worker を動かせる。
実際、5 件を 1 塊にしたせいで**片方の worker を 5 時間止めた**ことがある（2026-08-04）。

### 判断セクションの構造 — これは «エンジニアが PM に上げる escalation» である

**判断ブロックは「症状の説明」ではなく「決めてもらうための申し送り」である。**順序を固定する。

```
判断 N · <どの ticket の話か>       ← .dhead。判断だけ読んでも所属が分かる
① 決めてほしいこと（1 行）          ← .sym
② なぜ «あなたに» 聞くのか          ← .askwhy。下記。最重要
③ 経緯                             ← .story
     元の問題       何を直そうとしていたのか
     やろうとしたこと  そのために何をしたか
     そこで起きたこと  何が問題になったか
     期間 / 限界      いつまでの話か・測れていないこと
④ 詳しく（折りたたみ）              ← details.more
⑤ 選択肢（軸を固定）                ← 下記
⑥ 決めないとどうなるか              ← .blocking
⑦ 追跡情報                         ← .meta。AC 番号・ticket 名・窓
```

**⚠ ③ の «元の問題» を省かない。**症状だけ書くと**物語の途中から始まる**。「8/1 の実行を開くと『記録なし』と出ます」は、**今日まだ起きていない・これから作るものが作り出す問題**なのに、そう読めない。**何を直そうとしていて、その途中で何が起きたのか**まで書いて初めて、選択肢が恣意的でなくなる。

### ② なぜ «あなたに» 聞くのか — 2 種類ある

```html
<div class="askwhy need">    <!-- または class="askwhy check" -->
  <span class="kind">なぜ聞くのか — 決めてほしい</span>
  <p>利用者の画面に出る文言が変わるからです。技術的にはどの案でも動きます。</p>
</div>
```

**`need`（決めてほしい）** — 自分の権限では決められないもの。だいたいこの 5 つ:

| | |
|---|---|
| **お金がかかる** | 本番で 1 回実行してよいか |
| **利用者から見た挙動が変わる** | 422 → 200、画面の文言 |
| **優先順位のトレードオフ** | 今どこまで作るか |
| **取り返しがつかない** | 元に戻せない設定変更 |
| **リスクの許容度** | 未実測のまま出すか |

**⚠ どれにも当てはまらないなら、聞くべきではない。**この欄を書けないものは自分で決める。**「なぜ聞くのか」は、聞きすぎていないかの検算になる。**

**`check`（念のため確認）** — **推奨どおりで良いはずだが、引っかかっていること。**これを正式な種別として持つことに意味がある。無いと、**不安を抱えたまま黙る**か、**無理に「あなたの判断です」と装う**かの二択になる。

> 推奨（A）のとおりで良いはずですが、確認させてください。技術判断なので本来は私が決めるところです。ただ**「裏付けの無い理由で設計を縛る」ことになる**のが引っかかっています。

### ⑤ 選択肢の «軸» を固定する — 利用者 / コスト / 取り返し

案ごとに違う観点で Pros/Cons を並べると**横に比較できない**。3 軸に固定する。

```html
<div class="axes">
  <div class="ax"><span class="ak">利用者から見て</span><span class="av">…</span></div>
  <div class="ax"><span class="ak">コスト</span><span class="av">…</span></div>
  <div class="ax"><span class="ak">取り返し</span><span class="av">…</span></div>
</div>
```

**エンジニアは放っておくと «仕組みの説明» を厚く、«コストと可逆性» を薄く書く。**軸を固定すれば強制的に埋まる。

- **利用者から見て** — 誰の画面で何が変わるか。「変わりません」も立派な回答
- **コスト** — 時間 / お金 / 複雑さ。**「後から変えるといくらか」もここ**
- **取り返し** — やり直せるか。⚠ が付くのはたいていここ

**推奨案にも 3 軸すべて埋める。**空欄があるのは検討が足りていないだけ。

- **推奨は別枠にせず、案そのものに印を付ける**（`class="opt rec"` ＋ タイトル末尾に
  `<span class="chip c-acc">推奨</span>`）。別枠にすると説明と理由が二重になる
- **推奨しない案も同じ精度で書く。**薄く書けば誘導になる
- **規約と自分の判断が食い違うときは明示する。**「規約はこちらだが、実測に基づいて
  別を推す」と書く。黙って上書きしない
- **⚠ 出せない選択肢を作らない。**実際、3 案を出したところ**ユーザの結論はどれでも
  なかった**ことがある（それが最も良い設計だった）。だから「その他」を必ず置く

### ⑥ 決めないとどうなるか

**緊急度が伝わらないと、後回しにしてよいか判断できない。**「実装に入れません。担当が待機中です」「実装は進められますが、後から変えると手戻りが出ます」のように、**止まっているのか・待てるのか**を書く。

### 冒頭に「扱っている ticket」を置く

**判断だけが並んでいると、board 全体が何の作業についてのものか分からない。**冒頭に ticket の一覧を置き、**どの判断がどの ticket に属するか**まで書く。

```html
<div class="tks">
  <div class="tk">
    <div class="tk-head">
      <span class="tk-who">担当</span>          <!-- 並行作業なら worker / window 名 -->
      <span class="tk-name">ログを読み返す仕組み</span>   <!-- 症状ベースの短い名前 -->
      <span class="chip c-warn">実装前</span>            <!-- 状態 -->
    </div>
    <div class="tk-sym"><strong>症状を 1〜2 文。</strong>誰がいつ報告したかも</div>
    <div class="tk-q">この board の <b>判断 1・2・3</b>　·　触る範囲: サーバ側とインフラのみ</div>
    <div class="tk-id">&lt;ticket id&gt;</div>
  </div>
</div>
```

**`触る範囲` を書くと、複数 ticket が独立かどうかが読み手にも判定できる。**「片方だけ答えても構いません」が根拠つきになる。

### 詳細は折りたたむ

**症状ベースにすると、裏取りに必要な情報が落ちる。**消さずに `<details class="more">` へ入れる。**既定は閉じる。**

```html
<details class="more">
  <summary>詳しく — 技術的な内訳と実測値</summary>
  <div class="inner">
    <p><strong>実測した可視範囲</strong>: …<code>file:line</code>…</p>
  </div>
</details>
```

置き場所は **③ 経緯（`.story`）と ⑤ 選択肢の間**（構造図の ④）。「経緯」を読んで納得できなかった人だけが開く位置になる。

入れるもの: **AC の元の文言 / 実測値の生データ / `file:line` / 公式ドキュメントの引用 / 前例の ticket 番号**。つまり**症状の説明では削ったが、疑われたら出す必要があるもの**。

### 「その他」を全設問に必ず置く

`AskUserQuestion` には常に「その他」があるのに、board に無いと**選択肢のどれとも違う結論を持つ人が「一番近いものを選んでメモで否定する」しかなくなる**。出力には「選択: A」と残り、読む側は A が選ばれたと解釈する。

```html
<label class="opt other">
  <span class="opt-head"><input type="radio" name="qN" value="__OTHER__">
    <span class="opt-title">その他 — 下のメモに書く</span></span>
  <span class="opt-body"><dl><dd style="color:var(--ink-3);">メモの内容がそのまま回答になります。</dd></dl></span>
</label>
```

`__OTHER__` はテンプレートの JS が特別扱いし、メモ欄の内容を回答本文にする。**選ぶとメモ欄へ自動でフォーカスする。**

各設問の末尾にメモ欄を置く（`id="nN" data-note="N"`）。**複数選択にしたい設問は `input` を `checkbox` にするだけ**でよい（集計側が自動で `- [x]` 形式に切り替わる）。

### 出せない選択肢を作らない

実際にあった例: 判断 1 で 3 案を出したところ、**ユーザの結論はどれでもなかった**（「同時並行 20 で 250 秒で giveup して途中返却」）。それが最も良い設計だった。**選択肢は自分の想像力の限界であって、正解の集合ではない。**

## 必須ルール

いずれも実際の事故から来ている。省くと board の価値が消える。

### 事実の確度を書き分ける

- **確認済み** — 実際にコードを読んだ / コマンドを実行した
- **推論** — 筋は通るが実測していない。**必ず「未実測」と明記する**
- **測定不能** — 測る手段が無い。「無い」ではなく「**測れない**」と書く

推論を断定として書くと、ユーザは検証済みの事実として設計判断に使う。

### レビュー URL は path のみ

- dev-server は **プロジェクトの規約どおりに起動したもの**を提示する（`PDH-AGENTS.md`「Dev Server And Seed」）
- board には **path だけ**書く（`/ui/&lt;project&gt;/…`）。ホスト側のアドレスはユーザの環境のもの
- `localhost:` を含む URL を提示しない。**ユーザは devcontainer のホスト側から開くので到達できない**

### 図で説明できるものは図にする

**分岐・順序・依存関係**は文章より図のほうが速く正確に伝わる。

図にする価値が高いもの:

- **条件分岐**（「PostgreSQL は alembic を通るが SQLite は `create_all` だけ」）
- **処理の順序**（「検査 A が replay より先にあるので到達できない」）
- **依存関係**（どの作業がどれを待っているか）

依存関係の図は特に効く。**矢印を引こうとすると、引けない矢印が目に見える。**
実際、依存図を描いていて「今すぐ流せる」と書いた推奨案が実は別 window の
merge 待ちだと気づいた例がある。

### 図は `<pre class="mermaid">` で書き、描画機構を差し込む

**mermaid のソースをそのまま置いて終わりにしない。**native に描くのは Claude の
Artifact «だけ» で、**ファイルをブラウザで開く経路ではソースがそのまま並ぶ。**
発行先によって出るものが変わるのは、board としては壊れている。

**図は `<figure>` で包み、`<figcaption>` に «この図の何を見てほしいか» を書く。**

```html
<figure>
  <pre class="mermaid">flowchart LR
  A1[…] --> A2[…]
  B1[…] --> B2[…]</pre>
  <figcaption><strong>上が誤った理解、下が実際。</strong>…</figcaption>
</figure>
```

**図を使う board では、テンプレートの `__MERMAID__` に描画機構を差し込む。**
同梱の `mermaid-render.min.js`（beautiful-mermaid を browser 用に bundle したもの）を
そのまま埋めて、下の loop を足すだけでよい。**生成側に Node は要らない**
（ファイルを読んで文字列として差し込むだけ）。

```bash
# 図がある board だけ、bundle と描画 loop を 1 ファイルにまとめて渡す
{ printf '<script>'; cat <skill_dir>/mermaid-render.min.js; printf '</script>'; cat mm-loop.html; } > mermaid.html
sh <skill_dir>/build-board.sh <tpl> content.html "<title>" mermaid.html > board.html
```

```html
<!-- MM_LOOP: 描画して置き換える。色は board のトークンへ差し替える -->
<script>
(async function(){
  for (const el of document.querySelectorAll('pre.mermaid')) {
    try {
      let svg = await window.__renderMermaidSVG(el.textContent);
      svg = svg.replace(/@import\s+url\([^)]*\);?/g, '')          // ⚠ CSP で落ちる外部フォント
               .replace(/font-family:\s*'Inter'[^;}]*/g, "font-family: var(--sans)")
               .replace(/--bg:\s*#[0-9A-Fa-f]{3,8}/, '--bg:var(--card)')
               .replace(/--fg:\s*#[0-9A-Fa-f]{3,8}/, '--fg:var(--ink)');
      const d = document.createElement('div');
      d.className = 'mmwrap';        // ⚠ 図が親より広いとき «図だけ» 横スクロールさせる
      d.innerHTML = svg;
      el.replaceWith(d);
    } catch (e) { el.style.display = 'block'; }   // 失敗したらソースを見せる（黙って消さない）
  }
})();
</script>
```

**色は board のトークンに追従する。**beautiful-mermaid は全ての色を `--bg` / `--fg` から
`color-mix` で導出するので、その 2 つを差し替えるだけで light / dark 両方に付いてくる。

**⚠ bundle は 1.5 MB ある**（gzip で約 471 KB、描画は実測 57 ms）。
**図が 1 つも無い board には差し込まない。**上の `if` がその判定である。

**subgraph は使わない。**`direction` が無視される・順序が入れ替わる・タイトルがノードに
被る、のいずれかが起きる。前後比較のような並列は、**2 本の独立した鎖を `flowchart LR`
で並べる**と素直に段組みになる。

```
flowchart LR
  A1[今: …] --> A2[…] --> A3[…]
  B1[修正後: …] --> B2[…] --> B3[…]
```

**図は必ずブラウザで見る。**SVG になった時点で構文エラーでは落ちないが、
**日本語ラベルの折り返しや、線がノードに重なる崩れは目でしか分からない。**

### 発行前に、選択と集計が動くことを確認する

**選択 → 集計が出るかを 1 回だけ確かめる。**壊れているとユーザは「選んだのに回答が
出ない」状態で詰まる。壊れる原因はほぼ 1 つ — **`data-q` と入力の `name="qN"` の
対応漏れ**である。

**`file://` では動かない。**`python3 -m http.server` で出す。テンプレートは `<head>` を
持たないので、確認用の HTML には **`<meta charset="utf-8">` を自分で付ける**
（付け忘れると日本語が化け、テンプレートのせいだと誤診する）。

```bash
agent-browser eval "
(function(){ document.querySelectorAll('section[data-q]')[0].querySelector('input').click();
  return {decide:document.querySelectorAll('#toclist a.is-decide').length,
          out:document.getElementById('out').value}; })()
"
```

**`decide` が判断の数と一致し、`out` に全設問が出る**ことを確認する。
「その他」を使う設問があるなら、それも 1 度選んでメモを書いてみる。

### スクリーンショットは base64 で inline する

判断に画面が要るなら撮る。**UI の変更は文章より画面のほうが確か。**
「前はこうで今はこう」を見せられるなら前後の両方を撮る。

- artifact の CSP は外部ホストへの参照を全てブロックする
- `/tmp` のファイルはセッション再起動で消える。**パスを書いても後から開けない**
- **PNG のままだと重い。**Pillow で幅 1000px 前後・JPEG 品質 72 程度に落とす（4 枚で 300KB 弱に収まる）
- **⚠ `agent-browser screenshot` は相対パスだと repo ルートに保存される。**必ず絶対パスで撮る。
  実際に踏んだ: repo に残った PNG 2 枚が別 window の `ticket.sh close` をブロックした
- 同じ画面を light / dark 両方撮ってあるなら、`.shot-light` / `.shot-dark` を付ければ閲覧者のテーマに追従する（任意。**両方撮ることを要求はしない**）

- **`figcaption` に「この画像の何を見てほしいか」を書く。**画像だけ置いても、どこが論点か伝わらない

### 未対応の finding は全件・件数つきで書く

`PDH-AGENTS.md`「Human Gate Materials」の要件。**採用しなかったもの（起票 / 記録のみ / 棄却）を、件数と一行理由つきで全部載せる。**ゼロなら「ゼロ」と明記する。

何を直さなかったかは、直したことと同じ重さの判断材料であり、**board に載せなければ他のどこでも検証できない。**

### board の単位は「窓」ではなく「独立して決められるかたまり」

**複数の作業をまとめて 1 枚にすると、片方の前提が崩れたときに «両方» 止まる。**

2026-08-04 の実例: 2 つの window の AC 承認を 1 枚にまとめたところ、片方（ログの読み取り経路）が方式変更で AC ごと作り直しになった。**もう片方（会話ログの入口・frontend のみ・完全に独立）は決められる状態だったのに、同じ board に載っていたために 1 時間 50 分止まった。**

- **board を組む前に「この判断とあの判断は、片方だけ先に決められるか」を確認する。**依存があるなら、**どちらがどちらを待つのかを board に書く**
- 依存が後から判明することはある。**そのときは分割して再発行する**（テンプレート化してあれば数分で済む）
- **分割したら、残ったほうの board にも「何を外したか・なぜか・どこで決めるか」を書く。**黙って消すと、前に見た判断が消えた理由が分からない

### 決定の «文言» ではなく «意図» が守られているかを見る

worker が「Director の決定と技術的には矛盾しないが、意図次第では該当する」と報告してきたら、**それは worker が正しく止まっている。**勝手に解釈させず、ユーザに戻す。

2026-08-04 の実例が 2 つある。

- 「BigQuery への sink はやらない（データを複製しない）」と決めた後、**linked BigQuery dataset は複製しないので文言上は矛盾しない**。しかし「BigQuery を使うこと自体を避けたい」意図なら該当する。worker は自分で決めずに戻してきた
- 「有効化前のログが SQL で引けないのは許容する」と決めた後、実装段階で**それが「見えない」で済まず「無い」と «偽る» ところまで行く**ことが判明した。**許容したのは «見えないこと» であって «見えないものを無いと偽ること» ではない**

**board で選択肢を書くとき、その決定が «どこまで» を許容するのかを言葉にしておく。**「許容する」だけでは、実装がどこまで行っていいか決まらない。

### 前提が変わったら明記する

board は再発行できる。**前に提示した枠組みが古くなったら、変わったこと自体を書く。**

> 例: 「数時間前は『2 窓が同じ関数を並行で書き換える』ことが障害でしたが、window 2 が close 承認待ちになった今、順序を付ければ衝突は消えます。」

黙って新しい枠組みに差し替えると、ユーザは前回の判断が今も有効だと思ったまま読む。

### チケットは名前でなく症状で説明する

ユーザはプロダクト全体を知っていても、**チケット名までは覚えていない。**

- ✅ 「LLM の答えが途中で切れたのに 200 で成功として返っていたのを失敗にする」
- ❌ 「`260729-030156-truncated-output-fail-loud-all-modes` の close」（ticket 名は補助情報として小さく添える）

ID は補助情報として小さく添える。**出どころ（誰のどの報告か、いつの Slack か）も書く** — ユーザが文脈を思い出す最短経路になる。

## 判断例（実物）

2026-07-30 の board から。**Critical だが本 ticket 由来ではない finding をどう扱うか**という、
判断がユーザにしか下せない典型例。

---

**判断 3 — F13（Critical・既存の SQLite DB でアプリが起動できなくなる）**

*背景*: SQLite の起動経路は alembic を通らず `create_all()` だけ（`main.py:87-94`）。`create_all` は既存テーブルに列を追加しないので、既存 DB は列が増えないまま最初の ORM query が `no such column` で落ちる。2026-03-13 から同じ構造で、migration 086 も同じ露出を持っていた。**この ticket は 3 列追加するので、merge すれば実際に引き金を引く。**

**A. 本 ticket で直す** ［推奨］
- *起きること*: window 3 が実装 → フルスイート取り直し → codex gate → close。close は数時間後
- *Pros*: merge 時点で既存 SQLite 環境が壊れない / プロジェクトの「SQLite は本番と同格」方針に整合 / F15 とまとめればフルスイート取り直しが 1 回で済む
- *Cons*: close がさらに遅れる / **`main.py` の lifespan（起動経路）を触る** / `alembic_version` が無い DB への upgrade 挙動が**未実測**で、stamp の段取りを設計する必要がある

**B. 別 ticket で起票**
- *起きること*: window 3 は今日中に close できる。SQLite の問題は後日
- *Pros*: 独立した Why（SQLite 開発環境の起動）は立つ / 起動経路を今触らずに済む
- *Cons*: **merge した瞬間、既存 SQLite DB を持つ開発者の環境が壊れる**（作り直すまで）

**C. 記録のみ**
- *起きること*: 何も直さない。`technical-reference.md` に landmine として残す
- *Pros*: 086 のときも同じ露出があり、誰も困った記録が無い（＝実害が小さい可能性）
- *Cons*: **プロジェクトの SQLite 方針と正面から衝突する** / 「記録が無い」は「実害が無い」の根拠にならない。黙って DB を作り直した人がいた可能性のほうが高い

---

この例で守られていること:

- **C の Pros に、推奨に不利な事実（086 で問題化しなかった）をきちんと書いている。**そのうえで Cons で反論している。書かずに済ませると誘導になる
- **未実測（stamp の段取り）を推奨案の Cons に書いている。**推奨したい案ほど弱点を隠したくなる
- **「壊れる」の中身が具体的**（`no such column` / DB を作り直すまで）。抽象的な「リスクがある」では判断できない

## 発行するときの作法（`CLAUDE.md` / `AGENTS.md` で発行先が指定されている場合）

- **同じファイルパスで再発行すると同じ URL を保つ。**更新は必ず同じパスで行う
- `favicon` は**再発行をまたいで変えない**。ユーザはタブのアイコンで探す
- `label` に「何を変えたか」を短く入れる（版の一覧に出る）
- `description` は gallery カードの副題。そのページで何が決められるかを 1 文で
- 詳細が長くなる項目は**別ページに分け、board からリンクする**。board は一覧性を優先する

## 回答を受け取ったあと

ユーザはテンプレートの集計欄をコピーして会話に貼る。形はこうなる。

```
# 判断ボードの回答 — <board 名>

## <data-label>
選択: <選んだ選択肢>
メモ: <メモがあれば>

## <data-label>
- [x] <複数選択の項目>
- [x] その他: <メモの内容>

---
回答済み 3 / 3
```

- **「選択: その他 — …」はメモが回答本体。**そのまま指示として受け取る
- **「（未選択）」を勝手に埋めない。**答えられていない判断が残っているということ
- **決まった内容は ticket / note / commit message に落とす。**board は決めるための机であって記録ではない

## やってはいけないこと

| アンチパターン | なぜ |
|---|---|
| 判断の材料ではなく作業の経過を書く | board は決めるための道具。何をしたかは note と会話に書く |
| 選択肢を列挙して推奨を出さない | 「あなたが決めてください」は判断コストをユーザに丸投げしているだけ |
| 推奨案の Cons を空にする | 検討が足りていないだけ。トレードオフの無い選択肢はほぼ存在しない |
| 「その他」を置かない | 選択肢は自分の想像力の限界であって正解の集合ではない。逃げ場が無いと、近い案が選ばれて誤読される |
| 見出しを実装の言葉で書く | `AC2 に理由を持たせるか` は読み手の言葉ではない。**症状で書く** |
| 「なぜ聞くのか」を書かない | 書けないなら**聞くべきでない**。この欄は聞きすぎの検算 |
| 経緯の「元の問題」を省く | 物語の途中から始まり、選択肢が恣意的に見える |
| 案ごとに違う観点で Pros/Cons を書く | 横に比較できない。**利用者 / コスト / 取り返し** に固定する |
| 不安なのに «あなたの判断です» と装う | `check`（念のため確認）という種別がある。**正直に書く** |
| 追跡情報を先頭に置く | ticket 名や AC 番号が最初に来ると、何の話か分からないまま読み始めることになる。**下に小さく** |
| 裏取りの材料を «消す» | 症状ベースにすると詳細が落ちる。**消さずに `<details>` へ**。読みやすさと検証可能性は両立できる |
| 未確認のことを断定する | 上記「事実の確度」参照 |
| board を作って会話にも全文を書く | 二重管理になり、片方が古くなる |
| **URL を会話の途中に埋める** | 探すことになる。**末尾に置く** |
| CSS と JS をテンプレートから書き直す | **色は選ばない。**配色・目次・フォーム・コピー・ドロワーは検証済みで固定である |
| 1 件しかない単純な判断で board を作る | `AskUserQuestion` のほうが速い（ただしプロジェクトが **ticket / close の判断は 1 件でも board 必須**と定める場合はそれに従う） |

## 判断が済んだあと

board は**判断の記録としては使わない。**決定した内容は ticket / note / commit message に落とす。board はあくまで「決めるための机」であり、決まった後の正は repo 側にある。

ただし board 自体は消さない。**次に同じ論点が来たとき、前回どの材料で決めたかを引ける。**
