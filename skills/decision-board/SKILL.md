# Decision Board — 判断材料を 1 枚にまとめる

会話に埋めた報告は流れて読み返せない。**判断が溜まったら 1 枚のページにして、ユーザがそこだけ見て決められる状態にする。**

このドキュメントが定めるのは「何を書くか / 何を書かないか」と「回答をどう受け取るか」である。

**見た目とフォーム機構は同梱のコンポーネント群（`board-kit.tpl` + `board-runtime.js`）が持つ。**
配色・目次・トリアージ・回答フォーム・コピー・自動保存・右ペイン・折りたたみ・スマホ対応は
全部そこに入っているので、**CSS と JS を書き直さないこと。**書き手は `db-*` タグを並べるだけ
（下記「ボードの組み立て方」）。テンプレートを使う限り `artifact-design` skill の load は**不要**。
⚠ `Artifact` tool の説明は「ページを書く前に `artifact-design` を必ず load」と要求するが、
**board についてはこの skill が優先する**（見た目は既に決まっており、design を考え直す余地が無いため）。

## 出し方 — 既定はファイル。公開は指定されたときだけ

**既定は 1 枚の HTML をファイルに書き、会話にその path と要約を置く。**
置き場所は ticket の tmp ディレクトリ（`ticket.sh start`/`restore` 出力の `tmp_dir:`。
per-ticket layout なら `tickets/<name>/tmp/board.html`）。ticket に紐づかないものは
scratchpad でよい。**この経路は engine を選ばない。**

**⚠ path は必ずフルパスで書く。**ターミナル側にフルパスをクリックして開く機能があるため、
相対パスや「scratchpad の board.html」のような書き方では**開けない**。

**⚠ ただし «クリックして開いた先» が inline script を止めることがある。**ターミナルや
エディタのファイルビューアは、開いたファイルを `Content-Security-Policy: default-src 'none'`
＋ sandbox 属性つきの iframe で表示することがある。この場合 board の JS は 1 行も走らない。
テンプレートはこれを 2 段で受ける。**①ページ先頭に案内（`#nojs`）が出る**（JS が走れば消える）。
**②本文はコンポーネントの属性も含めて CSS だけで読める**ようにしてある（見出し・選択肢の
ラベル・軸名が JS 無しでも描かれる）。集計とコピーは動かないが、案内には「番号と記号で会話に
直接答えてよい」と書いてあるので、**止められても判断は返せる。**書き手が用意するものは無い。

path を渡すときは、**ビューアで開けない場合の代替をひとこと添える**とよい
（ブラウザで直接開く / そのディレクトリで `python3 -m http.server`）。

**page 公開サービス（Claude の Artifact など）を使うのは、`CLAUDE.md` / `AGENTS.md`
でそう指定されている場合だけ。**指定が無いなら勝手に外へ出さない — board には
未公開の ticket 情報・本番の実測値・社内の人の発言が載る。

発行先が指定されている場合も、board 側の作りは変えない。テンプレートは
**CSS / JS / 画像を全部 inline した 1 枚の HTML** なので、ファイルでも公開でも同じものが動く。
ただし発行先は「JS が動く」「同じ場所を更新できる」の 2 つを満たしていること。
満たさないならファイル経路に落とす。

**「gate の判断材料を 1 枚にまとめて先に出す」という要求は engine 中立である。**
`PDH-AGENTS.md`「Human Gate Materials」が定めるのは材料とその読みやすさであって、
発行手段ではない。**発行機構が無いことを、gate 材料を省く理由にしてはならない。**

## 使うとき / 使わないとき

| 状況 | 手段 |
|---|---|
| 判断が 2 件以上溜まっている | **decision board** |
| 1 件でも背景の説明が要る（仕組み・履歴・トレードオフ） | **decision board** |
| 画面を見てから決める（UI / 比較） | **decision board**（スクショ込み） |
| 判断 1 件・選択肢が単純・背景を共有済み | `AskUserQuestion` のほうが速い。board を作らない |
| 事実の報告だけで判断が要らない | 会話に書く。board を作らない |

**board を作ったら、会話には要約と path（または URL）だけ置く。**同じ内容を両方に書かない。

**⚠ path / URL は会話の «末尾» に置く。**本文の途中に混ぜると探すことになる。**未回答の board が複数あるなら全部を末尾に並べ、決めてほしい順に番号を振る。****回答が来たら «その board を末尾のリストから外す»** — 惰性で貼り続けると、決着済みの判断を «未決» として提示し続けることになる（実際にやった）。

`AskUserQuestion` との併用は**しない**。board の回答フォームが選択の入口を兼ねるので、二重に聞くことになる。

## 設計原則 — なぜこの形か

board の形は、実際の close gate（判断 4 件・資料 11 節）を判断者と往復して削った結果である。
コンポーネントはこの原則を実装している。**書き手が原則側に合わせて構造を崩さないこと。**

- **判断が本体、資料は付録。**読者の仕事は「N 問に答えて貼る」こと。資料は畳んだ付録
  （`db-appendix`）にまとめ、判断に要る根拠は**判断カードの中に inline で開く**（`db-chips`）。
  概要と詳細を離すと、読者は自分でスクロール位置を覚えて往復することになる —
  **「根拠は資料 X」と名前で指して飛ばせる書き方を禁止**しているのはこのため
- **1 判断 1 画面。**常時見えるのは「決めてほしいこと / なぜあなたに / 選択肢 / メモ」だけ。
  経緯・詳しくは畳む。根拠パネルは**選択肢の後**に置き、開いても選択肢を画面外へ押し出さない
- **開く操作は 2 種類だけ。**三角マーカー = 1 つのものを開く / チップ = 複数から選ぶ
  （押されたら反転が残る）。開閉は 0.2s のアニメーションで状態変化を見せる。
  長いパネルには sticky の「付録 · ◯◯」+ 畳むが自動で付く（**内部スクロールは使わない** —
  二重スクロールの認知負荷が高い）
- **範囲参照は展開する。**「AC4〜AC6 は達成」とブロックの外を指して書かない。参照先が
  同じブロック内に見えているときだけ範囲でよい。略号は初出で 1 度だけ定義する
- **有彩色は 5% 以下。**色が付くのは「選択中 / 推奨 / ⚠ / 判断ラベル」だけ。コンポーネントが
  守っているので、**本文の style 属性で色を足さない**（⚠ の `var(--warn)` は例外）
- **進捗はトリアージと目次のチェックだけ。**同じ状態を何通りにも見せない
- **判断どうしの依存を明記する**（`db-deps`）。どれとどれが一緒に決められるか、
  どれがどれを待つか。1 件でも決まれば作業は動かせる — 部分コピーがあるのはそのため

## ボードの組み立て方

同梱の `build-board.sh` に content（`db-*` の並び）を渡す。**sh / awk / grep だけで動く。**

```bash
sh <skill_dir>/build-board.sh content.html "<board 名>" > board.html          # 図なし
sh <skill_dir>/build-board.sh content.html "<board 名>" mermaid > board.html  # 図あり
```

**⚠ mermaid bundle は 1.5 MB ある。図が 1 つも無い board には差し込まない**（第 3 引数を省く）。

**次の 3 つは build がエラーで止める。**描画側は寛容（既定の表示に落として画面にそう書く）だが、
生成の時点で気づけるものを黙って通さない。build が通らないときにタグ名の当て推量で回避しないこと —
この一覧が語彙のすべてである。

- 未知の `db-*` タグ
- reason 無しの `db-embed`
- **ticket の ID を出しているのに `<db-pane>` が無い**（下記「ticket.md / note.md は右ペインに全文で入れる」）。
  判定は `db-tickets` の中の ID 行で行うので、ticket に紐づかない判断の board には掛からない

**⚠ 内容を «直して作り直す» 手順は必ず残す。**配色変更・不具合修正で同じ board を
何度も作り直すことになる（実際 1 日に 6 回あった）。content.html を残しておけば再 build は 1 コマンド。

content の骨格。**この順に並べる**（表示順 = 記述順）:

```html
<db-board date="2026-08-05" gate="close 前の確認" round="2" title="<症状ベースの board 名>">
  <db-lede>1〜2 文の趣旨。前提が変わっていればそれもここに。</db-lede>
  <db-deps>判断どうしの依存。無ければ要素ごと省く</db-deps>
  <db-tickets>
    <db-ticket name="<症状ベースの呼び名>" status="close 承認待ち" who="この窓">
      <db-facts>
        <db-row name="症状">誰がいつ報告したかも</db-row>
        <db-row name="狙い">何ができるようになれば終わりか</db-row>
        <db-row name="触る範囲">複数 ticket が独立かどうかを読み手が判定できる</db-row>
        <db-row name="いまの状態">AC n/n・テスト・レビューの件数</db-row>
        <db-row name="ID"><code>&lt;ticket id&gt;</code></db-row>
      </db-facts>
    </db-ticket>
  </db-tickets>
  <db-pane>
    <db-doc id="ticket" tab="チケット"><db-markdown><script type="text/markdown">
（ticket.md をそのまま貼る）
</script></db-markdown></db-doc>
    <db-doc id="note" tab="作業ノート"><db-markdown><script type="text/markdown">
（note.md をそのまま貼る）
</script></db-markdown></db-doc>
  </db-pane>
  <db-decision id="d1" …>…</db-decision>   <!-- 判断 1〜N。下記 -->
  <db-appendix title="確かめたもの — n 件" summary="…">
    <db-section id="r1" …>…</db-section>   <!-- 資料。順不同・数も可変 -->
  </db-appendix>
  <db-submit></db-submit>
</db-board>
```

テンプレートが**本文から自動で生成する**もの（書くと二重になる）: topbar / 目次レールと現在地 /
先頭のトリアージ（答えると ✓）/ 進捗 / この判断だけコピー / ticket が 2 種類以上のときの
「この ticket のぶんだけコピー」/ 提出欄の集計 / URL ごとの自動保存と復元通知 / 明暗テーマ切替。

**ticket.md / note.md は右ペインに全文で入れる。**`db-markdown` が front matter・表・リスト・
` ```mermaid ` フェンス・`{#id}` アンカーを描画し、`**AC1 —` のような AC 項目には自動で
`id="ac1"` が付く（`<db-ref to="ac1">` の宛先になる）。判断者はチケットを読まなくても決められる
作りにするのが前提だが、**確かめたい人がその場で原文に当たれる**ことが信頼の裏付けになる。
⚠ 原文に `</script>` を含む場合だけ `<\/script>` にエスケープする。

**原文への入口は本文の中に置く。**チケットカードには「チケットを開く」「作業ノートを開く」が
自動で出る（`db-doc` の `tab` から作られるので書かなくてよい）。**それ以外の場所からも
`db-ref` で開ける** — `db-doc` に `id` を付けておき、判断や資料の文中から指す:

```html
<db-ref to="note">作業ノート全文</db-ref>   <!-- 資料の先頭を開く -->
<db-ref to="ac3">AC3</db-ref>                <!-- 原文の中の 1 行を開いて光らせる -->
```

**「上のボタンを押してください」と書かない。**それは強いられる移動であり、押せるものを
その場に置けば済む（「やってはいけないこと」の「名前で指す」と同じ理由）。

**ペインの幅は読む人が変えられる。**左端を掴んで drag（`← →` キー / ダブルクリックで既定に戻る）。
幅は board 横断で保存されるので、**書き手が幅を指定する必要はない。**

**本文の幅は `--db-w` で決まる。**既定は 830px（日本語 45〜50 字/行）で、1500px 以上で 1000px、
1900px 以上で 1180px に広がる。**幅は上限であって固定値ではない** — 広い画面で余白を捨てないための
段階指定である。board 側で変えたいときは content の先頭に 1 行置く:

```html
<style>:root{--db-w:1100px}</style>
```

⚠ **変えるのは «その board の中身が広い幅を要求する» ときだけ**（横に広い表・並べて見る画像など）。
読みやすさの上限を超えて広げると 1 行が長くなり、行を追う目の動きが増える。

## 判断ブロックの書き方 — これは «エンジニアが PM に上げる escalation» である

**判断ブロックは「症状の説明」ではなく「決めてもらうための申し送り」である。**構成は固定:

```html
<db-decision id="d1" title="<決める内容を 1 行で>" tag="要判断"
             ticket="<症状ベースの呼び名>" triage="<トリアージに出す 1 行>">
  <db-prose label="決めてほしいこと" emphasis>1 行。疑問形</db-prose>
  <db-prose label="なぜ聞くのか — 決めてほしい" accent>…（下記 2 種）</db-prose>
  <db-reveal label="経緯を見る — 何が起きてこの判断になったか">
    <db-facts>
      <db-row name="元の問題">何を直そうとしていたのか</db-row>
      <db-row name="やろうとした">そのために何をしたか</db-row>
      <db-row name="起きたこと">何が問題になったか</db-row>
      <db-row name="いまの状態">どこまで済んでいるか</db-row>
      <db-row name="期間 / 限界">いつまでの話か・測れていないこと</db-row>
    </db-facts>
  </db-reveal>
  <db-reveal boxed quiet="詳しく" label="<裏取りの見出し>">実測値・前例・失うもの</db-reveal>
  <db-options> … 選択肢（下記 3 軸） … </db-options>
  <db-memo></db-memo>
  <db-chips label="根拠"> … その場で開く根拠パネル（下記） … </db-chips>
  <db-prose label="決めないとどうなるか">止まっているのか・待てるのか</db-prose>
  <db-meta>追跡: AC 番号・finding 番号・該当コード。小さく最後に</db-meta>
</db-decision>
```

**⚠ 経緯の «元の問題» を省かない。**症状だけ書くと物語の途中から始まる。「8/1 の実行を開くと
『記録なし』と出ます」は、**今日まだ起きていない・これから作るものが作り出す問題**なのに、
そう読めない。何を直そうとしていて、その途中で何が起きたのかまで書いて初めて、選択肢が
恣意的でなくなる。

### なぜ «あなたに» 聞くのか — 2 種類ある

**`accent`（決めてほしい）** — 自分の権限では決められないもの。だいたいこの 5 つ:

| | |
|---|---|
| **お金がかかる** | 本番で 1 回実行してよいか |
| **利用者から見た挙動が変わる** | 422 → 200、画面の文言 |
| **優先順位のトレードオフ** | 今どこまで作るか |
| **取り返しがつかない** | 元に戻せない設定変更 |
| **リスクの許容度** | 未実測のまま出すか |

**⚠ どれにも当てはまらないなら、聞くべきではない。**この欄を書けないものは自分で決める。
**「なぜ聞くのか」は、聞きすぎていないかの検算になる。**

**`accent="check"`（念のため確認）** — **推奨どおりで良いはずだが、引っかかっていること。**
これを正式な種別として持つことに意味がある。無いと、**不安を抱えたまま黙る**か、
**無理に「あなたの判断です」と装う**かの二択になる。label も「なぜ聞くのか — 念のため確認」にする。

### 選択肢 — 軸は「利用者から見て / コスト / 取り返し」に固定する

案ごとに違う観点で Pros/Cons を並べると**横に比較できない**。軸を固定する。
軸は行レイアウトで描かれる（左に軸名・右に本文）ので、縦に目を落とすだけで案を比較できる。

```html
<db-options>                     <!-- 複数選択なら <db-options multi> -->
  <db-option key="A" recommended label="A. <案の内容そのもの>">
    <db-row name="利用者から見て">誰の画面で何が変わるか。「変わりません」も回答</db-row>
    <db-row name="コスト">判断者が払うもの（待ち時間）で書く。後から変えるといくらかもここ</db-row>
    <db-row name="取り返し">やり直せるか。⚠ が付くのはたいていここ</db-row>
    <db-weak>推奨案にも必ず弱点を書く</db-weak>
  </db-option>
  …
  <db-option key="other" label="その他 — 下のメモに書く">
    <db-row name="書き方">メモの内容がそのまま回答になります。</db-row>
  </db-option>
</db-options>
<db-memo></db-memo>
```

- **推奨は別枠にせず `recommended` を付ける**（見出し末尾にバッジが出る）。別枠にすると説明と理由が二重になる
- **推奨しない案も同じ精度で書く。**薄く書けば誘導になる。**推奨案にも `db-weak` を必ず書く**
- **規約と自分の判断が食い違うときは明示する。**黙って上書きしない
- **`key="other"` を全設問に必ず置く。**選ぶとメモ欄へ自動でフォーカスし、メモが回答本体になる。
  実際、3 案を出したところ**ユーザの結論はどれでもなかった**ことがある（それが最も良い設計だった）。
  **選択肢は自分の想像力の限界であって、正解の集合ではない**
- 3 軸が合わない判断（法務・採用など）では `db-row name` を変えてよい。軸名は既定値であって型ではない

**項目ごとに処置を決める設問**（finding 5 件を 1 つずつ起票/見送り、など）は複数選択にしない —
「選ばなかった項目をどうするか」が言えず、「見送る」と「まだ見ていない」が同じ「チェックなし」になる:

```html
<db-per-item name="findings" choices="起票する, 見送る">
  <db-item key="f20" label="一覧の畳み込みが残る" detail="P1 の残余"></db-item>
</db-per-item>
```

**数値で答える設問**は固定案にしない（「10 分」を A/B/C にすると 7 分と言いたい人が other に逃げる）:
`<db-number-input name="limit" value="10" unit="分" min="1" max="60">` を選択肢の中に置き、
文中から `<db-val name="limit">` で参照できる。

**gate を通す行為そのもの**（close 承認など）は選択肢に混ぜず `db-approve` を使う —
「A でいいが close はまだ待ちたい」が言えなくなるため。`<db-approve label="close を承認する">`
は他の判断が全部答えられるまで押せない（`requires-all="false"` で解除）。

### 根拠は判断の中で開く — `db-chips` と `db-ref`

判断者は画面を行き来しない。**そのブロックの中で完結させる。**

```html
<db-chips label="根拠">
  <db-reveal chip="実測した幅（3 案）">2〜3 行の要点。
    ・ <db-ref to="r3">全文を出す — 実測表を見る</db-ref></db-reveal>
  <db-reveal chip="関係する受け入れ条件">
    <div><db-ref to="ac1">AC1</db-ref> 一覧は数字をそのまま出す — この判断はここに関わります</div>
  </db-reveal>
</db-chips>
```

- チップを押すとその場にパネルが開く。押されたチップは反転が残る
- `db-ref` は **AC・資料・判断のどれでも同じ 1 本**で指す。宛先が右ペインの中（AC など）なら
  ペインが開いてその行が 1.8 秒光る。畳まれた資料なら付録ごと開いてスクロールする。
  **画面を移動させない**（読者のスクロール位置は失われない）
- パネル末尾の「全文を出す」リンクは 1 本だけ。移動は選択肢であって既定ではない
- **判断 → 資料の向きを必ず張る。**資料 → 判断だけでは足りない

## スクリーンショット — 枚数を惜しまない

判断に画面が要るなら撮る。**UI の変更は文章より画面のほうが確か。**手順文は読まれないが、写真は読まれる。

- **確かめてほしいケースは 1 件残らず画面写真にする。多すぎるくらいでちょうどいい。**
  確認用サーバは開発コンテナの中で動いていることが多く、port が publish されていないと
  判断者はホストからも外からも開けない。手順だけ渡すと「開けない」で止まる
- 「一覧を見て、行をクリックして、詳細を見る」なら 2 枚に分ける。**1 枚に詰めない**
- **1 スロット 1 枚が既定。light（またはプロダクトの既定テーマ）で固定して撮る。**
  複数を同時に並べる `db-variant` は、**デザイン・色味の確認が論点のときだけ**使う
  （明/暗、変更前/変更後の比較など）。閲覧者のテーマで 1 枚を選んで出す形は使わない —
  もう一方の存在が画面から分からなくなる
- **キャプション（`db-shot` の中身）に「この画像の何を見てほしいか」を書く。**
  「出ること」だけでなく「高くないこと」のような**満たすべき条件**を書く
- 合成データ・手で書いた記録が混ざる写真は `tone="warn"` を付けて明示する
- 画像は base64 で inline する（外部参照はブロックされる。`/tmp` のパスは後から開けない）。
  PNG のままだと重い — 幅 1000px 前後・JPEG 品質 72 程度に落とす（4 枚で 300KB 弱）
- **⚠ `agent-browser screenshot` は相対パスだと repo ルートに保存される。**必ず絶対パスで撮る
- 撮る前の段階なら**寸法入りの枠**を置く: `<db-shot w="1280" h="720" label="実行詳細">キャプション</db-shot>`
  （src 無し = 枠。後から `src` を足して差し替える）

```html
<db-shot tag="① 攻撃の実行" note="exec-7908a0…" w="1280" h="720" label="一覧 → 実行詳細"
         src="data:image/jpeg;base64,…">4 区画に数字が出て、入力・攻撃が <code>1.000</code>。</db-shot>
```

### 自分で触る手順は折りたたみ + base_url 入力

手順は消さずに `db-reveal` の中へ。その中では:

- **`localhost` を既定値にしない・`localhost:` を含む URL を書かない。**ユーザは devcontainer の
  ホスト側（Tailscale 等の別アドレス）から開くので到達できない。board には **path だけ**書く
- ホストと port の入力欄を置く。**`persist="shared"` を付けると入力値が board を «跨いで»
  端末に保存され、次の board では最初から入っている**（閲覧環境のアドレスは毎回同じため）:

```html
<div class="db-inrow">
  <db-text-input name="host" persist="shared" label="ホスト" placeholder="例: dev-box.local"></db-text-input>
  <db-number-input name="port" persist="shared" label="port" value="4187"></db-number-input>
</div>
<db-link copy href="http://{host}:{port}/ui/proj_demo/logs" requires="host">/ui/proj_demo/logs</db-link>
```

  ホスト未入力の間は path だけが見え、入力すると「開く」リンクと URL コピーが生える
- 開けなかった場合にどうすればよいか（port を publish して起動し直す依頼の仕方）を書く
- dev-server は**プロジェクトの規約どおりに起動したもの**を提示する（`PDH-AGENTS.md`「Dev Server And Seed」）

## 図で説明できるものは図にする

**分岐・順序・依存関係**は文章より図のほうが速く正確に伝わる。特に依存関係 —
**矢印を引こうとすると、引けない矢印が目に見える。**実際、依存図を描いていて「今すぐ流せる」と
書いた推奨案が実は別 window の merge 待ちだと気づいた例がある。

図は `pre.mermaid`（または `db-markdown` 内の ` ```mermaid ` フェンス）で書き、
**build の第 3 引数に `mermaid` を付ける**。runtime が同梱の beautiful-mermaid で SVG に描画し、
色は board のテーマ（明暗両方）に追従する。描画に失敗したらソースがそのまま見える（黙って消えない）。

```html
<figure>
  <pre class="mermaid">flowchart LR
  A1[検査① 応答前] --> A2[応答に載せて返す 0.420]
  B1[検査② 13 秒後] --> B2[記録するだけ 0.550]</pre>
  <figcaption><strong>この図の何を見てほしいか</strong>を書く。図だけ置いても論点は伝わらない</figcaption>
</figure>
```

- **subgraph は使わない。**`direction` が無視される・順序が入れ替わる・タイトルがノードに被る。
  前後比較のような並列は、2 本の独立した鎖を `flowchart LR` で並べると素直に段組みになる
- ノードのラベルは短く。`<br>` による改行は効かない
- **図は必ずブラウザで見る。**SVG になった時点で構文エラーでは落ちないが、
  日本語ラベルの折り返しや線の重なりは目でしか分からない

## 必須ルール

いずれも実際の事故から来ている。省くと board の価値が消える。

### 事実の確度を書き分ける

- **確認済み** — 実際にコードを読んだ / コマンドを実行した
- **推論** — 筋は通るが実測していない。**必ず「未実測」と明記する**
- **測定不能** — 測る手段が無い。「無い」ではなく「**測れない**」と書く

推論を断定として書くと、ユーザは検証済みの事実として設計判断に使う。
経緯の「期間 / 限界」行と `db-note tone="warn"` が置き場になる。

### 未対応の finding は全件・件数つきで書く

`PDH-AGENTS.md`「Human Gate Materials」の要件。**採用しなかったもの（起票 / 記録のみ / 棄却）を、
件数と一行理由つきで全部載せる。**ゼロなら「ゼロ」と明記する。何を直さなかったかは、
直したことと同じ重さの判断材料であり、**board に載せなければ他のどこでも検証できない。**

### board の単位は「窓」ではなく「独立して決められるかたまり」

**複数の作業をまとめて 1 枚にすると、片方の前提が崩れたときに «両方» 止まる。**
実例: 2 つの window の AC 承認を 1 枚にまとめたところ、片方が方式変更で作り直しになり、
**完全に独立だったもう片方まで 1 時間 50 分止まった。**

- board を組む前に「この判断とあの判断は、片方だけ先に決められるか」を確認する。
  依存があるなら **`db-deps` にどちらがどちらを待つのかを書く**
- 依存が後から判明したら分割して再発行する（content を分けて再 build すれば数分で済む）
- **分割したら、残ったほうの board にも「何を外したか・なぜか・どこで決めるか」を書く**

### 決定の «文言» ではなく «意図» が守られているかを見る

worker が「決定と技術的には矛盾しないが、意図次第では該当する」と報告してきたら、
**それは worker が正しく止まっている。**勝手に解釈させず、ユーザに戻す。
board で選択肢を書くときも、その決定が «どこまで» を許容するのかを言葉にしておく。
「許容する」だけでは、実装がどこまで行っていいか決まらない。

### 前提が変わったら明記する

board は再発行できる。**前に提示した枠組みが古くなったら、変わったこと自体を書く**
（`db-lede` か該当判断の経緯に）。黙って新しい枠組みに差し替えると、ユーザは前回の判断が
今も有効だと思ったまま読む。

### チケットは名前でなく症状で説明する

ユーザはプロダクト全体を知っていても、**チケット名までは覚えていない。**

- ✅ 「LLM の答えが途中で切れたのに 200 で成功として返っていたのを失敗にする」
- ❌ 「`260729-030156-truncated-output-fail-loud-all-modes` の close」

ID は `db-facts` の 1 行として小さく添える。**出どころ（誰のどの報告か、いつの Slack か）も書く** —
ユーザが文脈を思い出す最短経路になる。

### ⚠ 症状で書くのは «呼び名» だけ — 実体の名前は言い換えない

**上の «症状で説明する» は ticket の呼び名の話であって、«何を触るのか» まで抽象語に置き換えてよい
という意味ではない。**ファイルパス・コマンド・ツール名・関数名・エンドポイント・commit の SHA は、
**そのまま書く。**

- ✅ 「`ticket.sh close` が作る commit message が読みにくい — 上流の `masuidrive/ticket.sh` に出すか」
- ❌ 「完了時の記録が読みにくい件を、上流の道具に出すか」

**⚠ 実体の名前を消すと、読み手は何を指しているのか復元できない。**「完了時の記録」も「上流の道具」も
**それ単体では何のことか分からず、しかも辞書が無い。**症状ベースの言い換えは読み手を助けるための
手段であって、**助けなくなった時点で目的に反している。**

判断の見出しは、読んだだけで **«何が» «どこで» «誰に»** が分かる形にする。判断カードの本文と
`db-meta` にも、grep できる固有名（パス・行番号・SHA・シンボル名）を必ず 1 つ以上置く。

⚠ **どこまで言い換えるかの線引き**は、読み手がその語を**自分の環境で確かめられるか**で決める。
`git log --oneline` / CI / API / JSON のような**どの現場にもある語は言い換えない**。
言い換える価値があるのは、**その repo の内部でしか通じない語**（内部フィールド名・処理順序の呼び名・
モジュール内の造語）だけで、それも**初出で 1 度、実体の名前を併記してから**にする。

**この規則は実際の失敗から来ている。**2026-08-09、close の状況をまとめた board で
`ticket.sh close` を「完了時の記録」、`masuidrive/ticket.sh` を「上流の道具」と書いたところ、
**判断の対象が何なのか読み手に伝わらなかった**（「完了時？上流の道具？」と聞き返された）。
同じ失敗はその 3 日前にも起きている。

### board は 1 枚で完結させる — 他の board を見に行かせない

**board は、それだけ読めば決められる状態にする。**読み手は他の board を持っていないし、
同じ ticket の 2 巡目でも、前の板に何が書いてあったか・自分が何を選んだかは覚えていない。

**他の board を «参照させる» ことを書かない。**「前回の board を参照」「別の board で決めたとおり」
と書いた時点で、読み手は決められなくなる。**書くのは参照ではなく «中身» である。**

- ❌ 「**前回の 4 件**は決まりました。それを反映して……」
- ✅ 「着手の前に判断が 4 件あり、答えをいただきました。①〜を含めません ②〜を統合します
  ③〜は寄せません ④〜は直しません。その決定を反映して……」

- **「前回」「先ほど」「上記」「例の」で始めない。**とくに `db-lede` の 1 文目。読み手が最初に
  読む場所を指示語で始めると、**何の話かが分からないまま**残りを読むことになる
- **この board で定義していない番号を使わない。**「判断 2 により範囲外」の 2 は、読み手には
  解けない記号である。番号を使いたいなら**この board 内で 1 度定義してから**使う
- **2 巡目でも「症状」「狙い」を書き直して載せる。**前に書いたから省く、をしない
- **⚠ 資料・チップ・付録の中まで掃く。**指示語は本文より**畳んだ中に残りやすい**（本文は読み返す
  ので気づくが、資料は書いたまま出す）。発行前に `前回` `先ほど` `上記` `判断 [0-9]` を grep する

### URL があるものはリンクを貼る

**上と矛盾しない。**禁じているのは「board を見に行かせること」であって、**出典を示すこと**ではない。
外部にあって URL で開けるものは、**結論を board に書いたうえでリンクを添える。**

- 仕様書・公式ドキュメント・規格・ライブラリの issue や PR
- GitHub 上のコード・commit・workflow の実行結果
- Slack の元メッセージ、外部の記事

**リンクは «確かめたくなったときの最短経路» として置く。**読まなくても決められる状態は保ったまま、
裏取りしたい人がすぐ原典に届くようにする。⚠ **リンクを貼ったことを、中身を書かない理由にしない。**

- ✅ 「litellm が `aspect_ratio` を捨てます（[BerriAI/litellm#18656](https://github.com/BerriAI/litellm/issues/18656)）」
- ❌ 「詳細は [#18656](https://github.com/BerriAI/litellm/issues/18656) を参照」

⚠ **リンク先が誰でも開けるかを確かめる。**private repo・要ログインのページ・期限つき URL は、
読み手の環境では開けないことがある。開けない可能性があるものは、**開けなくても足りるだけの
内容を board 側に書く。**リポジトリ内のファイルは URL ではなく**パスと行番号**で示す。

## 発行前に、選択と集計が動くことを確認する

**選択 → 集計が出るかを 1 回だけ確かめる。**壊れているとユーザは「選んだのに回答が出ない」
状態で詰まる。**`file://` では動かない。**`python3 -m http.server` で出す。

```bash
agent-browser eval "
(function(){ document.querySelector('db-option').click();
  return {decide: document.querySelectorAll('db-decision').length,
          checked: document.querySelectorAll('.db-triage .db-check.on').length,
          docs: document.querySelectorAll('db-doc').length,
          out: document.getElementById('out').textContent.slice(0, 200)}; })()
"
```

**`decide` が判断の数と一致し、`checked` が 1 になり、`out` に選択が出る**ことを確認する。
**`docs` は右ペインのタブ数**（ticket board なら ticket.md / note.md の 2）。build は `db-pane` の
欠落を止めるが、**中身が入っていない**（`db-markdown` の貼り忘れ）はここでしか気づけない。
「その他」を使う設問があるなら、それも 1 度選んでメモを書いてみる。図がある board は
ブラウザで図の崩れも見る。

## 回答を受け取ったあと

ユーザは提出欄をコピーして会話に貼る。形はこうなる。

```
# 判断ボードの回答 — <board 名>

## 判断 1 · <title>
選択: A. <選んだ選択肢>
メモ: <メモがあれば>

## 判断 2 · <title>
- [x] <複数選択で選んだ項目>
- [ ] <選ばなかった項目>

---
回答済み 3 / 4
```

- **「選択: その他 — …」はメモが回答本体。**そのまま指示として受け取る
- **「（未選択）」を勝手に埋めない。**答えられていない判断が残っているということ
- **決まった内容は ticket / note / commit message に落とす。**board は決めるための机であって記録ではない

## やってはいけないこと

| アンチパターン | なぜ |
|---|---|
| 判断の材料ではなく作業の経過を書く | board は決めるための道具。何をしたかは note と会話に書く |
| 選択肢を列挙して推奨を出さない | 「あなたが決めてください」は判断コストの丸投げ |
| 推奨案の `db-weak` を空にする | 検討が足りていないだけ。トレードオフの無い選択肢はほぼ存在しない |
| `key="other"` を置かない | 逃げ場が無いと、近い案が選ばれて誤読される |
| 見出しを実装の言葉で書く | `AC2 に理由を持たせるか` は読み手の言葉ではない。**症状で書く** |
| 実体の名前まで抽象語に言い換える | 「完了時の記録」「上流の道具」では**何を指すか復元できない**。パス・コマンド・ツール名はそのまま書く |
| 他の board を «参照させる» ことを書く | 読み手は他の board を持っていない。**参照ではなく中身を書く**（1 枚で完結させる） |
| 「前回」「先ほど」「上記」で書き出す | 読み手が最初に読む場所を指示語で始めると、何の話か分からないまま残りを読むことになる |
| この board で定義していない番号を使う | 「判断 2 により範囲外」は解けない記号。**決定の内容そのもの**を書く |
| URL で開けるものにリンクを貼らない | 出典を示すのは «見に行かせる» ことではない。裏取りの最短経路を奪っている |
| リンクを貼ったから中身を書かない | リンク先が開けるとは限らない。**結論は board 側に書き、リンクは添える** |
| 「なぜ聞くのか」を書かない | 書けないなら**聞くべきでない**。この欄は聞きすぎの検算 |
| 経緯の「元の問題」を省く | 物語の途中から始まり、選択肢が恣意的に見える |
| 「詳細は資料 X」「上のスクリーンショット」と名前で指す | 強いられる移動になる。`db-ref` か `db-reveal` でその場に出す |
| 案ごとに違う観点で Pros/Cons を書く | 横に比較できない。**利用者 / コスト / 取り返し** に固定する |
| 不安なのに «あなたの判断です» と装う | `accent="check"`（念のため確認）がある。**正直に書く** |
| 追跡情報を先頭に置く | 何の話か分からないまま読み始めることになる。`db-meta` で最後に小さく |
| 裏取りの材料を «消す» | 症状ベースにすると詳細が落ちる。**消さずに `db-reveal` へ** |
| 未確認のことを断定する | 上記「事実の確度」参照 |
| board を作って会話にも全文を書く | 二重管理になり、片方が古くなる |
| **URL を会話の途中に埋める** | 探すことになる。**末尾に置く** |
| CSS / JS を書き直す・style で色を足す | **色は選ばない。**配色・機構は検証済みで固定。本文の色は ⚠ の warn だけ |
| `localhost` を既定値や URL に書く | ユーザは別アドレスから開く。base_url 入力（`persist="shared"`）に任せる |
| 同じ要約を 2 箇所に書く | 同じ生成の中でも食い違う（実例あり）。要約は 1 箇所、全文は `db-ref` で指す |
| 1 件しかない単純な判断で board を作る | `AskUserQuestion` のほうが速い（ただしプロジェクトが **ticket / close の判断は 1 件でも board 必須**と定める場合はそれに従う） |

## 判断が済んだあと

board は**判断の記録としては使わない。**決定した内容は ticket / note / commit message に落とす。
board はあくまで「決めるための机」であり、決まった後の正は repo 側にある。

ただし board 自体（と content.html）は消さない。**次に同じ論点が来たとき、前回どの材料で
決めたかを引ける。**訂正版は同じ path に再 build して出す。
