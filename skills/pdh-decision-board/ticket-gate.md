# 実装前 gate（`PDH-ticket-human-review`）の判断ボード

この gate の承認は**「この Why を、この AC と解き方で解いてよいか」**である。**board の内容を board 用に発明しない** — 並べ替えと、決めるのに要る文脈を補うだけで、約束も語も ticket の節から取る。

## board と ticket の関係

- board は原則として自己完結させる。ticket の参照だけで内容を省略しない（機微な情報を扱う ticket だけは [risk-overlay.md](risk-overlay.md) に従う）。
- board の選択肢と、選択後の ticket の文面を一対一に対応させる。
- **board を書く途中で ticket の欠陥を見つけたら、board で判断を求めず、承認前の ticket を先に直す。**
- board に表示する AC は、承認対象となる ticket の最新文面と一致させる。
- **ticket へ書き戻せない事情がある場合は gate を止める。「承認後に直す」と約束して進めない。**

## 書き始める前に — 洗い出しは `PDH-ticket-review` の仕事〔手順 1〕

**未確定の洗い出し（`Open Questions` の全件確認・未確認を表す語の検索・断定の裏取り・影響範囲・合意された添付）は、[pdh-dev skill の `PDH-ticket-review`](../pdh-dev/SKILL.md) が調べる場所と確認内容の表を持っている。**board を書く前に、その洗い出しが済んでいて結果が note にあることを確認する。残っていたら board で判断を求めず、`PDH-ticket-review` へ戻って ticket を先に直す。

あちらの表に無い検索だけ、この gate が足す。**英語と記号のマーカー** — `draft`、`TBD`、`TODO`、`FIXME`、`needs-*`、`[NEEDS CLARIFICATION]`、`(?)`。その repo が使う独自マーカーは、既存 ticket を数件開いて見つける。

洗い出した項目は、[base.md](base.md)「判断の分類」で 3 つに分ける。**測定結果が scope・影響範囲・AC を変えたら、ticket を直してから board を作る。**

## 主線の固定部 — 5 面〔手順 4〕

**主線の面数 = 固定 5 面（なぜ / ゴール / 解き方 / 決めること / 返す）+ 判断の数 `N`**

1. **なぜ** — ticket の `Why / Intent`。誰が何に困り、直さないと何が起きるか。**まだ誰も困っていない予防の ticket では、«放置するとどの条件で誰が困るか» に置き換える。架空の «いま困っている人» を書かない。**
2. **ゴール** — ticket の `What / Acceptance Criteria`。冒頭の «終わると誰が何をできるか» の 1 文は ticket 本文の文をそのまま使う。現在と変更後を示す。
3. **解き方** — ticket の `確定判断 (Design Decisions)` と `Architectural Invariants check`。書き手が確定させた解き方と、退けた案。**承認者は AC だけでなく、この解き方ごと承認する。**確定判断の無い ticket では「確定判断なし」と 1 行書く（面ごと省かない）。
    - **各確定判断に «実コードで確認済み» か «実コードは未確認» かを添える。**
    - **ファイル名と行番号は主線ではなく畳みへ置く。消すのではない** — 畳みに **path:line と «そこで確かめたこと»** を並べる。
    - **解き方は «承認者から見て何が変わるか» で書く。**「この関数の role 判定を下げる」ではなく「viewer もテストを実行できるようになり、費用は project 上限で止まる」。
    - **他案を比べていないなら「他案は検討していない」と書く。**
4. **決めること** — ticket の `Open Questions` のうち、承認者にしか決められないもの。件数、依存順、推奨を先に示す。**`N` がいくつでも、ここに «AC 全件を承認して実装に入ってよいか» の承認文と、«承認が間違いになる条件» を置く。**権限の依頼があれば、判断とは別の欄としてここに置く。
5. **各判断** — [base.md](base.md)「主線の構成」のとおり。
6. **返す** — 選択内容または承認文をそのまま返せる文章。

**なぜとゴールを裏付けへ落とさない。**選択肢を比較する基準そのものだからである。

`N = 0` のときの主線は、1〜3 に加えて **「この AC で実装に入ることを承認してほしい」という承認文・AC 全件・承認が間違いになる条件**、そして承認・修正指示・差し戻しを返すための文章とする。**「判断なし。AC の承認だけ」と明記する。**

## 主線と裏付けに置くもの — これしか置かない〔手順 4〕

**主線は上の 5 面だけで、各面が持つのは次だけである。**

- この ticket が誰の何を可能にするか。Why と、上位の目的とのつながり（なぜ）。
- 承認対象となる AC 全件（ゴール）。
- 書き手が決めておいた内容と、退けた案（解き方）。
- 未確定の判断・選択肢・推奨と、承認文（決めること）。
- 承認者へ返してほしい答え（返す）。

**主線から 1 手で開ける裏付けに置くもの:**

- scope 外の内容と、外した理由。
- 計画を崩しうる既知のリスクと依存。
- ⚠ **ticket review 中に変えた内容と理由** — **推奨や解き方が起票時から反転しているなら、何がいつ反転したかを書く。復元できないなら「変更なし」と書かず、「記録が無いため復元できない」と書く。** reviewer に「変更履歴だから畳め」と指摘されても、反転の事実は主線から外さない。反転は承認者の判断材料である。

**この 2 つのリストに無いものを主線へ置かない。**書き手の裏取りの経緯、測定ログ、どの reviewer の指摘で何を足したか、板の数についての宣言は、どれも主線に置かない。置き場所の引き方は [final-check.md](final-check.md)「指摘への応じ方」に従う。

**該当しない項目は、書かない。**「無し」「該当なし」の根拠を節で書かせない。書かないことで承認者が取り違える項目だけ、1 行で「無い」と書く。

## 選択肢と ticket を一対一にする〔手順 5・10〕

各選択肢について、選ばれた後の ticket を具体化する。

- ticket のどの節・どの AC が変わるか。件数が変わるなら変更後の数も示す。
- 変更後に、Why・AC・Design Decisions・Out-of-scope が互いに矛盾しないか。
- 判断どうしの依存。別の判断の内容を変える判断を先に置く。**順序だけでなく後の判断本文にも依存条件を書く。**
- 一括承認か、群ごとの承認かを明記する。

**承認された選択肢を ticket へ反映できない状態で board を出さない。**

## 板を出さない条件〔手順 0〕

**現状が壊れていて、どの直し方でも現状より良く、外から見える契約が変わらないなら、実装前の板は出さない。**直してから、変更前と変更後の像を close 前 gate の板 1 枚で見せる。

## Open Questions を差し戻さない〔手順 2〕

書き手が決められる Open Question は board の前に決める。各項目について採った案と理由、採らなかった案と退けた理由を示し、**承認者には覆す道だけを残す。**不可逆な決定、プロダクト価値、費用負担など承認者の権限に属する項目は、推奨を付けた判断として残す。

⚠ **選択肢の一方が «触らない» でも、もう一方で利用者ができること（画面・API・CLI の出力・出荷物）が変わるなら、それは承認者の判断である。**触らない側を書き手が選んで問いを消さない。**書き手が決めた Open Question も ticket から消さず、採った案と退けた案を「解き方」に残す。**
