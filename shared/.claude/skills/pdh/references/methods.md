# 設計と試験の手法を、変更の特徴から引く

実装方針を迷ったときは、対象の行で条件と選択肢を見比べる。同じ目的を既存の仕組みで達成できれば、それを使う。この表を埋めたり、採用した手法を数えたりする必要はない。

## 実装するとき

| 要求や既存コードに見える特徴 | 候補になる手法と効き方 | 見送る条件・注意点 |
|---|---|---|
| 直前の出来事や操作順で、次にできることが変わる | **状態遷移表・有限状態機械（FSM）**。状態とイベントの組ごとに次の状態を決める | 分岐が小さく1か所で見通せるならそこで扱う。新しいライブラリは必須ではない |
| 排他的な状態ごとに必要な値が違う。似た型の値を取り違えられる | **判別可能なユニオン型・意味別の型**。矛盾する組み合わせを表現から外す | 独立したフラグはそのまま持てる。型だけで外部データの中身は検証できない |
| 同じ値を複数箇所で更新する | **単一の情報源・導出値**。計算できる値を元データから求める | 計算や外部取得が高価ならキャッシュも候補。鮮度の要件と失効条件を決める |
| 複数の経路が同じ保存上の制約を守る | **一意制約・外部キー・CHECK制約**。同じDBへの書き込みなら保存時に拒否できる | 画面だけのルールをDB全体に課さない。既存データとNULLの意味を確かめる |
| 複数更新が一緒に成功する必要がある。別の処理も同じ値を更新する | **トランザクション・原子的更新・条件付き更新（楽観的ロック）**。部分更新や上書きを防ぐ | トランザクションだけで更新消失を防げるかは分離レベルとSQL次第。単一の原子的更新で足りる場合もある |
| 失敗後に同じ要求を再実行する。DB更新と外部への通知がまたがる | **冪等性キー・トランザクショナルアウトボックス**。再試行を同じ操作とみなし、必要なら送信予定も更新と一緒に保存する | SDKが保証する範囲を先に見る。アウトボックスは再配送しうるため受信側の重複処理も考える |
| 外部処理が停止する、応答順が変わる、資源に解放が要る | **タイムアウト・キャンセル・上限つきバックオフ・スコープに沿った資源管理**。待機・再試行の所有者を決める | 副作用のある処理を無条件に再試行しない。待機の打ち切りと相手側の処理停止は別々に確かめる |
| ファイル書き換えの途中終了で旧データまで失う | **一時ファイルと原子的置換**。完成した出力を既存ファイルに置き換える | 同じファイルシステムなどOSの条件を確認する。電源断後にも残す必要があれば永続化の保証も調べる |
| 外部の値・利用者の権限が内部処理に入る | **境界でのスキーマ検証・認可済みスコープ・パラメータ化API**。値の意味と操作可能な対象を入口に合わせる | 形式が正しくても権限があるとは限らない。既存の検証・認可機構が覆う経路を先にたどる |
| 古い呼び出し元・データと新しい形式が共存する | **後方互換・段階移行（expand and contract）**。追加、移行、削除を分ける。CLIでは出力形式・終了コードも契約に含む | 全利用者とデータを同時に安全に更新できるなら段階移行の運用負担を省ける |
| 似たコード、複数の外部実装、計算とI/Oの混在がある | **DRY・アダプター・依存性注入**。一緒に変わる業務ルールを集約し、実際に差し替える境界を狭める | 似た式でも変更理由が違えば分ける。実装が一つで直接検査できるなら将来用の抽象層を作らない |
| 件数に比例して問い合わせや転送が増える | **バッチ取得・ページネーション・ストリーミング**。実データ量と要求回数・メモリ・時間を測って選ぶ | 件数が小さく上限も明確なら直接取得が簡潔。一括取得は別のメモリ負荷を生む |
| 利用者が操作する画面やCLIの入口を追加する | **標準HTML要素・既存UI部品・標準の引数解析**。入力・キーボード操作・ヘルプなどの既存挙動を再利用する | 製品固有の操作やエラー時の振る舞いは、既存部品を使っても別途確かめる |

## テストを書くとき

利用者との契約から、誤りを見分ける期待結果を先に決める。入力を選ぶ方法、正しさを判定する方法、実行する層は組み合わせられる。たとえば状態遷移は、関数でも実DBとの結合試験でもブラウザでも試せる。

| 確かめたいこと | 候補になる手法と観察 | 見送る条件・注意点 |
|---|---|---|
| 特定の入出力、境界、条件の組み合わせ | **具体例・同値分割・境界値分析・デシジョンテーブル・ペアワイズ**。異なる結果を生む代表例を選ぶ | 全組み合わせを列挙する費用と影響を比べる。ペアワイズは3要因以上の相互作用を保証しない |
| 操作順や並行した更新で結果が変わる | **状態遷移テスト・モデルベーステスト・並行実行テスト**。操作列と事後状態を独立した規則やモデルと照合する | 単一の例で十分ならモデルを二重に保守しない。内部の関数呼び出し順を仕様にしない |
| 広い入力範囲で同じ性質が成り立つ | **プロパティベーステスト（PBT）・メタモルフィックテスト**。入力を生成して不変条件や入力変形前後の関係を調べる | その性質の業務上の根拠が要る。生成回数を増やしても誤った期待値は直らない |
| 既存契約を維持しつつ実装を置き換える | **差分テスト・参照実装・契約テスト**。同じ入力の出力を比較し、呼び手と提供側の約束を確かめる | 意図的に変える挙動は比較から区別する。両方が同じ誤解を共有しうる |
| 遅延・部分失敗・再試行の結果を知る | **障害注入・stub・mock**。狙う時点の応答や失敗を制御し、利用者に返る値や実際に残った状態を調べる | 実DBの制約や外部との互換性には実物を使う。mockの呼出回数だけで業務結果の正しさを決めない |
| どの層で初めて間違いが観察できるか | **単体・コンポーネント・統合・E2E・実機試験**。必要な境界を含む最も軽い層を選ぶ。使い勝手や要求漏れなら**探索的テスト・利用者観察**も候補 | 同じ失敗を全層で試さない。実機・人の操作はその環境が結果を左右する場合に使う |
| 経路を通ったのに、誤った結果も通りそう | **文・分岐カバレッジ、ミューテーションテスト**。未実行箇所を探すか、代表的な誤りを入れてテストの判定力を調べる | 数値は未検査の手掛かり。採点やcloseの閾値にしない。全変異を毎回試す必要はない |
| 期待結果が明確だが実装の答えに引きずられそう | **テストファースト・TDD・独立した期待値の設計**。契約から失敗例や成立すべき性質を決め、小さく動かす | タイミングと期待値の独立性は別。仕様が未決なら、テストで製品の意味を勝手に決めない |
