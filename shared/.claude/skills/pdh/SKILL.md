# Brief の利用場面を完成させる

**着手。** 実行履歴の質問なら記録を読み、実行したかどうかを答える。実装の依頼なら product-brief.md を読み、誰が何をできるようになるかを1文で言えるところから始める。Brief を作るときは、使う人と困り事、完成したときの操作と結果、許せない失敗・許せる費用・外部制約を書く。製品の判断が変わる具体例を残す。実装手順は開発文書へ置く。

**起票・再開。** [チケットの操作手順](../../../tickets/PDH.md) に従って `./ticket.sh new` で起票し、合意を記録してから `./ticket.sh start <名前>` でチケットの worktree に移る。再開も同じ `start` を使う。worktree でリンクを復元するには `./ticket.sh restore` を実行する。

**約束。**今回扱う場面を `tickets/<名前>/scope.md` に、画面・API・CLI 等で観察できる結果として1条件1行の `- 条件` で書く。対象の人・環境・接続先が複数なら、全部を照合できるようにする。見出しと空行も使える。依頼にある条件をそのまま使える場合は二度聞かない。意味の決まらない条件だけ着手前に人と決める。Brief と scope を含む commit の完全な SHA を合意の基点として `tickets/<名前>/progress.md` に `- 初回合意 | 完全SHA` の1行で記録・commit し、再開時も同じ値を使う。利用者が何を判断・実行し、どんな失敗がそれを誤らせるかも同じ記録に1〜2行で書く。Brief にあれば参照でよい。時間の予算があれば開始時刻と人に戻す時点も控える。

**試験を計画する。** [実装者用の指示](references/implementation.md) を使い、実装前に、Briefの利用場面を利用者の入口から最後の判断・操作までたどる。まず普通に使う一往復を選び、どの境界で何が食い違うと利用者の判断が変わるかを考える。選んだ場面はチケットの `checklist.md` に、試す操作・正しさを照合する別の事実・何が見えれば失敗かが分かる `- [ ]` の文で残す。既存試験で足りる場面はその名前を使う。実機や人の操作が必要なら、どの候補版で、誰がいつできるかを先に見通す。詳細と例は[試験計画](../../../tickets/PDH.md#試験計画)。実行後に確認済み `[x]` または対象外 `[-]` とし、直下の `  根拠: …` に観察結果か対象外の理由を記す。未確認は `[ ]` に残す。

**作る。** 委譲するときは、利用者が得る結果・対象・触れてよい範囲、Brief と AC の場所を依頼文に書く。実装・試験担当には「作業先の `.claude/skills/pdh/references/implementation.md` を読んで今回の実装と試験を選ぶ」と依頼する。作業先から読めなければ本文を渡す。まず利用者と同じ入口から最小の一往復を通し、早いうちに各対象で本物の結果を見る。作り方・調査・やり直しは担当者が決める。人に決めてもらうのは利用結果や許容する失敗の変更、未承認の費用や外部への影響、最後の完了承認。現実装の不具合は元のACで直す。外部仕様や残り予算などから約束を選び直す根拠があるときだけ、元のACを守る案（作り直しを含む）と変更案を人に示す。両案で何ができ、何を失い、費用とBriefの完成がどう変わるか、推す案と理由、先送りなら戻す時期か未定であることを説明する。明示の選択を受けてから Brief または scope を改訂・commit し、progress.md に `- 再合意 | 最初の合意の完全SHA | 改訂後の完全SHA | 変更を提案する根拠 | 維持案の得失 | 変更案の得失 | 人の明示回答` を1行記録して commit する。以後もコマンドには最初の合意を渡す。達成できなかった部分を条件から消して完了にしない。

**試す。** まず利用者が何を判断・実行するかからシナリオを選び、既存試験を生かして実行する。途中の遅れや失敗が判断を変えるなら、その間の表示と実際の状態も照合する。実行後、何を確かめたかをチケットの `tests/coverage.tsv` で合意した各ACに対応付ける。既存の結果を使い、根拠が不足する場面だけを追加して試す。[実行結果の収集と対応付け](../../../tickets/PDH.md#シナリオと実行結果) を参照する。

- **application test** は、close 後も毎回守る製品の振る舞いを通常スイートで検査する。既存試験で破れを検出できれば追加は0件。漏れる失敗だけ、検出できる最も軽い層で既存試験を広げるか、代表例を一つ足す。別の層や組合せにも足すのは、そこだけで起きる別の失敗があるとき。遅い試験を常設する前に実行時間を測り、軽い試験では拾えない失敗を明らかにする。
- **ticket test** は、今回のACや反例を確かめる実機操作、計測、故障の再現。再実行する試験は実行できるコードとして `tickets/<名前>/tests/` に保存し、worktree の `./current_ticket/tests/` から使う。共通の入口は `./scripts/test-ticket-local.sh` で、現在のチケットの実行可能な `tests/test-ticket-local.sh` を呼ぶ。専用スクリプト・実データ操作の結果は機微データを除いて `evidence.md` に残す。手動で足りるときは手順もそこに書く。製品と通常スイートはここに依存させない。一つの操作で複数のACを確認してよい。

実装中は影響する試験だけを回す。実データは許可された隔離環境で照合し、機密を除いた順序・差・時間などを残す。実機が必要で使えなければ未確認とする。各ACと選んだ反例を判定でき、既知の違反が解消したら追加を終える。時間のかかる確認は既存結果で足りるかを先に調べ、予算内に確かめられない条件は未確認として人に戻す。

**見直す。** close 前に、実装時の会話を引き継がない subagent に、Brief・AC・既知の制約・候補の差分とテストコード・試してよい環境を渡す。実装者の合否判断、試験結果、PMのclose判断を伝える前に、ACがすべて通っても利用者が判断や操作を誤りそうな場面を一つ選び、試す操作と何が見えたら失敗かを返してもらう。その操作を利用者と同じ入口から試す。作り直しでは、同じ約束について旧版で実際に失敗した操作を検収側で照合する。反例を新しく探すのは作業ごとに原則1回。約束を破ったら同じ作業で直す。修正確認の担当には既知の再現手順を最初から渡し、失敗した操作と通常の操作を再試験する。再提出では修正が影響する範囲を確かめる。ACを満たした上で残る制約は、製品の known-limits に影響・回避・再判断の条件を残す。既に判明した未解決の違反があれば提出を止める。

**完了を判断する。** 製品と試験を commit し、その版で各条件の観察をそろえる。チケットのディレクトリ（`tickets/<名前>`）を WORK、最初に記録した完全な SHA を AGREED とすると、次の順に進める。

1. `python3 scripts/pdh.py test "$WORK" "$AGREED"` でその製品の scripts/test-all.sh を1回実行する。成功時に WORK/suite-pass ができる。
2. WORK/evidence.md に `- 条件の原文 | 観察した完全な commit SHA | どの入口で何と比べ何を観測したか` を1条件1行で書く。続けて見出し `## 反例確認` の下に1行、`- 判定 | 製品の完全SHA | 試した操作 | 観察結果 | 処置` を書く。`問題なし` は観察した範囲、`許容` の処置は `影響 / 回避 / 再判断条件`（回避できなければその旨）。`要修正`・`約束変更`・`未確認` の間は提出を止める。記録を commit する。
3. 新しく合意したチケットは、worktree で `./ticket.sh decision` を実行し、[送信内容を確認して判定を記録する](../../../tickets/PDH.md#独立検収)。既定は独立した Codex セッション。保留なら該当ACか反例を一度確かめ、新しい観察で再確認は1回まで。ACを満たす制約は known-limits に残す。
4. `python3 scripts/pdh.py ready "$WORK" "$AGREED"` を実行する。未確認の結果を書いて通さない。

製品・application test・通常スイートの実行条件を変えたら最終候補で全体試験を1回通す。ticket test は使う版を commit してから観察する。それだけを変えたときは通常スイートの成功を使えるが、ready には変更後の版での各ACと反例の観察が要る。独立した説明の修正は scripts/pdh-prose.txt に列挙されたファイルだけが対象で、同じ製品の結果を使える。証拠と残る制約を人に渡す。試行中は、選んだ場面・追加で見つかったこと・提出判断の変化・所要時間を progress.md に残す。人から対象の版への明示の完了承認を受けたら、返事と版を progress.md に記録・commit し、チケットの worktree で `./ticket.sh close` を実行する。通常の close は `ready` を呼ぶ。新方式ではチケットの worktree から通常の close を使う。中断時は基点、最後に動いた場面、残る条件、次の一手を同じファイルに残す。
