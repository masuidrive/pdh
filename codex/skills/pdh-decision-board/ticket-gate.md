# `PDH-ticket-human-review` の decision-board

（ファイル名の `ticket-gate` は、PDH-ticket-human-review を指す古い呼び名である。リンクが参照するので名前は変えない。）

この PDH-stage の承認は**「この Why を、この AC と作り方の判断で解いてよいか」**である。**decision-board の内容を decision-board 用に発明しない** — 並べ替えと、決めるのに要る文脈を補うだけで、約束も語も ticket の節から取る。

## decision-board と ticket の関係

- decision-board は原則として自己完結させる。ticket の参照だけで内容を省略しない（機微な情報を扱う ticket だけは [risk-overlay.md](risk-overlay.md)（危険が大きいときの追加規則）に従う）。
- decision-board の選択肢と、選択後の ticket の文面を一対一に対応させる。
- **decision-board を書く途中で ticket の欠陥を見つけたら、decision-board で判断を求めず、承認前の ticket を先に直す。**
- decision-board に表示する AC と Out-of-scope は、承認対象となる ticket の最新文面と一致させる。
- **ticket へ書き戻せない事情がある場合は PDH-ticket-human-review を止める。「承認後に直す」と約束して進めない。**

## 書き始める前に — 洗い出しは `PDH-ticket-review` の仕事〔手順 1〕

**未確定の洗い出し（`Open-Questions` の全件確認・未確認を表す語の検索・断定の裏取り・影響範囲・合意された添付）は、[skill `pdh-ticket-review`](../pdh-ticket-review/SKILL.md) が調べる場所と確認内容を持っている。**decision-board を書く前に、その洗い出しが済んでいて結果が note にあることを確かめる。残っていたら decision-board で判断を求めず、`PDH-ticket-review` へ戻って ticket を先に直す。

あちらの表に無い検索だけ、この PDH-stage が足す。**英語と記号のマーカー** — `draft`、`TBD`、`TODO`、`FIXME`、`needs-*`、`(?)`。その repo が使う独自マーカーは、既存 ticket を数件開いて見つける。

洗い出した項目は、[base.md](base.md)「判断の分類」で 3 つに分ける。**測定結果が scope・影響範囲・AC を変えたら、ticket を直してから decision-board を作る。**

## 本文の固定部 — 5 節〔手順 4〕

このファイルの «本文» は、decision-board のうち**承認者が必ず読む部分**を指す。«節» は本文の節（スライドの媒体ならスライド 1 枚）を指す。本文以外の材料は、本文から開いて読む根拠（以下「根拠」）に置く。

**本文の節の数 = 固定の 5 節（なぜ / ゴール / 作り方の判断 / 決めること / 返す）+ 判断の数 `N`**

1. **なぜ** — ticket の `Why`。誰が何に困り、直さないと何が起きるか。**まだ誰も困っていない予防の ticket では、«放置するとどの条件で誰が困るか» に置き換える。架空の «いま困っている人» を書かない。**
2. **ゴール** — ticket の `What / Acceptance Criteria`。冒頭の «終わると誰が何をできるか» の 1 文は ticket の文をそのまま使う。現在と変更後を示す。Out-of-scope も全文を示す。
3. **作り方の判断** — ticket の `Design-Decisions` と `Architectural-Invariants-check`。ticket の書き手が確定させた作り方の判断と、選ばなかった案。**承認者は AC だけでなく、この作り方の判断ごと承認する。**作り方の判断の無い ticket では「作り方の判断なし」と 1 行書く（節ごと省かない）。
    - **各作り方の判断に «実コードで確認済み» か «実コードは未確認» かを添える。**
    - **ファイル名と行番号は本文ではなく、閉じた `<details>` に入れる。消すのではない** — `<details>` の中に **path:line と «そこで確かめたこと»** を並べる。
    - **作り方の判断は «承認者から見て何が変わるか» で書く。**「この関数の role 判定を下げる」ではなく「viewer もテストを実行できるようになり、費用は project 上限で止まる」。
    - **他案を比べていないなら「他案は検討していない」と書く。**
4. **決めること** — note の `Open-Questions` のうち、承認者にしか決められないもの。件数、依存順、推奨を先に示す。**`N` がいくつでも、ここに «AC と Out-of-scope の全件を承認して実装に入ってよいか» の承認文と、«承認が間違いになる条件» を置く。**権限の依頼があれば、判断とは別の欄としてここに置く。
    - **承認文の前に、コストと利益を置く。**note の `## PDH-ticket-review. Ticket contract check` の節にある `Benefit:`・`DB-changes:`・`API-changes:`・`Complexity:` を、承認者の言葉で 1〜3 行にする。承認者はこれを見て «この利益に、このコストを払うか» を決める。`Feasibility:` は閉じた `<details>` に入れる
    - `DB-changes:` か `API-changes:` が «なし» でないときは、その変更と戻し方を本文に書き、[risk-overlay.md](risk-overlay.md)「不可逆な変更」に当たるかを判定する
    - **ticket の diff が `[SKILLS_PATH]/pdh-review/SKILL.md`「fail-open を先に探す diff の一覧」に当たる見込みなら、«PDH-review で修正が落ち着いた後に、網羅探索をもう 1 巡回すか» を判断の 1 つとして置く。**当たるかは、ticket の Design-Decisions と影響範囲から decision-board の書き手が判定する。PDH-review に入ってからは聞かない（`[SKILLS_PATH]/pdh-review/SKILL.md`「収束」）。選択肢は «回す（推奨。拒否すべきものを通す経路を、修正の後にもう一度探す）/ 回さない（その 1 巡の時間を使わない）» の 2 つで、答えを ticket の Design-Decisions に書き戻す
5. **各判断** — [base.md](base.md)「承認者が必ず読む本文の構成」のとおり。
6. **返す** — 選択内容または承認文をそのまま返せる文章。

**なぜとゴールを根拠の側へ移さない。**選択肢を比較する基準そのものだからである。

`N = 0` のときの本文は、1〜3 に加えて **「この AC と Out-of-scope で実装に入ることを承認してほしい」という承認文・AC と Out-of-scope の全件・承認が間違いになる条件**、そして承認・修正指示・差し戻しを返すための文章とする。**「判断なし。AC の承認だけ」と明記する。**

## 本文と根拠に置くもの — これしか置かない〔手順 4〕

**本文は上の 5 節だけで、各節が持つのは次だけである。**

- この ticket が誰の何を可能にするか。Why と、上位の目的とのつながり（なぜ）。
- 承認対象となる AC 全件（ゴール）。
- ticket の書き手が決めておいた内容と、選ばなかった案（作り方の判断）。
- コストと利益、未確定の判断・選択肢・推奨と、承認文（決めること）。
- 承認者へ返してほしい答え（返す）。

**本文から 1 回の操作で開ける根拠に置くもの:**

- scope 外の内容と、外した理由。
- 計画を崩しうる既知のリスクと依存。
- ⚠ **PDH-ticket-review の間に変えた内容と理由** — **推奨や作り方の判断が起票時から反転しているなら、何がいつ反転したかを書く。復元できないなら「変更なし」と書かず、「記録が無いため復元できない」と書く。** 

**この 2 つのリストに無いものを本文へ置かない。**decision-board の書き手の裏取りの経緯、測定ログ、どの reviewer の finding で何を足したか、decision-board の数についての宣言は、どれも本文に置かない。置き場所の決め方は [final-check.md](final-check.md)「finding への応じ方」に従う。

**該当しない項目は、書かない。**「無し」「該当なし」の根拠を節で書かせない。書かないことで承認者が取り違える項目だけ、1 行で「無い」と書く。

## 選択肢と ticket を一対一にする〔手順 5・10〕

各選択肢について、選ばれた後の ticket を具体化する。

- ticket のどの節・どの AC が変わるか。件数が変わるなら変更後の数も示す。
- 変更後に、Why・AC・Design-Decisions・Out-of-scope が互いに矛盾しないか。
- 判断どうしの依存。別の判断の内容を変える判断を先に置く。**順序だけでなく後の判断の文面にも依存条件を書く。**
- 一括承認か、群ごとの承認かを明記する。

**承認された選択肢を ticket へ反映できない状態で decision-board を出さない。**

## decision-board を短くしてよい条件〔手順 0〕

**現状が壊れていて、どの直し方でも現状より良く、外から見える契約が変わらないなら、PDH-ticket-human-review の decision-board は短くしてよい。**本文は なぜ・ゴール（AC と Out-of-scope の全件）・承認文・返す だけにし、作り方の判断の比較と選択肢を省く。

- **短くしても省かないもの: AC と Out-of-scope の全件の提示、承認者の明示の回答、`AC-approved:` のハッシュの記録。**不具合を直すだけの ticket でも、実装前の AC と Out-of-scope の承認は省かない（`PDH-AGENTS.md`「PDH-flow」の承認の規則）。«直してから見せる» にしない
- **理由**: 承認者が選ぶものの無い判断を並べても、判断の記録にならない。承認者が決めるのは «この AC で直してよいか» だけである。
- **PDH-human-review の decision-board も省かない。**変更前と変更後の画面写真か出力の実例は、そこで見せる。
- ほかの理由（判断が少ない・選択肢が単純・急ぐ）では、PDH-ticket-human-review の decision-board を短くしない。
- 当たるかは ticket ごとに判定する。3 条件のうち 1 つでも怪しければ — とくに «外から見える契約が変わらない» に確信が持てなければ — **通常の decision-board を作る。**

## Open-Questions を差し戻さない〔手順 2〕

decision-board の書き手が決められる Open Question は decision-board の前に決める。各項目について採った案と理由、採らなかった案と採らなかった理由を示し、**承認者には覆す道だけを残す。**不可逆な決定、プロダクト価値、費用負担など承認者の権限に属する項目は、推奨を付けた判断として残す。
