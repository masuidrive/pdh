# decision-board の共通規則

承認の PDH-stage と媒体に依存しない共通規則である。手順と読む順は [SKILL.md](SKILL.md) にある。

## decision-board を作る前に〔手順 0〕

- **この承認の PDH-stage で、承認者が実際に決めることは何か。**先にそれを 1 行で書く。
- **その判断は、目で見て決めるものか。**画面の見た目・配置・操作の有無・出力の形を選ばせるなら、**画面写真か出力の実例が要る。誰がいつ撮るか（作るか）をここで決めてから書き始める。**

## 判断の分類〔手順 2〕

洗い出した未確定の項目に、まず 1 問を当てる。

> **その項目をどちらに決めても、ticket が約束するもの — Why の達成・AC・利用者ができること — は同じか。**

同じなら判断にしない。decision-board の書き手が決め、決めた理由を note に残す。上の問いで «同じではない» となった項目だけを、次の 3 つに分ける。**既定は「decision-board の書き手が測れる」とする。**

- **decision-board の書き手が測れる** — decision-board を書く前に測る。
- **実装しないと分からない** — 未測定と明記し、反証条件と停止条件を付ける。
- **承認者にしか決められない** — decision-board の判断にする。**不可逆な決定、プロダクトとしての価値判断、費用の負担、既知のリスクを残す決定、信頼境界を動かす変更**が該当する。**実装方式の差でも、出力・監視・運用手順が変わるなら承認者の判断にする。どれにも当たらない実装方式・命名・内部構造は、decision-board の書き手が決める。**

**見た目の差は、それだけでは «価値判断» にならない。**利用者ができること・費用・不可逆性のどれも変わらない見た目の差は、decision-board の書き手が決めて理由を note に残す。**判断にしてよいのは、その見た目の差で «誰が何をできるか» が変わるとき**（操作を隠して到達できなくなる、名前が契約として外部に出る）である。**「利用者が見る結果が違う」を判断化の根拠にしない。**

**decision-board の書き手がアクセス手段を持たず測定できない場合は、対象・範囲・取得項目・取得しない項目・保存先・削除時期を示して、必要な権限だけを依頼する。**依頼は `N` に数えず、**断られた場合に採る次善策**を併記する。

## 判断の数でモードを選ぶ〔手順 3〕

**`N` は «承認者が独立に返答できる指示の単位» の数である。**選択肢の数でも、成果物の数でも、未確定の項目の数でもない。**複数の未確定が «同じ 1 つの文・設定・値» を決めるなら、まとめて 1 件と数える。**まとめた場合は、推奨の組み合わせで完成した文面の全文と、別案を選んだときに完成する文面を decision-board に置く。**承認者に文章を合成させない。**

**モードを選ぶ前に、`N` を減らせないかを次の順に試す。**

1. **decision-board の書き手が決める側へ戻す**（上の 3 分類）。
2. **ticket を分ける。**別々の Why に属する判断が 1 枚に載っているなら、大きいのは decision-board ではなく ticket である。
3. **それでも残った数**でモードを選ぶ。**段階承認を «`N` を減らす手段» に使わない。**

### `N = 0` — 承認だけ

架空の選択肢を作らない。**何の承認を求めるかと、そのとき承認者が必ず読む本文は、PDH-stage 側のファイル（`ticket-gate.md` か `close-gate.md`）が定める。**承認も 1 枚のカードで出し、選択肢を「承認する / 修正して / 差し戻す」に固定する。判断ごとの集計と複数回答の同期は置かない。

```
### 承認 — <何の承認かを 1 行で>
承認文: <「この AC で実装に入ることを承認してほしい」の形の 1 文>
出来上がりの実例: <承認どおりに進んだ後に承認者が見るものを、画面写真か出力の実例で 1 つ以上。
  変更前と変更後を «同じ入力・同じ画角・同じ幅» で並べる。前の decision-board に貼った実例も再掲する>
ゴールの達成のされ方: <承認どおりに進むと、Why と AC がどう達成されるか。1 行、ticket の言葉で>
得るもの / 失うもの: <承認して得るものと、代償・リスク。失うものを必ず書く>
承認が間違いになる条件: <観測できる反証条件 / 優先条件>
実装を止める条件: <承認後に作業を止めて承認者へ戻す境界>

回答: 承認する / 修正して / 差し戻す （選ばせる媒体では «押せる» ようにする）
メモ: <修正指示・差し戻し理由は、ここが本体になる>
```

### `N = 1〜少数` — 個別判断

判断ごとに下の型を置く。複数あるなら、回答を失わず、未回答を明示し、選択結果をそのまま返せるようにする。

### `N` が多数 — グループ化して段階承認

**目安は 5 件以上。**判断を意味のまとまりに分け、依存する判断を先に並べ、グループごとに段階的に承認する。**後の判断内容が前の判断で変わる場合は、後の判断本文にも依存を明記する。**決定サマリーにはグループ名、今回承認する段階、未承認で残る段階を書く。

## 判断カードの型 — 承認か、別の指示か〔手順 5〕

返答は **承認か、別の指示か** の形にする。承認しない場合に進む具体的な道を用意する。**欄が埋まらない判断は、まだ比較が終わっていない。**

```
### T<n> — <決めることを 1 行・疑問形で>
背景: <この判断がどの Open Question・どの要望から来たか。Why / AC のどこに効くか>
推奨: <案の番号と名前 + 選ぶ理由 1 行。理由は Why / AC の言葉で。契約の全文は書かない>
推奨を覆す条件: <事実の判断なら観測できる反証条件 / 価値の判断なら優先条件>

選択肢 1（推奨）— <案の名前>
  内容: <何をするか。契約・仕様の全文はこの欄に 1 回だけ置く>
  ゴールの達成のされ方: <この案で Why / AC のどこが、どう達成されるか。1 行、ticket の言葉で>
  出来上がりの実例: <選んだ後に利用者が見るものを、同じ入力 1 件で示す画面写真か出力の実例>
  得るもの / 失うもの: <推奨案にも失うものを必ず書く>
  選んだときに起こること: <選んだときに変わるもの（ファイル・DB のデータ・他者が使う契約）と、選択後に成立する文面。次に承認者の判断が要る時点>
  選ばなかったときに起こること: <この案は捨てられるのか、後から選び直せるのか>

選択肢 2 — <別案。同じ 5 欄を同じ精度で。薄く書けば誘導になる>

回答: <承認者がそのまま返せる形>
```

- **設問の番号は、会話と ticket と同じ `T<n>` を使う**（`pdh-pm`「設問には番号を振る」）。⚠ **decision-board の中だけ別の番号にしない** — 承認者が «T2 の 3 で» と返せなくなる
- **推奨は 1 つ**に絞り、最初に置く。別案は、推奨を採らない場合の指示先として置く。**`N = 0` では別案を捏造しない**が、«承認する / 承認しない» の 2 つは選ばせ、コメント欄を置く。
- **ゴールの達成のされ方は、ticket の Why と AC の言葉で書く。**decision-board の中で発明した基準で選ばない。**全案でゴールの達成のされ方が同じなら、その判断は承認者の判断ではない。**
- **覆す条件は判断の種類で書き分ける。**事実で決まる判断は「この測定でこの値が出たら誤り」と観測できる形で、価値で決まる判断は「〇〇より△△を重く見るなら別案のほうがよい」と承認者が持っている基準で書く。**価値の判断に客観的な反証条件を求めない。**
- **コストを作業時間で書かない。**代わりに「選んだときに起こること」の**選んだときに変わるもの**（ファイル・DB のデータ・他者が使う契約）と**次に判断が要る時点**で書く。reviewer に作業時間の差を求められても採らず、採らなかったことと理由を成果物に残す。**「戻せる」とだけ書かない** — 不可逆な変更には、危険が大きいときの追加規則（[risk-overlay.md](risk-overlay.md)）を当てる。
- **decision-board の書き手が測れることを「先に測る案」として置かない。**

### 出来上がりの実例

**文章ではなく、画面写真か出力の実例で置く。**UI の変更なら実装前でも画面の試作を撮って選択肢の隣に埋め、API・CLI・データ・ログなら各案が返す実例の文面を置く。**承認された実例は「合意済みの画像」になり、実装後の確認で実物と突き合わせる。**

- **全案で同じ入力 1 件を使う。案ごとに結果が違うなら、案の数だけ実例を作る。**同じ入力・同じ画角・同じ幅でそろえ、**差が現れる部位を含めて**撮る（差が小さいならその事実も caption に書く）。
- **幅は «承認者がその画面を実際に見る幅» で撮る。**分からなければ承認者に聞く。
- **どの実例がどの案かを実例の隣に明記し**、変更前の実例も基準として 1 つ置く。**その実例がどの選択肢を選んだ姿かを、判断カードに列挙する。**
- **別の HTML を書き起こさない。アプリを起動し、提案する要素を実画面の DOM へ差し込んでから撮る。**変更前と変更後は、同じセッション・同じ幅・同じテーマで連続して撮る。
- **値は実データから採る。**採れない値は、例であることを実例の隣に書く。
- **「試作 — 未実装」を、画像の中・画像の隣・alt の 3 か所に書く。**画像の中の分は、画面の中身を隠さない角に、画像そのものへ描き入れる。
- **切り抜き・強調（annotation）で判断に効く部位を目立たせてよい（歓迎）。**ただし **decision-board のレイアウトそのものを詰めるのに時間をかけない** — 画面写真は判断の証拠であって見た目の作品ではない。差が見える最小の画面写真を撮ったら次へ進む。（**本体アプリの UI をユーザ依頼で撮って調整するのは別問題で、正当な実装作業。凝らないのは decision-board 自身の見た目のことだけ。**）**ブラウザが使える環境なら使って撮る**（無ければ、画面写真を撮れなかったことと理由を書き、承認者に画面で確かめてもらう。撮っていないのに «確認した» と書かない）。

## Acceptance Criteria の書き方〔手順 4〕

**AC は ticket を書く時点で承認者の言葉になっている。decision-board はそれをそのまま出す。**

- **読んで意味の取れない AC が来ても、decision-board で言い換えて辻褄を合わせない。**decision-board を書き進める前に ticket を直し、直した原文を出す。
- 文脈のために語を補うときも、約束を増減させない。**AC の群記号、番号、並び順を組み替えない。**補ったなら原文を隣に置く。末尾へまとめない。
- 緩い達成条件は、緩いことも判断材料として明記する。

## 合意済みの画像〔手順 1〕

要望、報告、回答案に**添付がある場合は decision-board を書く前に開く。**完成形の mockup、試作、変更前後の比較、仕様書、実データの標本、PDF、表計算、設計図、ログの抜粋は、合意した文章と同じ重さで扱う。

- **既定は成果物への埋め込み**とし、媒体が保持できない場合または機微性・容量が発行先の制約を超える場合だけ、アクセスが制御された保存先（ticket の一時領域・登録済みの発行先）へのリンクに切り替えて理由を書く。機微な情報を含む画像は inline にせず、[risk-overlay.md](risk-overlay.md) の秘匿版を使う。
- 画像が決める文言・色・画面の移り方・並び順を、画像の隣で文字にもする。
- **画像と異なる提案は、差異と理由を判断として明示する。黙って上書きしない。**
- 合意済みかを保存場所だけで推測しない。decision-board の書き手が確認できなければ承認者の判断にする。

## 承認者が必ず読む本文の構成〔手順 4〕

承認者が必ず読む本文（以下、本文）は、decision-board の書き手が調べた順ではなく、承認者が決める順に並べる。**本文のまとまりの数 = PDH-stage 側のファイルが定める固定部 + 判断の数 `N`**（スライドならスライドの枚数、文書なら節の数。スライドも節も無い媒体でも、このまとまりを見出しか段落として保つ）。

- **各判断**は、材料、推奨、代償、反証条件、別案、回答を同じ情報単位に置く。
- 本文の最後には**「返す」** — 選択内容または承認文をそのまま返せる文章 — を置き、**その文をどこへ返すのかを decision-board 自身に書く。**
- 実測の全表、測定ログ、選ばなかった案の詳細、scope 外、リスク、作業経緯は、本文から 1 回の操作で開ける根拠（閉じた `<details>`）または付録へ置く。**事実と、decision-board の書き手がその事実へ至った経緯を同じ段落に混ぜない。**

## 決定サマリー〔手順 4〕

冒頭に 1 画面相当で置く。**行数は決めない。**

1. **この作業は何のためか** — この decision-board が扱う作業が、**誰の何を変えるために始まったか**を 1 行で書く。**省かない。**
2. 今回決めること — 対象を症状か契約の名前で書く。判断の番号だけの行にしない。
3. 推奨 — Why / AC の言葉で、選ぶ理由を添えて。
4. 確かめた事実。
5. まだ確かめられないこと。
6. 承認後に実装を止める条件。

`N = 0` では 2 の答えを承認文にする（1 の目的は `N = 0` でも書く）。多数モードではグループと承認段階を示す。

## 読み手の仕事を増やさない〔手順 6〕

### 差分で語らない — Why から、毎回新しく書く

承認者が変更前の decision-board を持つと仮定しない。「何を変えたか」だけでなく、**承認する約束そのものを現在形で書く。ticket review 中に AC・推奨・作り方の判断を変えた事実は隠さず**、判断の枠ではなく検証用の注記として、変更内容と理由を示す。**AC 番号を単独で置かない** — 番号を出す場所で、意味または原文を同時に確認できるようにする。

**decision-board は毎回、Why から書き起こす。「前回からこう変わりました」を本文に置かない。**前の版との違い・今回直したところ・再発行の理由は、**閉じた `<details>` に入れて置く。**

**ただし «前回の回答» からの差分は、閉じた `<details>` に入れて必ず置く。**`<details>` の題（summary）は「前回の回答『<返ってきた指示>』に対して変えたこと」のように、**何に対する差分かが分かる形**にする。**基準は前の版ではなく前の回答である。**回答がまだ無い decision-board には、この `<details>` は要らない。

### 未確定の残し方

- **対象を数え、分類し、decision-board の書き手が片付けられなかった残りだけを判断に出す。**「ほかにもあるかもしれない」のまま広い受容を求めない。数える権限がなければ、必要なアクセスの安全範囲を具体化して依頼する。
- **調べれば分かる由来・判定方法・件数・過去の実測値は調べる。実装しないと分からない達成値や導入可否だけ**を未確定として開示し、反証条件と停止条件を付ける。**«推論» と書けば調べなくてよい、にしない。**

### 作業経緯は閉じた `<details>` に入れる

判断を変える結論と未測定の事実は本文に置く。実行条件・生ログ・一覧・commit・調査経緯は、検証できる形で付録へ置く。**見出しは「何を測ったか」ではなく、測定から分かった結論にする。**

**閉じた `<details>` に入れるとは、開く操作をしないと中身が見えない状態にすることである。**節を分けて後ろへ置くだけでは、そうならない。HTML なら閉じた `<details>`、Markdown なら折り畳み記法にする。

**削るのは «読む必要» であって «情報» ではない。**背景・ファイルの抜粋・測定の生データは、**閉じた `<details>` に入れて残す。**

## 数と断定の扱い〔手順 6〕

| 種類 | 例 | 求める精度 |
|---|---|---|
| **判断が変わる数** | 消える機能・落とす列・影響を受ける行数・直さなかった finding・確かめていないこと・上限や閾値 | **正確に。**下の検算はこの種類にだけ当てる |
| **規模の目安** | 差分の行数・変更ファイル数・テストの件数・レビューの件数・測った点の数 | **目安でよい** |

**数が判断の材料になっている decision-board では、冒頭で線を宣言する** —「この decision-board の数は目安である。正確に書いたのは «判断が変わる事実» のほうである」と書き、何を正確に書いたかを並べる。**争っている数が無い decision-board には書かない。**

**書かないもの** — **commit の SHA**（操作に使う名前で足りる。証拠の紐づけ用は note に置く）と、**decision-board を書く行為で変わる数**（note や progress の行数、この decision-board 自身を含む件数）。

**読み手が検算できる形にする。**

- 数を出したら、対象集合を数え直せる形にする。**「同型は n 箇所だけ」「該当なし」と書くときは、数え直しに使った検索条件も書く**（検索した語・対象範囲・除外したもの）。
- **推奨の根拠を 1 例だけにしない。**合計を出すか、合計未測定と書く。合計と内訳の関係が並列か直列かを書く。
- **断定には decision-board 内の証拠を付ける。**載せられなければ確度を下げ、**実測 / 推論 / 測定できていない**に分ける。**実証できない不存在は、実証できないと書く。ticket の主張を証拠として循環利用しない。**
- **測定値だけでなく、実際の実行条件**（設定、実行入口、資源配分、並列・直列の関係）**を書く。条件が異なる数値をそのまま比較しない。**

**通常の本文で個別に列挙する上限は 20 件とする。**超える集合は、分類ごとの件数、代表例、例外、最大影響を本文に置き、完全な manifest は付録または別の生成物へ置く。**本文の分類別件数を足すと総数を復元できる**形にする。

## 読み手を決める〔手順 6〕

decision-board の冒頭か承認表で、**誰が何を承認するか**を決める。

- 読み手の技術水準は上級エンジニアとする。SQL・schema・API の応答・設定ファイルの断片は、decision-board に貼って必要な説明を添えれば読める。**避けるのは技術的な内容ではなく、decision-board の外を見に行かせること。**
- **この ticket の内容、経緯、調査内容、過去の指示文は思い出していない前提にする。**
- repo 固有の語は、対象 repo に実在するかを検索して判定する。**勝手な略語を作らない。**
- **skill 内部の比喩や呼称を decision-board へ持ち出さない。**decision-board そのものを指すときは «decision-board» と書く。
- 規約を根拠にするときはファイル名だけを指さず、**判断に必要な規則本文をその場で引用または要約する。**

**量を削りたくなったら、まず「判断の分類」へ戻って `N` を減らせないかを見る。**文を削るのは、そのあとである。**量は «決めることの大きさ» に釣り合わせる。判定は行数ではなく、1 段落ずつ次の 1 問で行う。**

> **この段落を読まなくても、承認者は同じ判断を下せるか。**下せるなら本文から外し、閉じた `<details>` の根拠へ移すか消す。

**「あとで疑われたときのために」は本文に残す理由にならない。短くした結果、承認者が指示対象や根拠を復元するなら、それは短すぎである。**

## 危険が大きいときの追加規則を当てるか〔手順 0〕

**次のどれかに当たるなら、[risk-overlay.md](risk-overlay.md) を読んで基本規則を上書きしてから decision-board を作る。1 つも当たらないなら、このファイルは読まない。**

- **不可逆な変更** — 元に戻せない、または戻すのに同規模の作業が要る。**«migration があるか» では決めない** — 列や index を足すだけで既存の値を書き換えず、戻す操作が用意できるなら当たらない
- **機微な情報** — セキュリティ修正、脆弱性、secret、個人情報
- **承認者が複数、または repo 外**
- **hotfix** — 被害が続いており、遅延そのものが害になる
- **差分または生成集合が巨大** — 本文の列挙上限（20 件）を超える
- **公開された契約が変わらない** — docs・コメント・内部説明だけの変更

## 媒体を選ぶ〔手順 7〕

媒体は 2 つに分けて決める。**表現**（テキスト / Markdown / HTML）は decision-board に要るものから選び、**受け渡し経路**（どこへ出し、答えがどこへ戻るか）は起動側と project が定める（`pdh-pm`「起動側が受け渡し経路を指定したとき」）。受け渡し経路から表現を決めない — 受け渡し経路が許す上限の中で、decision-board に要る表現を選ぶ。

decision-board は 1 つにする。同じ中身を手で 2 つ書かない（HTML で作るなら HTML の decision-board が元で、Markdown はそこから `tools/to-markdown.sh` で作る）。**形式が Markdown でも、外部の共有先へ置けば外部発行である。**

| 表現 | 選ぶ基準 | 読む追加ファイル |
|---|---|---|
| **テキスト** | `N = 0` または 1、画像なし、回答を同じ会話ですぐ返せる | なし |
| **Markdown** | `N = 0`〜少数、表と引用が中心。折りたたみ・表・mermaid は表示先が描画する範囲で使う | なし |
| **HTML（文書+スライドの 1 枚トグル）** | 表・長い AC・画像・付録を 1 ページで突き合わせる、または狭い画面でも読ませる | [html.md](html.md) |

**複数の行に当てはまるなら、上から順に決める。**

1. **受け渡し経路の上限を超える表現は選べない。**上限が Markdown の受け渡し経路で HTML が要るなら、HTML を登録済みの発行先へ置き、**`tools/to-markdown.sh` で作った Markdown と URL を受け渡し経路へ出す。**置ける発行先が無ければ Markdown で組み、画面写真は撮れなかった（載せられなかった）ことと理由を書き、承認者に画面で確かめてもらう。
   - ⚠ **この «HTML を発行先へ置く» 道を選んだときだけの話である。**表現が Markdown で足りる decision-board は、はじめから Markdown で組んでよい（上の表の 2 行目）。⚠ **その場合は HTML を作らない。**
   - ⚠ **HTML を作ったなら、Markdown は書かない。HTML から作る。**手で書いたものが 2 つになると、片方だけ直したときに黙ってずれる（「decision-board は 1 つにする」は、このずれを防ぐための規則である）。**`tools/to-markdown.sh` で作った Markdown は HTML の decision-board から作った写しなので、«decision-board は 1 つにする» に反しない。**
   - 変換は見出し・段落・箇条書き・表・引用・`<details>`・mermaid・判定の `.tag`・選択肢を残し、**目次と回答 UI と svg の中身を落とす**（svg は «図は HTML の board にあります» に置き換わる）。⚠ **だから URL を必ず添える** — 図と画面写真は Markdown 側に無い。
   - ⚠ **HTML が見えない場面があるから両方出す**（ログインが要る・通信が無い・発行先が消えた）。**Markdown だけで判断が下せる状態を保つ。**
2. **機微な情報を含むなら**、外部へ発行しない受け渡し経路（ファイル / 会話）。
3. **表・長い AC・付録を突き合わせるなら**、1 ページで見比べられる文書。
4. **承認者が主に狭い画面で読むなら**、HTML（文書とスライドを 1 枚に）。
5. **どれも決め手にならないなら**、いちばん軽い表現（テキスト → Markdown → HTML）。

**HTML を選んだら、文書とスライドを 1 枚に持つ**（`--layout combined`。[html.md](html.md)「1 枚に文書とスライドを持つ」）。既定表示は文書で、スライドは上のトグルで開く。読む操作が上下スクロール 1 種類で済み判断どうしを見比べられるので主に読まれるのは文書、スライドは狭い画面のため。**回答は同じ判断 ID で両表示が共有する。**粒度は揃えなくてよい — スライドは決めるのに要る結論だけ、文書は根拠まで、でよい。ただしスライドで落とした材料が文書にあることは確かめる。判断・選択肢・AC・数値は**同じ 1 つ**を持つ。**内容を直したら 1 枚を作り直して再発行する。**読み手の媒体の好みは [reader-profile.md](reader-profile.md) 【媒体】に従う。多数モードでは、Markdown か HTML 文書の段階表を優先する。

**選択 UI を作れない表現でも、判断番号、推奨の選択文、自由記述欄、未回答表示を含む貼り戻し用テンプレート（貼り戻し文 = 回答をコピーして会話へ貼る文の雛形）を末尾に置く。`N = 0` でも «承認する / 承認しない» の 2 択とコメント欄を入れる。**貼り戻し文の直前に、**答えを戻す先**（受け渡し経路の «答えが戻る場所»。会話、issue コメント等）を 1 行で書く。

## 発行〔手順 9〕

**発行先は受け渡し経路が定める。**優先順は、起動側が `<Human-Agent-Interface>` で囲んで渡した指定 → `AGENTS.md` → 既定。既定は、ticket の dir の `boards/` へファイルで書いて commit し、会話に絶対 path を示す。ticket の一時領域（`tmp_dir`）と engine の scratchpad は git に残らないので、そこへ置くと note の待ち行の `発行先:` が、session が終わった後に指す先を失う。発行手段は engine の能力で選ぶ — **選択 UI を持つ HTML や登録済みの発行先が使えないことを理由に材料を省かない。**公開 URL や共有ツールへ新しく発行すると取り消せない場合は、試作やサンプルを発行する前に承認を得る。機微な情報には [risk-overlay.md](risk-overlay.md) の規則を優先する。

**発行したら、発行を記録する同じ commit で note の `## Checklist` へ待ち行を書き、手順 10 で回答を反映する同じ commit で `[x]` にする**（行の形は `PDH-AGENTS.md`「受け渡し経路」）。

## 完成検査〔手順 8〕

**decision-board を書き終えたら [final-check.md](final-check.md) を読み、final-check.md の 3 節（形・中身・判断）を実施する。**decision-board と、一緒に承認者へ渡すもの（`tools/to-markdown.sh` で作った Markdown・画面の試作・出力の実例）のすべてに行う。**«判断» の節は reviewer との往復が要るので、発行の直前ではなく書き終えた時点で始める。**
