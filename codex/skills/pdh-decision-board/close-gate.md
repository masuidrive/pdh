# `PDH-human-review` の decision-board

（ファイル名の `close-gate` は、PDH-human-review を指す古い呼び名である。リンクが参照するので名前は変えない。）

同じ主題について [base.md](base.md) と両方に規則があるときは、このファイルに従う。

- **この PDH-stage の承認文は «この達成で ticket を閉じてよいか» であり、AC の承認は求めない。既定は `N = 0`。**
- **この PDH-stage の固定部は 4 節**（決定サマリー / 出来上がりの実例 / AC ごとの達成 / 返す）。それ以外は、本文から開いて読む根拠として「返す」の後ろに置く。

承認者が持っている想定は、PDH-ticket-human-review で承認した ticket — Why・AC・作り方の判断・合意済みの画像 — である。**その想定と出来上がりを並べ、ずれを decision-board の書き手が先に全部見つけて、承認者にはずれを受け入れて閉じるか、差し戻すかだけを残す。**

**出荷して壊れうるもの — 保存されている形の変更と、外部から見える契約の変更 — は、それを含む ticket でだけ重点になる。**該当するかは手順 0 で判定し（判定は [ship-risk.md](ship-risk.md)「当たらないと判定する前に」）、当たれば ship-risk.md を読んで根拠に節を足す。当たらない ticket では、差分の規模の節の 1 行で終える。

## 書き始める前に — 実装が固まっているか

**decision-board を書き始めるのは、コードのレビューと本番の確認が終わってからにする。**

この規則の目的: 承認者が、実装の現状と矛盾しない達成状況・規模・検証結果で close を判断できること。

- **板を作った後に実装が変わったら、影響する検証を補い、達成・未確認・差分の規模・テスト結果が互いに矛盾しないようにする。**note の Checklist に `- [ ] close の板: 実装変更後の達成・未確認・規模・テスト結果が一致する（対象の板の path）` を足し、照合結果を progress に残して `[x]` にする。未了は close の `require_checklist` が数える。
- **PDH-human-review の直前に scope が増えた（AC が足された）ときは、decision-board を直す前に証拠を作り直す** — テスト、画面写真、本番の確認。

## 本文は 4 節 — 残りは根拠

このファイルの «本文» は、decision-board のうち**承認者が必ず読む部分**を指す。«節» は本文の節（スライドの媒体ならスライド 1 枚）を指す。

**本文 = 決定サマリー / 出来上がりの実例 / AC ごとの達成 / 返す、の 4 節 + 判断の数 `N`。**残りは**疑ったときに開く根拠**として「返す」の**後ろ**へ置き、根拠の先頭に「ここから先は、決めるために読む必要はない」と明記する。

- **決定サマリー** — [base.md](base.md) の 6 つの答え。**1 行目の「この作業は何のためか」は PDH-human-review の decision-board でも省かない** — **この ticket が何を作ろうとしていたか**を書く（**出荷しないで閉じる decision-board ほど要る**）。「確かめた事実」の行には AC の達成状況（全件達した / n 件が部分・未達）を、「まだ確かめられないこと」の行には直さなかった finding の件数と未確認の有無を書く。ship-risk が当たる ticket では、保存されている形と外部契約の変更の有無を 1 行ずつ足す。**PDH-ticket-human-review で承認した作り方の判断は、1 件ずつ «そのまま実装した / 変えた / 実装しなかった» のどれかを書く。**変えたなら変更後と «崩れた前提» を、実装しなかったならその理由を 1 行添える。**落ちた判断を «変更» の欄で拾おうとしない** — 1 件ずつ数えないと、空欄のまま通る。
- **出来上がりの実例** — 冒頭に「何ができるようになったか」を利用者の言葉で 1〜2 文（ticket の Why ではなく**終わった結果**。利用者の挙動が変わらない ticket では効果を発明せず、書けるものが無いなら「利用者から見た変化は無い」と書き、根拠で «無いことの根拠» を示す）。画面写真か出力の実例は [base.md](base.md) の型のとおり、変更前と変更後を同条件で並べる。**PDH-ticket-human-review で承認した合意済みの画像があれば、実物と並べて一致・不一致を書く。**
- **AC ごとの達成** — AC 全件に、**達した / 部分的に達した / 達していない / 未確認**と、**証拠を 1 行**（テストの名前、実行した操作、画面、出力。**「実装した」は証拠ではない**）。間接的にしか確かめていない、または別の経路の結果から推測しているなら、そう書く。**各 AC を確かめたデータの出所（実データ・seed・合成したデータ）も書く。利用者が触る振る舞いの AC を合成したデータだけで確かめているなら、PDH-human-review を止める。**証拠の生出力・手順は根拠の閉じた `<details>` に入れる。**AC の文面は ticket の最新版と一致させる。**実装中に AC が変わったなら、**変わったこと・理由・いつ承認されたか**を書く（**承認を得ずに変えた AC があるなら、それは PDH-human-review を止める理由である**）。
- **返す** — 承認文・得失・承認が間違いになる条件（観測できる症状）・回答 UI。ship-risk が当たる ticket では「戻せるか」の 1 行を足す。**どの ticket でも «merge した直後に、利用者がいま使えている機能を失うか（yes / no）» の 1 行を置く。yes なら、後続の作業で戻す予定があっても PDH-human-review を止める。****`N = 0` でも «承認する / 承認しない» を選ばせ、コメント欄を置く。**`N` があるなら AC ごとの達成と返すのあいだに置く。

**実装中に既定の値で進めた判断**（note の `## Open-Questions` のうち、PDH-implement 以降に足した行）は、承認者の想定とのずれの候補である。承認者が決めるものは «返す» の判断にし、PM が決めたものは根拠に決めた内容を並べる。

**根拠として必ず含める内容**（順不同）: **差分の規模** / **テストと動作確認**（出力そのもの）/ **直さなかった finding**（全件。件数を先に。**閉じた `<details>` に入れない**）/ **自分で確かめる手順** / **merge の後に人が手でやる作業**（本番の設定変更・terraform apply・secret の登録や入れ替え・外部サービスの設定など。無ければ «無い» と 1 行）/ ship-risk が当たる ticket だけ **保存されている形の変更**と**外部から見える契約の変更**。

根拠の節の中でも、**`<details>` の外に置く文は結論と判断が乗る事実だけ**にし、確認コマンド・生出力・数え上げ・手順詳細は閉じた `<details>` に入れる。

`pdh-verify`「未確認の出口」の対象は、「AC ごとの達成」に **未確認（権限・環境の制約の理由・足りない証拠）** と書き、未確認のまま閉じるかを承認者の判断にする。達成件数には数えない。証拠の補完は既定のままとし、本番の確認や利用者の実データを要する AC でも、worker が権限・環境で補えないと示した不足だけをこの出口へ渡す。未確認を検証済みとする理由に使わない。未確認のまま閉じる承認を得た後の AC の処置と承認 hash は、`pdh-pm`「承認の PDH-stage」の処理 5 に従って記録する。

## 差分の規模

**承認者が「どれくらいのものを承認するのか」を掴むために置く。評価を付けない。行数を正確に詰めない。**

- **変わったのは何か**を、まとまりごとに 1 行（app 本体 / テスト / DB の移行 / client / 設定 / 文書）。**DB の移行と、外部から見える契約に触るものは、必ず名指しする。**触らない ticket では、ここに「保存されている形と外部から見える契約に変更なし — <確かめた範囲>」と 1 行書いて終える。
- **どちらが多いか**（主に足したのか、主に消したのか）。**削除が追加を上回る ticket では、削除を先に書く。**
- **削除だけのファイル**と**新規ファイル**の有無。大きさを添えるなら**おおよその行数**でよい。
- **PDH の記録**（ticket・note・progress）と**自動生成されるもの**（型、SDK、lock ファイル、スナップショット）は、規模の話から外して読ませる。**ただし生成物のうち «外部から見える契約» を表すものは、「外部から見える契約の変更」の節から外さない。**

## テストと動作確認

**テストは独立した節を持つ。**要約に 1 行で混ぜない。スライドの媒体ではテスト専用のスライドを 1 枚作る。

節の先頭に置くのは **«全部通ったか» と «飛ばした・実行できなかったものがあるか»** である。**件数は目安でよいが、合否と «飛ばしたもの» は正確に書く。**

**2 種類のテストを «分けて» 示す。**合算した 1 つの数だけを出さない。**片方が無いなら «無い» と書く。「ticket-local-test は 0 件」と書く前に、スイート外で走らせた確認を数え直す。**

| 種類 | 何を指すか |
|---|---|
| **application-test** | スイートに常設され、**この ticket が閉じたあとも回り続ける**もの |
| **ticket-local-test** | この ticket の変更を確かめるためだけのもの。**close 後は回らない**（ドライラン、本番の smoke test、ブラウザでの確認） |

続けて、**スイート自身の要約行をそのまま貼る**（合否・skip・retry-pass の扱いは `.codex/agents/pdh-qa.toml`「結果の貼り方」に従う）。

- **環境エラーで test が 1 件も走らないまま失敗した区分**は、retry-pass に数えない — **「初回に実行不能だった区分」**として名前を出し、環境を直して**全区分を回し直し**、初回と再実行の**両方の要約を貼る**。
- **どの commit に対する結果か**を書く。あとで変更したなら、**その結果は無効**である。
- 最終 SHA のフルスイートを PR の CI に委ね、board を出す時点ではまだ走っていない運用では、要約行の代わりに `pdh-verify`「出力」の 3 点（委ねた先の workflow 名・対象の SHA・merge を止める必須のチェックの名前）を書く。⚠ **まだ走っていない run を成功と書かない**

**件数の下に、テストが «何を守っているか» を書く。**まとまりごとに分け、切り方はテストファイルではなく**守っている契約**で決める。各まとまりに置くのは、**何を守っているか**（1 文、契約の言葉で）、**破れたら何が起きるか**、application-test / ticket-local-test のどちらか。**まとまりごとの件数は要らない。数が多い場合も、代表例だけにして «ほか N 件» で済ませない** — まとまりの数を増やして分ける。

**わざと壊して落ちることを確かめたなら（変異・mutation）、その結果も件数で出す。落ちなかった契約があれば、それは «守られていない契約» である。**

## 直さなかった finding

**直さなかった finding を全件書く。**処置は 4 つ — **いま直す / 起票する（その ticket 名）/ 記録だけ残す / 棄却する（前提が違う）**。「後で起票する」は処置ではない。**PDH-human-review までに起票する。**

材料は progress の `### Findings` 表の 起票する / 記録だけ残す / 棄却する の行から作る。**作る前に、各行の処置がいまの判断と一致しているかを確かめる。**progress は追記だけなので、判断が変わっても元の行は書き換えない。表の後ろに、finding の識別子（表の `#` と見出しの巡、例: `PDH-review-1 #3`）を付けて «処置の変更: 起票する → いま直す — 理由» の行を追記する。decision-board には変更後の処置を書き、前の処置を添える。

**1 件ずつの一行理由が要るのは、直さなかった 3 つ。この 3 つは «判断が変わる数» なので、件数も中身も正確に書く。直さなかったものがゼロなら、ゼロと明記する。いま直したものは、件数すら要らない**（PDH-review を何巡回したかだけ書けば足りる）。

**同じ原因が他の場所にもありうるなら、その場所を数える。**「ほかにもあるかもしれない」のまま承認を求めない。

## 自分で確かめる手順

**承認者が自分で見るための手順**であって、decision-board の書き手が自分のために残した手順の記録ではない。

- 画面なら **URL と、押す場所・見るもの**。API なら **コマンドと、期待する status と中身**。
- 認証が要るなら**その取り方**（値そのものは書かない）。
- **agent 用の自動操作コマンドを、承認者の手順として出さない。**
- 手作業の準備が要るなら、**補助スクリプトを置いて path を渡す。**

## 判断の数

**`N` が増えるのは、decision-board の書き手が決められないものが残っているときだけ。**次が該当する。

- 直さなかった finding のうち、**起票するか記録だけ残すか**が、プロダクトの価値に関わる。
- **部分達成・未達の AC、または「未確認」を残したまま閉じるかどうか。**
- ship-risk が当たる ticket で、**後方非互換をいつ・誰に予告するか**、**不可逆な操作をいつ実行するか**（migration の本番適用、データの削除）。

**decision-board の書き手が決められることを判断にしない。**[base.md](base.md)「判断の分類」の最初の問いをそのまま当てる。

## 完成検査

**[final-check.md](final-check.md) の 3 節（形・中身・判断）をそのまま当てる。**reviewer への 7 問と依頼文もそのまま使う。**本文に «承認者が使わない情報» が無いかを、reviewer に聞かない** — 本文を 4 節に閉じ、そこに無いものを置かせないことが防ぐ。

ship-risk が当たる ticket では、[ship-risk.md](ship-risk.md) の問 9〜11 を足す。**問 9〜11 に finding が残っている状態で close を承認させない。**finding を直すか、**直さない理由を decision-board に書いて、それ自体を判断材料にする。**応じた後は、足した情報を本文の 4 節に入れるかを必ず判定し直す。
