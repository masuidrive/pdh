# close 前 gate（`PDH-human-review`）の判断ボード

同じ主題について [base.md](base.md) と両方に規則があるときは、この分冊に従う。

- **この gate の承認文は «この達成で ticket を閉じてよいか» であり、AC の承認は求めない。既定は `N = 0`。**
- **この gate の固定部は 4 面**（決定サマリー / 出来上がりの像 / AC ごとの達成 / 返す）。それ以外は裏付けとして「返す」の後ろに置く。

承認者が持っている想定は、実装前 gate で承認した ticket — Why・AC・解き方・合意済みの像 — である。**その想定と出来上がりを並べ、ずれを書き手が先に全部見つけて、承認者にはずれを受け入れて閉じるか、差し戻すかだけを残す。**

**出荷して壊れうるもの — 保存されている形の変更と、外部から見える契約の変更 — は、それを含む ticket でだけ重点になる。**該当するかは手順 0 で判定し（判定は [ship-risk.md](ship-risk.md)「当たらないと判定する前に」）、当たれば同じ分冊を読んで裏付けに節を足す。当たらない ticket では、差分の規模の節の 1 行で終える。

## 書き始める前に — 実装が固まっているか

**board は、コードレビューと受け入れ条件に必要な検証の結果を揃えてから仕上げる。**本番確認が条件に含まれていなければ、追加の必須条件にしない。

- **実装が変わったら、影響する検証を補い、board の事実を更新する** — 達成、未確認、差分の規模、テスト結果の相互矛盾を残さない。
- **gate の直前に scope が増えた（AC が足された）ときは、board を直す前に証拠を作り直す** — 追加条件に必要なテスト、画面の像、実行環境での確認。

## 主線は 4 面 — 残りは裏付け

**主線 = 決定サマリー / 出来上がりの像 / AC ごとの達成 / 返す、の 4 面 + 判断の数 `N`。**残りは**疑ったときに開く裏付け**として「返す」の**後ろ**へ置き、裏付けの先頭に「ここから先は、決めるために読む必要はない」と明記する。

- **決定サマリー** — [base.md](base.md) の 6 つの答え。**1 行目の「この作業は何のためか」は close 板でも省かない** — **この ticket が何を作ろうとしていたか**を書く（**出荷しないで閉じる板ほど要る**）。「確かめた事実」の行には AC の達成状況（全件達した / n 件が部分・未達）を、「まだ確かめられないこと」の行には直さなかった指摘の件数と未確認の有無を書く。ship-risk が当たる ticket では、保存されている形と外部契約の変更の有無を 1 行ずつ足す。**実装前 gate で承認した確定判断は、1 件ずつ «そのまま実装した / 変えた / 実装しなかった» のどれかを書く。**変えたなら変更後と «崩れた前提» を、実装しなかったならその理由を 1 行添える。**落ちた判断を «変更» の欄で拾おうとしない** — 1 件ずつ数えないと、空欄のまま通る。
- **出来上がりの像** — 冒頭に「何ができるようになったか」を利用者の言葉で 1〜2 文（ticket の Why ではなく**終わった結果**。利用者の挙動が変わらない ticket では効果を発明せず、書けるものが無いなら「利用者から見た変化は無い」と書き、裏付けで «無いことの根拠» を示す）。像そのものは [base.md](base.md) の型のとおり、変更前と変更後を同条件で並べる。**実装前 gate で承認した像（合意済みの画像）があれば、実物と並べて一致・不一致を書く。**
- **AC ごとの達成** — AC 全件に、**達した / 部分的に達した / 達していない**と、**証拠を 1 行**（テストの名前、実行した操作、画面、出力。**「実装した」は証拠ではない**）。間接的にしか確かめていない、または別の経路の結果から推測しているなら、そう書く。証拠の生出力・手順は裏付けへ畳む。**AC の文面は ticket の最新版と一致させる。**実装中に AC が変わったなら、**変わったこと・理由・いつ承認されたか**を書く（**承認を得ずに変えた AC があるなら、それは gate を止める理由である**）。
- **返す** — 承認文・得失・承認が間違いになる条件（観測できる症状）・回答 UI。ship-risk が当たる ticket では「戻せるか」の 1 行を足す。**`N = 0` でも «承認する / 承認しない» を選ばせ、コメント欄を置く。**`N` があるなら AC ごとの達成と返すのあいだに置く。

**裏付けとして必ず含める内容**（順不同）: **差分の規模** / **テストと動作確認**（出力そのもの）/ **直さなかった指摘**（全件。件数を先に。**畳まない**）/ **自分で確かめる手順** / ship-risk が当たる ticket だけ **保存されている形の変更**と**外部から見える契約の変更**。

裏付けの節の中でも、**主文は結論と判断が乗る事実だけ**にし、確認コマンド・生出力・数え上げ・手順詳細は畳む。

## 差分の規模

**承認者が「どれくらいのものを承認するのか」を掴むために置く。評価を付けない。行数を正確に詰めない。**

- **変わったのは何か**を、まとまりごとに 1 行（app 本体 / テスト / DB の移行 / client / 設定 / 文書）。**DB の移行と、外部から見える契約に触るものは、必ず名指しする。**触らない ticket では、ここに「保存されている形と外部から見える契約に変更なし — <確かめた範囲>」と 1 行書いて終える。
- **どちらが多いか**（主に足したのか、主に消したのか）。**削除が追加を上回る ticket では、削除を先に書く。**
- **削除だけのファイル**と**新規ファイル**の有無。大きさを添えるなら**おおよその行数**でよい。
- **書き手の作業記録**（ticket、note、作業ログ）と**自動生成されるもの**（型、SDK、lock ファイル、スナップショット）は、規模の話から外して読ませる。**ただし生成物のうち «外部から見える契約» を表すものは、「外部から見える契約の変更」の節から外さない。**

## テストと動作確認

**テストは独立した節を持つ。**要約に 1 行で混ぜない。面のある媒体ではテスト専用の面を作る。

節の先頭に置くのは **«全部通ったか» と «飛ばした・実行できなかったものがあるか»** である。**件数は目安でよいが、合否と «飛ばしたもの» は正確に書く。**

**2 種類のテストを «分けて» 示す。**合算した 1 つの数だけを出さない。**片方が無いなら «無い» と書く。「一時確認は 0 件」と書く前に、スイート外で走らせた確認を数え直す。**

| 種類 | 何を指すか |
|---|---|
| **application-test** | スイートに常設され、**この ticket が閉じたあとも回り続ける**もの |
| **ticket 固有の一時確認** | この ticket の変更を確かめるためだけのもの。**close 後は回らない**（ドライラン、本番の smoke test、ブラウザでの確認） |

続けて、**スイート自身の要約行をそのまま貼る**（合否・skip・retry-pass の扱いは `PDH-AGENTS.md`「Execution Model」に従う）。

- **環境エラーで test が 1 件も走らないまま失敗した区分**は、retry-pass に数えない — **「初回に実行不能だった区分」**として名前を出し、環境を直して**未実行区分と環境変更の影響を受ける区分を実行し**、初回と再実行の**両方の要約を貼る**。
- **どの版と環境に対する結果か**を書く。変更後の再利用は `PDH-AGENTS.md`「Verification」の鮮度条件に従い、記録だけの変更と実行条件の変更を区別する。

**件数の下に、テストが «何を守っているか» を書く。**まとまりごとに分け、切り方はテストファイルではなく**守っている契約**で決める。各まとまりに置くのは、**何を守っているか**（1 文、契約の言葉で）、**破れたら何が起きるか**、恒久 / 一時のどちらか。**まとまりごとの件数は要らない。数が多い場合も、代表例だけにして «ほか N 件» で畳まない** — まとまりの数を増やして分ける。

**わざと壊して落ちることを確かめたなら（変異・mutation）、その結果も件数で出す。落ちなかった契約があれば、それは «守られていない契約» である。**

## 直さなかった指摘

**直さなかった指摘を全件書く。**処置は 4 つ — **いま直した / 別 ticket にした（その ticket 名）/ 記録だけ残した / 退けた（前提が違う）**。「後で起票する」は処置ではない。**この gate までに起票する。**

材料は note の `### Findings` 表の 別 ticket / 記録だけ / 退けた の行から作る。**作る前に、各行の処置がいまの判断と一致しているかを確かめる。**判断が変わった行は処置を書き直し、前の処置を同じセルへ残す（例: `別 ticket → この ticket で修正`）。

**1 件ずつの一行理由が要るのは、直さなかった 3 つ。この 3 つは «判断が変わる数» なので、件数も中身も正確に書く。直さなかったものがゼロなら、ゼロと明記する。いま直したものは、件数すら要らない**（何巡回したかだけ書けば足りる）。

**同じ原因が他の場所にもありうるなら、その場所を数える。**「ほかにもあるかもしれない」のまま承認を求めない。

## 自分で確かめる手順

**承認者が自分で見るための手順**であって、書き手の作業ログではない。

- 画面なら **URL と、押す場所・見るもの**。API なら **コマンドと、期待する status と中身**。
- 認証が要るなら**その取り方**（値そのものは書かない）。
- **agent 用の自動操作コマンドを、承認者の手順として出さない。**
- 手作業の準備が要るなら、**補助スクリプトを置いて path を渡す。**

## 判断の数

**`N` が増えるのは、書き手が決められないものが残っているときだけ。**次が該当する。

- 直さなかった指摘のうち、**別 ticket にするか記録だけにするか**が、プロダクトの価値に関わる。
- **部分達成・未達の AC、または「未確認」を残したまま閉じるかどうか。**
- ship-risk が当たる ticket で、**後方非互換をいつ・誰に予告するか**、**不可逆な操作をいつ実行するか**（migration の本番適用、データの削除）。

**書き手が決められることを判断にしない。**[base.md](base.md)「判断の分類」の最初の篩をそのまま当てる。

## 完成検査

**形・文・判断の 3 層は [final-check.md](final-check.md) と同じ。**独立 reviewer への 7 問と依頼文もそのまま使う。**主線に «承認者が使わない情報» が無いかを、reviewer に聞かない** — 主線を 4 面に閉じ、そこに無いものを置かせないことが防ぐ。

ship-risk が当たる ticket では、[ship-risk.md](ship-risk.md) の問 9〜11 を足す。**問 9〜11 に指摘が残っている状態で close を承認させない。**指摘を直すか、**直さない理由を board に書いて、それ自体を判断材料にする。**応じた後は、引き込んだ情報が主線の 4 面に属するかを必ず引き直す。
