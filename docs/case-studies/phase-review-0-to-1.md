# 0→1 フェーズのレビュー運用事例

これは開発初期の運用事例であり、PDH の既定ルールでも、配布する skill でもない。ユーザが一般化して共有した報告をまとめた。元の実装・レビュー記録を独立に検証した評価結果ではなく、製品名や内部の識別情報は掲載しない。

## 誰が、いつ、何のために読むか

[追試 Issue #51](https://github.com/masuidrive/pdh/issues/51) の検証計画を作る前に、同 Issue のリード（この事例を受け取った Codex）が読む。担当が変わる場合は、後任へこの作業も引き継ぐ。

- [ ] 計画対象の版の PDH と照合し、既にある規則と新しい候補を分ける。
- [ ] 各候補について「採用候補・採らない・判断保留」と理由を #51 に記録する。
- [ ] 追試へ組み込む必要があるかを判断する。変更するなら別条件として計画に明記し、#51 の開始条件を満たしてから実行する。

この文書の追加は、新しいレビュー規則の採用やモデル実行の許可ではない。判断結果は #51 に残し、この事例本文を後から成功例に書き換えない。

## 報告された運用

役割は次のように分かれていた。モデル名は報告時の構成例であり、PDH の推奨設定ではない。

| 役割 | 構成例 | 行うことと権限 |
|---|---|---|
| 実装役 | sol | 実装・テスト・報告。コミットしない |
| レビュー役 | astra | 読み取り専用 sandbox で静的レビュー。編集・コミット・ネットワークアクセス・テスト実行をしない |
| まとめ役 | Claude | 実装役の報告をそのまま採用せず、自分の環境で検査と全テストを実行。通過後にレビューへ渡し、指摘の処置を決めてコミットする |

レビューは変更のたびではなく、フェーズまたは層が仕上がった時点で行った。読む順番と差分の範囲を依頼文で指定し、重点を3〜4観点に絞った。

- 次の段階を妨げる重大な欠陥。送信不能、消失、取り違え、二重送信、復帰しない停止、AI 接続先への大量アクセスなど。疑わしい経路を具体的に指定した。
- 層の境界違反。担当外の判断や他の層の DB へのアクセスなど。
- 重複と大きさ。AI が修正時に読む範囲が過大になっていないか。

出力は「次へ進めるか」「必ず直すもの」「後回しでよいもの」に分けた。必須の指摘にはファイルと行、具体的な発生場面と結果、修正案を求め、まとめ役が重大さを判断した。後回しの項目は1行ずつ記録した。

必須の修正は実装役へまとめて渡し、欠けた試験の追加も修正に含めた。後回しの項目は既知の問題の一覧へ残し、そのフェーズでは直さなかった。ただし層の境界違反は、後で直す負担を考えて修正に含める場合があった。

2回目は、前回の必須指摘の解消を根拠付きの表で確認し、修正が新しく持ち込んだ重大な欠陥を調べた。全体の探索はやり直さなかった。結果はフェーズごとの `review-N.md` に残し、修正 commit と解消を確認したレビューを結び付けた。容量不足による失敗には、5分間隔・最大3回の再試行を設けていた。

## 報告された結果と限界

以前は25回の往復があったのに対し、この運用では3つのフェーズがそれぞれ初回と修正確認の2回で通ったという報告がある。変更量・課題・モデル条件を揃えた対照比較ではないため、往復の減少をこの手法の効果と断定できない。

修正範囲の外の退行は見逃しやすい。まとめ役の全テストで補っていたが、試験がない経路まで保証できるわけではない。静的レビューでは実行時だけの問題を判定できず、上流との接続もモックでしか確認していなかった。

## PDH と照合するときの論点

| 事例から得る候補 | 採用前に分けて判断すること |
|---|---|
| まとめ役が検証した証拠をレビュー役へ渡す | 同じ版の差分・試験結果を渡せるか。未コミットの変更も識別できるか |
| 読み取り専用レビューを試験の妥当性や境界へ集中させる | 静的には決められない指摘を、まとめ役への確認依頼として返せるか |
| 重点経路と具体的な発生条件を指定する | AC 未達や契約違反を、重点外という理由で見逃さないか |
| 修正後の確認範囲を絞る | 修正が以前の証拠を無効にする経路まで含め、境界や共通処理の変更時は必要な範囲を広げられるか |

「critical だけ直す」「必ず2回で終える」は PDH へそのまま移さない。ticket が持ち込んだ退行、AC 未達、契約違反は重大度だけで免除できない。実在する欠陥を後回しにする場合は、[PR #53](https://github.com/masuidrive/pdh/pull/53) の起票・集約と再発見の仕組みに照合する。層の境界の変更も、承認された範囲と契約を越えて「ついでに直す」根拠にはしない。

モデル構成と容量不足時の再試行間隔は、この事例の実行条件として残す。共通の既定値にはしない。新しい評価が必要な場合も、生成・採点・途中確認を含む費用と、何の判断を変えるために測るかを #51 で先に決める。
