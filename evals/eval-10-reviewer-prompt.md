# eval-10 — 依頼文は、欠落のある板と無い板を撃ち分けるか

これは board を書く側ではなく、**[final-check.md](../skills/pdh-decision-board/final-check.md) の「依頼文」と 7 問そのもの**を測る。

⚠ **壊した板だけを渡しても判別しない。**壊した板を渡せば reviewer は「決められない」と返す。どんな依頼文でも同じ答えが返るので、依頼文が効いているかは分からない。**要るのはペアである** — 通るはずの板で「決められる」が返り、1 か所だけ壊した板で「決められない」＋欠落の名指しが返って、初めて撃ち分けていると言える。

## 読ませるもの

reviewer には **board だけ**を渡す。skill は読ませない。依頼文は `final-check.md`「依頼文」の全文（立場の 3 行 + 問 1〜7 + 「文」の層の各項目）。

## 入力

[fixtures/reviewer-prompt/](fixtures/reviewer-prompt/) の 5 枚。題材は「監査ログの保持期間」（判断 1 件 + AC 3 件）。

| 板 | 入れた欠落 | 拾うはずの問い |
|---|---|---|
| `v0-clean.md` | 無し（通る板） | — |
| `v1-no-tradeoffs.md` | 各案の得失を消し、推奨だけ残す | 問 2 |
| `v2-option-offboard.md` | 選択肢 B の内容を主線から抜き、裏付け参照にする | 問 4 |
| `v3-no-wrongness-condition.md` | 「承認が間違いになる条件」を全部消す | 問 1 |
| `v4-punts-to-approver.md` | 書き手が数えられる行数を承認者へ振り、実測を全部落とす | 問 6 |

## タスク

各板に依頼文を当てて回す。あわせて **ablation** として、立場の 3 行（承認者として読む / 知っているのは一般的な技術語と board 本文の語だけ / board 以外は見ない）を外した「問 7 問だけ」でも回し、答えが変わるかを見る。

## expected_behavior

- [ ] `v0` で「決められる」が返る（欠落を作っていない板を落とさない）
- [ ] `v1` `v2` `v3` `v4` で「決められない」が返る
- [ ] 各板で、詰まった場所として**入れた欠落そのもの**が名指しされる（別の箇所を挙げて偶然落とす形にしない）
- [ ] ablation（立場の 3 行なし）では、少なくとも 1 枚で判定が甘くなる — 同じ欠落を見つけても「決められる」側へ倒れる

## 実行記録

- 2026-09-01 — **model / effort を 5 構成へ広げ、対照群の欠陥を 3 度目に見つけ、依頼文を 1 行直した。**
  - 構成: claude opus / claude sonnet / codex `gpt-5.6-sol` high / 同 max / `gpt-5.6-luna` max。5 枚 × 5 構成。
  - **v1〜v4 は opus と codex 3 構成が全件、入れた欠落を名指しで落とした。**⚠ **sonnet だけが `v1` を «決められる» で通した** — B の比較が無いことに問 2・問 3 では触れながら、問 1 の判定は通している。
  - ⚠ **`v0-clean` を、sonnet 以外の 4 構成が落とした。理由が 2 系統に割れた。**opus（2 個体が独立に）は **board 内の数の矛盾** —「1 年で 2.4 億行まで増え」と「13 か月より古い行が 1.9 億行」「毎月 2,000 万行増」は両立しない。codex 3 構成は **承認者への委ね** —「その規程は承認者のほうが把握している」を、立場 3 行の «知っているのは一般的な技術語と board 本文の語だけ» に照らして «確認できていない» と扱う。
  - ⚠ **sonnet の «決められる» は精度ではなく見落としだった。**opus が見つけた矛盾を sonnet は「数値の内部整合性は取れている」と通している（v2 でも同じ）。**«v0 を通すこと» だけを合格条件にすると、欠陥を見落とす読み手が最高得点を取る。**採点は «v0 を通し、かつ v1〜v4 を名指しで落とす» の両方で見る。
  - **対照群を直した**（5 枚共通の base）。数の矛盾（運用開始から 5 年 / 毎月 400 万行 / 3 年後に 60 分）、B の «40 分から 6 分縮んだだけ» の二義、容量 780GB→160GB の出所、«下の SQL» の指す先。**v0 の欠陥はこれで 3 回目**（2026-08-26 に 1 件、08-30 に 2 件）。
  - **直した後、opus と codex の判定理由が一致した** — どちらも «委ね» だけを残して落とす。opus の診断が正確だった: 「«承認が間違いになる条件» 自体は board に書かれている。詰まっているのは、条件が書かれたうえで、その充足確認が承認者側にしか無い情報に依存している点。承認者が 2 点を確認できれば、その場で A を選べる」。
  - **依頼文の立場 3 行へ 1 行足した** — «board が «承認者が把握している» と名指しで委ねた事実は、あなたが持っているものとして扱う。名指しされていない未確認は、これまでどおり «決められない» の理由になる»。⚠ **知識量で線を引くのをやめ、«明示的に委ねたか» で引く。**知識量は連続量なので engine ごとに割れる（実際に割れた）。委ねの乱発は問 6（書き手が自分で調べられた項目を残していないか）が既に拾う。
  - **追加後: `sol/high` で `v0` が «決められる»**（「承認者が把握していると明記された 2 点は、承認者として照合済みとして扱う」）。**`v1`〜`v4` は落ちたまま**で、副作用は出ていない。
  - ⚠ **この文言は判断ボード側だけに閉じる。**AC 読み手（`pdh-verifying`）の «書かれていない前提を埋めない» はそのままが正しい — AC には委ねを書く場所が無い。
