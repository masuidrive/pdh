# evals — 判断ボード skill を直すときの資料

`eval-*.md` が評価シナリオ、[fixtures/](fixtures/) がシナリオが渡す入力の実体、[examples.md](examples.md) が規則の由来になった日付つきの事故と実測値である。**どちらも配布物ではない。**特定時点の制約を skill の実行者に持たせるとゴールから遠ざかるので、規則ファイルには現在形の規則だけを書き、由来はここに置く。

**この skill への規則の追加・削除は、ここの評価で測ってから行う**（Anthropic 「Skill authoring best practices」の evaluation-driven development）。事故が起きたら、散文の規則を足す前に、まずその事故をシナリオとしてここへ再現する。

各シナリオは実際に起きた失敗の再現である。入力とタスクを fresh agent （この repo では claude opus と codex gpt-5.6-sol xhigh の両方）へ渡し、出力を expected_behavior と突き合わせる。

path は repo root からの相対である。**この `evals/` は配布物ではない** — 配布先は skill の規則を変えないので、回す相手がいない（`scripts/` と同じ扱い）。

## 実行方法

1. fresh agent に `SKILL.md`（と、シナリオが指定する分冊）を読ませる
2. シナリオの「入力」と「タスク」だけを渡す。expected_behavior は渡さない
   - ⚠ **`evals/` をまるごと «開くな» と指示しない。**シナリオが [fixtures/](fixtures/) を指す場合、それは評価基準ではなく**入力そのもの**である。禁じると agent は fixture を自作し、**欠落の位置を知っている状態で採点する**ことになる。禁じるのは `eval-*.md` だけにして、`fixtures/` は渡す
   - 版の違いを比べるときは、**両版が同じ規則群を読んでいるか**を確認する。シナリオが `git show <commit>:<path>` のように歴史的なファイルを指す場合、片方だけがそれを読むと比較が成立しない
3. 出力を expected_behavior の各項目で PASS / FAIL 判定する
4. FAIL した項目だけが skill を直す理由になる。直したら再実行する

baseline（skill 無しで同じタスクを解かせた結果）と比べると、その規則が実際に挙動を変えているかが分かる。変えていない規則は削る候補である。

⚠ **仕込んだ欠落に、それ自体の被害を持たせない。**被害が大きいと、測りたい経路（例: 全件を数えたか）を通らなくても被害の側から見つかり、baseline が満点を取って判別しない。eval-12 の初版がこれで、D3 の未実装に「契約 2 社が 429 を受ける」を持たせていた。**欠落が静かなときにだけ、«数えたか» を測れる。**

⚠ eval-3 の題材は、SKILL.md「判断カードの型」の良例/悪例と同じ実失敗である。agent が例を照合するだけで通れるため、汎化の検査としては弱い。別の題材で同じ失敗形を試すシナリオを足すときは、skill 本文に例が無いものを選ぶ。

⚠ **skill の description を測るときは «当てる» と «当ててはいけない» の対を作る。**当たる依頼だけを試すと、何にでも反応する description と区別が付かない。**1 問の結果で «外れた» と判定しない** — `pdh-coding` を 1 問で欠陥と断定したが、6 問へ広げたら 6/6 正解で、外れて見えた 1 問は別 skill の起動語が正しく効いていただけだった。⚠ **測れるのは «description が読み手に正しい 1 つを選ばせるか» までで、実機の発火機構そのものではない。**
