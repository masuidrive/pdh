# 日付つき事故・実測
このファイルは、判断ボード規則の根拠になった事故と実測を保存する事例集である。通常は読まず、規則の理由、既定値の由来、過去の再発形を調べるときだけ読む。

## 2026-08-12 — 調査前の推奨は、札を付けても正しくならない

サンプル board は「8 分に届く」を見込みのまま示し、別案へ「先に測らせる — 約 30 分」を置いた。 board 自身が 30 分で測れると書いていたため、これは実装後にしか分からない不確実性ではなかった。**測れる項目は board の前に測り、測定を承認者への選択肢にしない**という規則になった。

同じ board は「削除対象 7 件が規則の不備から生まれた」を `推論` とした。`git log -S` で追うと、 7 件のうち 4 件はその規則より前に存在し、推奨の中心が部分的に否定された。`推論` のラベルは調査を省く許可ではなく、調査しても実証できない主張だけに使う。

## 2026-08-12 — 数は集合と条件を持たないと誤読される

外部 reviewer は、次の不整合を指摘した。

- 「7 件を削除・統合する」と書いたが、7 件を 1 件ずつ復元できなかった。
- 1 件が準備だけで `5.12 秒`かかる例を、全体の見積もりとして読める位置に置いた。
- 全体 `17.5 分`と、複数の内訳を並べたが、並列か直列かを書かなかった。
- `10 分 / 8 分 / 5 分`の目標に、各処置の寄与を積み上げなかった。
- `15 分 08 秒`は別処理の並走中、`8 分以下`は単独実行であり、比較条件が違った。
- `171±2`という AC は、対象 7 件を処理しなくても数値だけ満たせる緩い条件だった。

この事故から、集合の再集計、同条件比較、合計と内訳の関係、目標の積み上げ、緩い AC の明示を別々に検査するようになった。

## 2026-08-12 — reviewer 用の抽出が board の欠陥を作った

HTML をテキストへ抽出して reviewer に渡したところ、抽出処理が強調を落とした。reviewer は「拾い読みで筋が通らない」を 6 回連続で返したが、どこまでが元の board の欠陥かを分離できなかった。**承認者へ渡す形を加工せず reviewer へ渡す**という規則になった。

## 2026-08-12 — 狭い画面の空白と横 overflow

sticky 見出しの背景を擬似要素の `inset: 0 -50vw` で広げた HTML 文書を Galaxy Z Fold 7 で開くと、幅 `380px` の条件で `scrollWidth = 527`、`clientWidth = 365` になった。擬似要素の絶対配置が scroll 範囲へ加算されていた。`box-shadow` へ変えると配置範囲を増やさず背景を伸ばせた。

当時は文書を `344px` から `1600px` まで測った。汎用 renderer では特定端末名を規則にせず、プロジェクトの最小・最大 viewport を使う。`380px` は、設定がないときの実測由来の狭幅目安として残した。

## 2026-08-13 — 実際の実行条件で推奨が反転した

テスト所要を 1 本ずつ単独で測ると、絞り込みは `82 秒`の損に見えた。board は 9 周のあいだ「短縮は並列実行から出る。絞り込みからは出ない」とした。しかし実際の `test-all.sh` は 2 本を同時実行していた。同じ形で測ると絞り込みは `85 秒`の得になり、推奨が反転した。

この repo では測定条件を「2 本同時・各 7 並列 — 実行入口と同じ形」のように書く必要があった。 `test-all.sh` や PostgreSQL は汎用規則ではなく、この事例の具体名として残す。

## 2026-08-14 — 1 面に収まる検査が 3 回とも安全側へ誤った

最初は `.p { min-height: 100dvh }` に `scrollHeight > clientHeight` を使い、内容と一緒に clientHeight が伸びたため 7 周のあいだ overflow 0 と報告した。測り直すと 23 面中 18 面が viewport より高く、最大 `1.67 倍`だった。

次に `height: 100dvh` へ変えたが、flex child の `offsetHeight` が面高へ丸められた。内容が `1982px`ある面で `offsetHeight = 844px`を返し、10 項目中 4 項目目以降が切れていた。

さらに高さだけを比較すると、内容全体が下へずれていても合格した。`transform-origin: center center` では、`390 × 630` の面で内容が `172px`下へはみ出し、選択肢とメモ欄が画面外になった。

`scrollHeight` と下 padding、`center top`、上下端の位置比較、故意に壊す probe を組み合わせる規則になった。情報を削らず面を 34 面へ分けると、基準超過は 1 面まで減った。

## 2026-08-19 — close board の初実走で踏んだ 4 つ（ticket 260819-072511）

close 前 gate の board を初めて実走させ、独立 reviewer に 10 周かけて出した。うち 4 つは規則にできた。

- **復旧元を「main」と書いた** — merge 後の main は移行後を指すため、出荷後には成立しない復旧手順だった（r3 で検出）。固定 commit ID へ書き換え、ドライランで確認してから直った。机上の 2 案（一括 revert / main への checkout）は両方とも実行すると成立しなかった。
- **「戻せる」を 1 つの文で書いた** — 実装ファイル・作業記録・発行済み文書で戻る/戻らないが違うのに、まとめて「全部戻る」と書いて 3 周往復した。
- **初回 9/14 → 再実行 14/14 を「retry-pass 0 件」と要約した** — 依存欠落で 5 区分が 0 秒 FAIL（test 未実行）だった事実と食い違って見え、独自定義の語だと 2 周指摘された。両方の要約を貼り「初回に実行不能だった区分」と書いて通った。
- **出来上がりの像に、条件の違う既存の 2 枚を流用した** — 切り取りも幅も違う v1/v2 比較は「CSS の差」の証拠にならないと指摘され（r4）、同じ markup・同じ幅・同じ切り取りで撮り直した。判断カード側には既にあった「同じ入力・同じ画角・同じ幅」の規則を、承認カードが参照していなかった。

もう 1 つ、規則ではなく運用の事故: **旧版の終了条件（2 周連続・文の検査ゼロ）が会話の context に残っていて、それに従って 10 周回した。**現行の final-check（「3 周『決められる』が続いたら打ち切り」）なら 5〜7 周で出せていた。skill を読み直さず記憶の規則で回すと、直した側の規則が効かない。

## 2026-08-26 — 問 8 を足した後も、同じ形で主線が太った

判断 1 件（スマホで板の右が切れて押せないのを直す）の close 板で、reviewer の 4 巡がいずれも「足りない項目を名指しせよ」を返し、書き手がそのたびに主線へ書き足した。承認者が 3 択を押す手前に、裏取りの突合表・退けた案 2 つと screenshot・「この board の数は実測値である」の宣言が並んだ。**2026-08-20 の対策（close gate の問 8、「指摘への応じ方」）が入った後の再発である。**書き手の自己申告は「規則は足りていた。当てなかっただけ」だった。
