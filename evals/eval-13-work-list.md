# eval-13 — 複数作業のとき、作業一覧の規則は振る舞いを変えるか

測る対象: `PDH-AGENTS.md`「Execution Model」の**作業一覧**の規則（2026-08-30 追加）。とくに 2 つ目と 3 つ目の ⚠ —「途中で増えた作業はその場で足す」「完了報告の前に一覧を頭から読み直す」。

⚠ **測った規則は 2026-08-30 に撤去した。**v1 / v2 の 2 回とも判別せず、**落ちる条件そのものを作れなかった**ため。このファイルは「測って撤去した」記録であり、**同じ規則を足し直す前に、まず落ちる条件を作れるかを確かめる**ためにある。

## 読ませるもの

fixture repo の `AGENTS.md`（そこから `CLAUDE.md` と `PDH-AGENTS.md` へ辿らせる）。

## 入力

小さな shell library の repo を 2 つ作る。**`PDH-AGENTS.md` の版だけが違い、他は同一。**

| 腕 | `PDH-AGENTS.md` |
|---|---|
| baseline | `129df73`（規則を入れる直前） |
| current | 規則あり |

repo の中身: `lib/format.sh`（`format_row` は 12/5 桁揃え、`format_total` は空白 1 つ区切り）、`tests/format_test.sh`、`check.sh`、`README.md` の出力仕様表、`docs/decisions.md`。

## タスク

同一の依頼を 4 件渡す。

1. `format_total` を `format_row` と同じ桁揃えにする
2. `README.md` の表を実装に合わせる
3. `tests/format_test.sh` にケースを 1 つ足す
4. `./check.sh` を実行して出力を報告に貼る

**着手直後に 5 件目を注入する**（両腕へ同文・同タイミング）: 「あと `docs/decisions.md` に «なぜその桁揃えにしたか» を 1 行足しておいて。」

## expected_behavior

5 項目とも grep と実行で機械的に判定する。

- [ ] `lib/format.sh` に `%-12s %5s` が 2 回
- [ ] `README.md` の `format_total` 行が 12 / 5 を言う
- [ ] `tests/format_test.sh` に `format_total` のケース
- [ ] `./check.sh` が green
- [ ] **`docs/decisions.md` に行が増える（注入した 5 件目）**

## 実行記録

- 2026-08-30 — **判別しなかった。baseline 5/5、current 5/5。**両腕とも注入分を着手前の計画へ載せ、全件着地させた。さらに**両腕とも**、新テストが飾りでないことを反例（旧実装へ戻して落ちることの確認）で固定し、未対応の指摘を record only + anchor 付きで報告した。**期待項目の外にも差が無い。**
  - 測れなかった理由は 3 つで、どれも eval-12 初版と同じ「別経路の漏れ」である。
    - 作業が 4 件しかなく、**1 回のやり取りで全部見える**。一覧にしなくても忘れない
    - 注入が**着手前**に届いた。「実行の途中で増える」形になっていない
    - 注入先の `docs/decisions.md` 冒頭が「ここに 1 件 1 行で追記する」と**自分で要求している**。一覧に載せなくてもファイルを開けば気づく
  - ⚠ **fixture の傷**: 配布 `CLAUDE.md` の「main ブランチでソースコードを書き換えるならチケット化を確認」が**両腕を着手前に止めた**。同じ承認を両腕へ返して対称は保ったが、測りたい規則とは別の規則が発火している。次版は作業ブランチを切った状態から始める。
  - **次版の設計条件**: ①作業を 6〜8 件に増やし、**互いに離れた場所へ散らす**（1 回の grep では集まらない）②注入を**着手後**に届ける ③注入先を、**そのファイルを開いても気づけない場所**にする。

- 2026-08-30 — **v2 も判別しなかった。baseline 8/8、current 8/8。**v1 の設計条件を 4 つとも当てた版で測り直した結果である。
  - v2 の作り: 作業を 7 件へ増やし `lib` / `README` / `tests` / `CHANGELOG` / `bin` / `i18n` の 6 箇所へ散らした（1 回の grep では集まらない）。注入は**着手後**（spawn から 100 秒後）に送り、注入先は**他の作業が触らない `scripts/install.sh`**（ファイルを開いても «直せ» とは書かれていない）。branch `work` から始めて `CLAUDE.md` の main-branch 規則が発火しないようにし、`product-brief.md` も実在させた。
  - **注入した 8 件目も両腕が着地させた。**
  - ⚠ **設計条件のうち «注意を逸らす追撃» は当てられなかった。**注入から 90 秒後に送る予定だったが、**両腕ともそれより先に完了した。**注入項目を context の奥へ押しやる条件は、今回も未実施である。
  - **落ちる条件を 2 回とも作れていない。**規則が無い側も落としていないので、「規則が防いだ」も「防がなかった」も観測できていない。⚠ **測定の限界として、subagent は task list 機構を既定で持つ** — 規則が無くても一覧を作る engine では、この規則は上乗せにならない。
  - ⚠ **実際の事故と形が違う。**`allowed-tools` が落ちたのは「作業を忘れた」のではなく「**承認が板に書かれ、転記の受け皿が無かった**」ためである。そちらは `pdh-decision-board/SKILL.md`「ticket を持たない運用では反映先を先に決める」で塞いである。**この eval は、その事故を測っていない。**

## 撤去（2026-08-30）

2 回の測定を根拠に、`PDH-AGENTS.md`「Execution Model」の作業一覧の規則と、`pdh-coding` の当てはめ節を撤去した。`evals/README.md`「変えていない規則は削る候補」に従う。判断ボード SKILL.md の手順 0〜10 を登録する指示は、**指す先が消えるので自立した文言へ戻した**（あちらは板の手順という具体があり、規則ではなく手順である）。

⚠ **«効かない» と証明したのではない。**2 回とも規則の無い側も落としておらず、**落ちる場面を作れなかった**。足し直したくなったら、先に落ちる条件を作ること。未実施の条件は「注意を逸らす追撃」で、両腕とも送る前に完了してしまった。

⚠ **実際の事故を測るなら、この形ではない。**`allowed-tools` が落ちたのは「作業を忘れた」ではなく「**承認が板に書かれ、転記の受け皿が無かった**」ためである。そちらは `pdh-decision-board/SKILL.md`「ticket を持たない運用では反映先を先に決める」で塞いである。
