達成すること

01 / INTENT

目的と合意を保つ

依頼の背景、対象者、受け入れ条件、確定した判断を実装まで引き継ぎます。担当や会話が変わっても、合意を勝手に変えずに進められることを確かめます。

02 / EXECUTION

必要な作業を実行する

調査、実装、レビュー、検証について、担当、入力、利用できる手段、完了条件を揃えます。指示が具体的な行動につながるかを実行ログで確かめます。

03 / DECISION

人が必要な判断をできる

承認者に、選択肢と影響、推奨の根拠、未確定事項を提示します。人の選好は人が決め、合意済みの範囲の実行は agent が進めます。

04 / EVIDENCE

達成を根拠で確かめる

今回実行した検証、以前の記録、推論、未確認事項を区別します。残った問題とその影響まで含め、成果を受け入れられるか判断できるようにします。

プロンプトとフローを見直す方針

既存の工程、役割分担、ファイル構成、プロンプト本文は大幅に変更できます。各指示について「何を達成するために、誰が、何を使って、どの行動を取り、何をもって完了とするか」を対応づけます。

  1. 1目的守るべき合意と達成条件を定める
  2. 2手法目的に必要な判断と作業を記述する
  3. 3実行入力、ツール、権限、結果の回収を揃える
  4. 4検証成果物とログから達成を判定する

重複や矛盾を削り、必要な手順が欠けていれば書き直します。読み込み量、役割数、レビュー回数の変更は、目的の達成に与える効果と実行負担を測って採用します。

確認する指示と変更範囲

常駐する指示、スキル本文、役割定義、実際の worker 依頼文、評価タスク、採点プロンプトを一続きで確認します。

docs / skills / templates / scripts / evals / README / INSTALL / product-brief.md が対象です。Codex 専用化に合わせ、既存の engine 中立方針と導入、更新手順も整合させます。

目的に沿って評価する方法

今回のチューニングの主評価者には Astra を使います。モデル名と候補名を伏せた成果物、入力、実行証跡を渡し、評価項目ごとに根拠を求めます。機械的に確認できる起動、終了、テスト結果、ファイルの一致はスクリプトでも確認します。

評価対象確認すること根拠
目的と合意要望の保持、勝手な変更、判断の取りこぼし時点を固定した依頼と仕様、変更後の成果物
実行可能性指示された作業を実際に遂行できたか実行ログ、ツール結果、終了状態
検証の正確さ見逃し、誤指摘、根拠のない実施報告反証ケース、実行証跡、成果物との対応
人の判断選択肢と影響を示し、必要な承認を待てたか判断資料と作業の停止位置
実行負担再試行、不要な質問や作業、時間、トークン実行ごとの記録。評価者の使用量も別記

既存の実案件を案件単位で調整用と最終確認用に分けます。正解と後続時点の情報を実行側から隔離し、同じ入力と環境で現行版、候補版、必要に応じてスキルなしを比較します。採点プロンプトは正しい成果物と欠陥のある成果物で事前に確認します。

モデルはタスクに十分な能力を持つものを使います。プロンプトやフローの効果を測る比較ではモデルを揃え、次にモデルと推論強度を比較します。Astra の利用は主に候補比較と最終評価へ集中させます。

現時点では、このチューニングによる品質向上、費用削減、新しいモデル別の優劣は未計測です。下記のテスト成功は配布物の構造検査であり、PDH 全体の実行品質を保証する結果ではありません。

初期調査で見つかった問題
  • 既存ランナーの通常の Codex 起動はモデルを明示せず、環境設定を継承します。推論強度は xhigh に固定されています。
  • snapshot 作成元の既定値と一部の採点プロンプトが元ディレクトリを参照しており、worktree の変更を取り込めない経路があります。
  • 使用量集計は同じ作業場所の最新セッションを採用します。実行 ID との対応がなく、使用量の欠落を 0 と扱うため、比較値の取り違えや過小計上が起こり得ます。
  • 評価タスクに network 禁止と依存インストールの案内が同居しています。利用可能な手段と要求する行動を揃える必要があります。
  • 評価設計では入力の隔離を要求していますが、既存ランナーには sandbox を無効化する指定があります。新しい評価で必要な読み取り境界を別途検証します。

これらはファイルを読んで確認した問題です。このチューニングでの失敗率はまだ測っていません。
