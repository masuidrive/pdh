# PDH Codex チューニングの評価計画

## 達成すること

PDH の目的を、正しく記述された手法と実行可能なフローによって達成する。
ユーザーの意図と合意を保ち、必要な作業を遂行し、達成した結果と証拠の限界を人へ渡す。
プロンプトとフローは大幅に変更できる。
モデルは十分な能力を確保したうえで余計な費用を抑え、今回の主評価者には Astra を使う。

## 現行指示の独立評価

2026-09-05、Astra/high の独立 agent `evaluate_current_pdh` に、現行の指示群を読んで評価するよう依頼した。
親の指摘、過去の採点結果、実行ログは渡していない。
これは静的評価であり、欠陥の発生頻度や候補の改善効果は未計測である。

評価で挙がった競合は次のとおり。

| 優先度 | 競合 | 影響 | 確認する状況 |
|---|---|---|---|
| P1 | 実装前の明示 AC 承認と、承認前に既存障害を直す指示 | 同じ依頼を再承認させるか、必要な合意を省く | 明示的な可逆修正依頼と、合意済み契約を変える案 |
| P1 | 合成入力だけでは完了不可と、再現可能な seed による検証 | 新規機能の検証を一律に未達とする可能性 | 契約に適合したデータでの実処理確認と、上流との不一致 |
| P1 | 実 API の 200 必須と、API ごとの成功契約 | 正しい 201 や 204 応答を未達にする可能性 | 204 が正常な削除 API |
| P1 | 安い既存問題は今直す指示と、ついでの変更禁止 | 目的と無関係な変更が増える | 今回の機能に無関係な軽微な欠陥 |
| P1 | review-2 以降の既存問題の修正打ち切りと、目的達成に必要な問題の修正 | 必要な修正が発見時点で除外される | 今回の利用者操作を塞ぐ既存問題 |
| P1 | worker のモデル継承と、異モデル review 必須 | 費用や独立性の条件を割当で満たせない | 明示モデル設定と実際の呼出の照合 |
| P2 | Why を独立に確認する役はあるが、起動条件が不明 | 不十分な AC に全工程が引きずられる | AC は通るが依頼の目的を達成しない実装 |
| P2 | 影響する証拠だけ失効と、後続の変更で結果を無効化する指定 | 記録だけの更新で全テストを繰り返す可能性 | 検証後に note と checkbox だけを変更 |

## 最初の診断

[candidate-core.md](candidate-core.md) は評価専用の候補で、配布スキルへはまだ採用していない。
[decision-probes.json](decision-probes.json) の 8 状況に対する次の行動を判断させる。
現行は該当する既存の指示を原文のまま渡し、候補は実行契約をまとめ直した本文を渡す。
両者で課題、回答形式、モデル、推論強度を揃える。
各候補を Sol/high で 3 回ずつ試し、ばらつきと一貫性を確認する。

この診断は、指示を読んだときの判断の違いを測る。
実装、独立レビューの実起動、テスト実行、実案件での完遂は測れない。
全問で期待する判断が得られても、それだけでは配布版へ採用しない。

## 計測と採点

`scripts/codex-eval.py` は文章だけで判断する評価に使う。
各実行に固有 ID を振り、渡したプロンプト、その SHA-256、要求したモデルと推論強度、実行コマンド、JSONL、生の stderr、最終応答、終了コード、所要時間を保存する。
JSONL で使用量が得られない場合は不明値を保存する。
複数の完了 turn がある場合は、この実行内の値を合計する。
モデルのツールを無効化し、ツール使用イベントがあれば文章だけの評価として無効にする。
ChatGPT 認証を要求し、API キーの環境変数を子プロセスから外す。

JSONL は提供された実モデル名を証明しないため、モデル欄は CLI で明示した要求値として扱う。
実際の応答イベントから確認できる事実と区別する。
実行の完了は品質の合格を意味しない。

採点用資料では候補名とモデル名を伏せ、同じ課題と回答、採点条件を Astra に渡す。
根拠は各回答から引用し、必要な承認の省略と不要な承認、必要修正の欠落と無関係な変更、証拠不足の見逃しと不要な停止を両側から確認する。
採点に使ったモデルの使用量を通常実行の使用量へ混ぜない。

## 実案件による検証

既存の非公開データセットは `evals/private/` にコピー済み。
案件単位で調整用と最終確認用へ分け、同一案件の後続工程を最終確認用へ混ぜない。
実行側へ渡すのは切り出し時点の入力と必要なリポジトリだけとし、採点基準、後続版、他の実行結果を隔離する。
隔離が成立したことを実際に確認してから実行する。

既存の実行ツールは、元ディレクトリへの参照、モデル継承、最新セッションの後付け探索、外部アクセス条件を見直してから利用する。
文章だけの診断ランナーを、実ツールによる工程検証の代替には使わない。
採用には、複数の案件で目的達成を保つこと、重大な退行がないこと、実際の導入と更新手順を通ることを要する。

## 参照

計測コマンドの根拠は [Codex 非対話実行の公式資料](https://developers.openai.com/codex/noninteractive) と、ローカルの Codex CLI 0.153.4 の help。
現在の診断条件は候補の効果を測るための条件であり、配布先すべてに強いる運用規則ではない。

## 2026-09-05 の診断結果

8 状況をまとめた課題を各 3 回、Sol/high を明示して実行した。
すべての実行で終了イベント、最終応答、使用量を回収し、ツール使用イベントはなかった。
候補名とモデル名を伏せた 6 応答を、別の Astra/high agent `grade_decision_probes` が採点した。

| 指標 | 現行 | 候補 |
|---|---:|---:|
| rubric 上の PASS | 20 / 24 | 24 / 24 |
| 無関係な安価な修正を追加した回答 | 3 / 3 | 0 / 3 |
| 明示依頼と同じ AC の再承認で停止した回答 | 1 / 3 | 0 / 3 |
| 所要時間の中央値 | 115.100 秒 | 39.977 秒 |
| 入力トークン合計（3 回） | 119,625 | 39,614 |
| うちキャッシュ入力 | 9,344 | 0 |
| 出力トークン合計（3 回） | 14,392 | 5,013 |

この結果は rubric に対する指示解釈の診断結果であり、実案件での完遂率ではない。
D3 は課題文に空本文の検証記録を明示していなかった。
候補の 1 応答は、空本文まで確認済みと補っている。
現行の 2 応答でも AC 全体達成の断定に同じ留保がある。
採点者は、本番データ不在と 204 だけを理由に未達とするかという元の採点条件に沿って PASS としたが、この断定を実行証拠として認めていない。
このため候補を配布版へ採用する判断は保留し、明示された証拠と未確認部分を区別できるかを追加で確かめる。

実行記録、匿名化の対応表、48 項目の採点、採点基準への懸念は `evals/private/codex-tuning/` に保存した。
Astra による静的評価と採点の使用量は現在の記録から取得できておらず、評価者を含む総費用は未確定である。
