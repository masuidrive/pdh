# eval-12 — 実装されなかった確定判断を、review は見つけるか

再現する失敗: 承認済みの確定判断が実装されないまま close へ進んだ。**変更は diff に現れるが、脱落は diff に現れない。**PDH の対応づけは AC だけが順方向（AC → 実装）で、確定判断は逆方向（diff → AC・確定判断）にしか無かった。逆方向は diff 起点なので、**diff を 1 行も生まなかった判断は原理的に見えない。**

⚠ **これは eval-8 の裏側である。**eval-8 は確定判断が «崩れて書き換えられた» 側を見る。こちらは «そのまま忘れられた» 側を見る。前者は記録の有無で判定できるが、後者は記録すべき出来事が起きていないので、判定の起点を確定判断そのものに置くしかない。

## 読ませるもの

`claude/skills/pdh-reviewing/SKILL.md`

## 入力

- [fixtures/dropped-decision/ticket.md](fixtures/dropped-decision/ticket.md) — 検索 API の tenant 別レート制限。AC 3 件、確定判断 3 件
- [fixtures/dropped-decision/diff.md](fixtures/dropped-decision/diff.md) — 実装 diff、テスト結果、実装者の完了報告

仕込みは 3 件で、**AC は 3 件すべて実装されている。**

| | 状態 | 期待 |
|---|---|---|
| D1 固定窓 | 判断どおり実装 | 実装済みとして対応づく |
| D2 middleware の置き場 | 実装中に変更、**ticket に変更記録あり** | 独断変更として報告しない |
| D3 上限値の config 上書き | **実装なし。diff に痕跡が一切無い** | 未実装として報告する |

D3 を落としても AC は 1 件も欠けない。`LIMIT_PER_MINUTE = 60` のハードコードだけが実体で、**AC 起点の順方向対応づけでは届かない。**

⚠ **D3 に外部への被害を持たせない。**初版では D3 を「契約で別枠を約束した tenant が 2 社ある」とし、実装者の完了報告に D1・D2 だけを名指しさせていた。**どちらも確定判断を数えなくても D3 に着く道**であり、baseline が満点近くを取って判別しなかった。落ちた判断は、**それ自体の被害が静かなときにだけ**「数えたか」を測れる。

## タスク

あなたは reviewer である。レンズ 2（AC conformance + AC 妥当性）を担当する。ticket と diff を渡すので、対象 SHA を明記して findings を報告せよ。

## expected_behavior

- [ ] D3 が実装されていないことを finding として報告する
- [ ] その finding を **確定判断起点**で述べる（「AC が足りない」ではなく「確定判断 D3 に対応する実装が無い」）
- [ ] 確定判断を 1 件ずつ順方向に対応づけ、D1 / D2 について対応する file を名指しする
- [ ] D2 を再合意なき独断変更として誤って報告しない（ticket に変更記録がある）
- [ ] `LIMIT_PER_MINUTE = 60` を、単なる magic number ではなく **D3 の未実装の実体**として扱う
- [ ] D3 を finding として起票し、「AC は 3 件とも満たすので問題なし」で流さない

## 実行記録

- 2026-08-30 — **v1 は判別しなかった。**D3 に「契約で別枠を約束した 2 社」を持たせ、実装者の完了報告に D1・D2 だけを名指しさせた版で baseline（現行 skill）を回したところ **5/6**。D3 は Critical として拾われたが、**拾い方は確定判断の数え上げではなかった** — 「契約 2 社が 429 を受ける」という被害と、「完了報告が D3 に触れていない」という欠落から着いている。落ちた項は 1 つで、**確定判断を 1 件ずつ順方向に対応づける**だけだった（順方向の表は AC 1〜3 しか無い）。⚠ **シナリオが測りたいものを、シナリオ自身が別経路で漏らしていた。**v2 で両方を外した。
- 2026-08-30 — **v2 で判別した。baseline 4/6 → current 6/6**（claude、同一シナリオを別々の fresh agent へ）。
  - **落ちた 2 項が、そのまま規則の根拠になった。**baseline の順方向トレース表は AC 1〜3 だけで、**確定判断は 1 行も並ばない。**current は同じ表に D1 / D2 / D3 を並べ、D2 に `src/routes/search.rb:54` を名指しし、D3 を「無し / 未実装」と書いた。
  - ⚠ **予期していなかった FAIL が 1 つあった。**baseline は D2 の変更に「再合意の記録が無い」と指摘した。**これは誤検出である** — 確定判断は記録を残せば再合意なしに書き換えてよい（`docs/product-delivery-hierarchy.md`）。**eval-8 が implementor 側で塞いだ失敗形が、reviewer 側に残っていた。**current では消えた。
  - ⚠ **「脱落は見えない」という当初の仮説は成り立たなかった。**被害を静かにした v2 でも、baseline は D3 を Major として拾っている。**見つからないのではなく、系統的に数えていない。**規則が変えたのは «見つかるかどうか» ではなく «全件を数えるかどうか» である。
  - 両版とも AC 3 の到達経路（admin route が diff に無い）を独立に見つけており、シナリオが規則の有無と無関係な finding も生むことは確認済み。
