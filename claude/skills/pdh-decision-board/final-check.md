# 完成検査 — 形・文・判断〔手順 8〕

**board を書き終えてから読む。**主成果物と、承認者へ渡す補助資料のすべてに実施する。

## 形

選んだ媒体で、幅、overflow、見出し、画像、表、回答操作、狭い画面を確認する。HTML の検査は [html.md](html.md)「発行前検査」にある。Markdown、端末、PR コメントでは実際の表示先で折り返し、表、リンク、画像、貼り戻し文を確認する。

## 文

**承認者に復元作業をさせる文だけを探す。**文体・語調・言い回しの好みは、この層の対象ではない。

- 主語または目的語がなく、何が何をするか分からない文。
- 指示語（「これ」「それ」「上記」「同様に」「前述の」）の指す先が、段落をまたいでいて一意に決まらない箇所。**対象を名指しする。**
- 初出なのに単独では意味が分からない語や数。
- 比喩で書かれ、指している対象が本文にない語。
- 中身が本文のどこにも書かれていない主張（「経路を新しくしました」— 新しい経路が何かが無い）。**その場で特定する。**
- **決定サマリーの 1 行目に「この作業は何のためか」が無い board。**

## 判断 — 独立 reviewer

**別の engine の独立した reviewer に board だけを渡す。**起動方法、利用できる engine、sandbox、保存先はプロジェクト設定が定める。共有設定に特定 engine のコマンドや広い権限を既定として書かない。**権限を絞れないなら、依頼文で参照範囲を指示する。起動できないことを理由に検査を省かない。別 engine がまったく使えない場合**は、そのことを board に書いたうえで書き手が 7 問に答える（**ただし問 1・2・5・7 は書き手の自己判定が代わりにならない。そのことも board に書く**）。機微な情報を扱う board では [risk-overlay.md](risk-overlay.md) に従う。

- board を別形式へ抽出・整形せず、承認者へ渡す形のまま渡す。
- 試験用の注記は board 内ではなく reviewer への依頼文へ置く。
- **«足りない材料を挙げよ» という問いを足さない** — 引き込む力しか持たない。**主線に «承認者が使わない情報» が無いかも聞かない** — 過剰は問いでは防げない。主線を閉じたリストにして、そこに無いものを置かせないことが防ぐ。

### 依頼文

board 以外を渡さない。**依頼文に repo の path・ticket・note・git のコマンドを書かない** — 書くと reviewer は board と実装の突き合わせを始め、この検査は終わらなくなる。実装の検査はコードレビューの仕事である。

```
あなたは、この判断ボードの承認者として読む。

- board の冒頭か承認表に「誰が何を承認するか」が書いてある。**その人として読む。**
- あなたが知っているのは、一般的な技術語と、board 本文に出てくる語だけである。
  ⚠ **board に書かれていない前提を、自分の知識で埋めない。**
  ⚠ **ただし board が «承認者が把握している» と名指しで委ねた事実は、あなたが持っている
  ものとして扱う。**名指しされていない未確認は、«決められない» の理由になる。
- board 以外は見ない。repo・ticket・作業ノート・git のどれも参照しない。

<board をそのまま貼るか、board のファイルだけを渡す>

次の問いに、番号を変えずに答えよ。
<問 1〜7 と、上の「文」の層の各項目>
```

reviewer に次の 7 問を、番号を変えずに聞く。

1. **決められるか。**最初に「決められる / 決められない」を答え、詰まった場所を示す。**«承認が間違いになる条件» が board に無ければ、それだけで «決められない» と答える。**
2. **推奨を選ぶと、この ticket のゴール（board が書く Why と AC）に届くと、board から分かるか。**分からないなら、どの記述が足りないか。別の選択肢のほうが届くと読めるなら、それも言う。
3. **誤った判断をしうる箇所**はあるか。**board の中だけで分かるもの**に限って答える — **board 内の矛盾、過大に読める数値、根拠の書かれていない断定、数の不一致。**
4. 見出しと強調だけを拾っても、判断の筋が通るか。読む手間はどこにあるか。**主線の段落を 1 つずつ «これを読まなくても同じ判断を下せるか» で当て、下せる段落を名指しする。量は «決めることの大きさ» に釣り合っているか。**
5. 追加調査なしで決められたか。
6. **書き手が自分で調べたり決めたりできた項目を、承認者へ残していないか。**残っていれば、書き手が何を済ませるべきか。**判断 1 件ずつに «この選択で、利用者ができること・費用・戻せるかのどれかが変わるか» を当てる。**どれも変わらないなら、それは書き手が決めるものである。**board に推奨が書いてある判断は、とくに疑う。**
7. **この board だけを読んで、この作業が何のために始まったか分かるか。前の版・前の会話・ticket を見ずに答える。**分からなければ、どこに何を書けば分かるかを示す。あわせて、**前回からの変化を語っている箇所**が主線にあれば名指しする。**前回の回答がある board では、その指示に対して何を変えたかの畳みが要る** — 無ければ「承認者が自分の指示の通り具合を確かめられない」と指摘する。

同じ依頼で、上の「文」の層の各項目も挙げさせる。

## 指摘への応じ方 — 指摘された場所は、直す場所ではない

reviewer の「足りない」に、**指摘された節へ文言を足して応えない。**直す前に置き場所を引く。

1. **置き場所** — gate skill の主線固定部で、その情報が主線・裏付け・畳みのどこに属するかを引く。
2. **統合** — 同じ主張の既存の記述を検索し、足すのではなく 1 か所へまとめる。
3. **主線に足してよいのは、その節で承認者が判断に使う結論だけ。**書き手が実行する操作の詳細（コマンド・確認手順・実行フロー）は畳みへ。

## 出す条件 — reviewer は 1 回だけ回す

**合格は «欠陥ゼロ» ではない。**ゴールは 1 つだけ — **承認者が追加調査なしで判断を下せること。**

**reviewer は 1 回しか回さない。«決められなくする» 指摘が返ったら、その指摘だけを最小に直して出す。再走しない。**毎周が独立した読み手なので、直った確認にはならず、別の場所を見た新しい指摘が返るだけである。**例外は 1 つ — 構成を組み直したとき**（節の順序、判断の数、主線と補足の切り分け、媒体のいずれかを変えたとき）**だけ、もう 1 回回す。部分的に直しただけなら回さない。**

**それ以外の指摘は «直さずに出してよい»。**採らないと決めた指摘は、**件数と 1 行理由を note に残す。**

**«決められなくする» 指摘とは、次のどれかである。**

- 承認者が選ぶ側の事実が間違っている（推奨と別案の得失が入れ替わる）
- 推奨がゴールに届くと board から読めない、または別案のほうが届くと読める（問 2）
- 承認する対象（AC・契約）が board 内で矛盾していて、どちらを承認するのか決まらない
- 書き手が調べれば分かることを、承認者に調べさせている（問 6）
- 読み手が復元作業をしないと判断の筋が通らない（問 4）— 1 文に契約の全文を詰めた推奨、裏付けの全文をそのまま主線に複製した面、指示対象の書かれていない語

**言い回しの好み・語順・同義の言い換えは、これに当たらない。数の不一致も、それが «規模の目安» の側なら当たらない。**

**指摘が «互いに両立しない» 2 通りを含んでいたら、書き手が決めて、決めた理由を board に書く。**

**報告には、採らなかった指摘の件数と 1 行理由、構成を組み直したかどうかを書く。**「レビュー済み」とだけ書かない。

## 書き手が決めてよいかの判定

迷ったら、次の 3 つを全部満たすかで決める。**満たすなら書き手が決める。**満たさないものが 1 つでもあれば、判断として出す。

- **ticket が約束するものが変わらない**（Why の達成・AC・利用者が見る結果 — 画面・API の応答・出荷物 — が同じ）。
- **元に戻せる**（版管理に前の状態が残る）。
- **決めた理由を、後から探せる場所に残す**（作業ノート・記録用の文書）。

**「安いから」「小さいから」は基準にしない。**小さくても外から見える動きが変われば、それは承認者の判断である。

## 修正後の一貫性

数値、識別子、AC、判断範囲を直す前に、成果物内の出現箇所を**安定した識別子で全部出す**（文章全体ではなく数値、AC 番号、節 ID で検索する）。判断範囲を直したら、表題、決定サマリー、推奨、承認を求める見出し、返答文を確認する。**構造を一括置換したら、前後の見出し、面、回答項目の数を比較する。**
