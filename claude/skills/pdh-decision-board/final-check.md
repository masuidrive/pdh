# 完成検査 — 形・中身・判断〔手順 8〕

**decision-board を書き終えてから読む。**decision-board と、一緒に承認者へ渡すもの（`tools/to-markdown.sh` で作った Markdown・画面の試作・出力の実例）のすべてに実施する。

**読み手プロファイル（SKILL.md「読み手プロファイル」）があれば、発行前にもう一度当てる。**プロファイルが指す媒体・語彙・写真の要否・選択肢の出し方を、この decision-board が満たしているか確認する。

## 形

選んだ媒体で、幅、overflow、見出し、画像、表、回答操作、狭い画面を確認する。HTML の検査は [html.md](html.md)「発行前検査」にある。テキスト、Markdown では実際の表示先で折り返し、表、リンク、画像、貼り戻し文（承認者が回答をコピーして会話へ貼る文）を確認する。

## 中身

**承認者に復元作業をさせる箇所だけを探す。**文章の書き方（言語ごとの規則）は、この節の対象ではない — `CLAUDE.md`（codex では `AGENTS.md`）が定める。

- 中身が本文のどこにも書かれていない主張（「経路を新しくしました」— 新しい経路が何かが無い）。**その場で特定する。**
- **決定サマリーの 1 行目に「この作業は何のためか」が無い decision-board。**
- **«〜を確認してください» «〜を確認すべき» で承認者に調査を回している箇所。**書き手が確かめられることは確かめて結果を書く。確かめられないなら、何がなぜ確かめられないかを書く（`PDH-AGENTS.md`「確認が要るのは判断であって、調査ではない」）。

## 判断 — reviewer

**decision-board の書き手とは別に起こした reviewer に decision-board だけを渡す。**書いた本人は自分の decision-board を読めてしまうので、別の worker にすることがこの検査の要である。reviewer の engine は `CLAUDE.md`（codex では `AGENTS.md`）の engine 割り当てに従い、**指定が無ければ decision-board の書き手と同じ engine の別 worker にする。**別 engine を指定すると、同じ engine が書き手と reviewer の両方で見落とす欠陥も見つかる。起動方法、sandbox、保存先は `CLAUDE.md`（codex では `AGENTS.md`）が定める。共有設定に特定 engine のコマンドや広い権限を既定として書かない。**権限を絞れないなら、依頼文で参照範囲を指示する。起動できないことを理由に検査を省かない。reviewer を起動できない場合**は、そのことを decision-board に書いたうえで decision-board の書き手が 7 問に答える（**ただし問 1・2・5・7 は decision-board の書き手の自己判定が代わりにならない。そのことも decision-board に書く**）。機微な情報を扱う decision-board では [risk-overlay.md](risk-overlay.md) に従う。

- decision-board は承認者へ渡す形のまま渡す。data URI で巨大になる HTML は、`python3 tools/review-copy.py --input <完成 HTML> --out <専用ディレクトリ>/board.html` で完成物から画像だけを別ファイルにした検査用の写しを作り、HTML と生成された画像を一緒に渡してよい。本文・CSS・回答操作・画像の中身は保ち、要約や仮画像に置き換えない。変換の保持は skill の `tools/selftest.sh` が `tools/review-copy-test.py` を実行して数え、形の検査は元の完成 HTML を表示して行う
- 試験用の注記は decision-board 内ではなく reviewer への依頼文へ置く。
- **«足りない材料を挙げよ» という問いを足さない** — 本文（承認者が必ず読む部分）に材料を足させる方向にしか働かない。**本文に «承認者が使わない情報» が無いかも聞かない** — 過剰は問いでは防げない。本文に置くものを閉じたリストにして、そこに無いものを置かせないことが防ぐ。

### 依頼文

decision-board 以外を渡さない。**依頼文に repo の path・ticket・note・git のコマンドを書かない** — 書くと reviewer は decision-board と実装の突き合わせを始め、この検査は終わらなくなる。実装の検査はコードレビューの仕事である。

```
あなたは、この decision-board の承認者として読む。

- decision-board の冒頭か承認表に「誰が何を承認するか」が書いてある。**その人として読む。**
- あなたが知っているのは、一般的な技術語と、decision-board の本文に出てくる語だけである。
  ⚠ **decision-board に書かれていない前提を、自分の知識で埋めない。**
  ⚠ **ただし decision-board が «承認者が把握している» と名指しで委ねた事実は、あなたが持っている
  ものとして扱う。**名指しされていない未確認は、«決められない» の理由になる。
- decision-board 以外は見ない。repo・ticket・note・git のどれも参照しない。

<decision-board をそのまま貼るか、完成 HTML を渡す。巨大な HTML は上の手順で作った検査用の HTML と画像だけを渡す>

次の問いに、番号を変えずに答えよ。
<問 1〜7 と、上の「中身」の節の各項目>
```

reviewer に次の 7 問を、番号を変えずに聞く。

1. **決められるか。**最初に「決められる / 決められない」を答え、詰まった場所を示す。**«承認が間違いになる条件» が decision-board に無ければ、それだけで «決められない» と答える。**
2. **推奨を選ぶと、この ticket のゴール（decision-board が書く Why と AC）に届くと、decision-board から分かるか。**分からないなら、どの記述が足りないか。別の選択肢のほうが届くと読めるなら、それも言う。
3. **誤った判断をしうる箇所**はあるか。**decision-board の中だけで分かるもの**に限って答える — **decision-board 内の矛盾、過大に読める数値、根拠の書かれていない断定、数の不一致。**
4. 見出しと強調だけを拾っても、材料から推奨と理由までがつながって読めるか。読む手間はどこにあるか。**本文の段落を 1 つずつ «これを読まなくても同じ判断を下せるか» で当て、下せる段落を名指しする。量は «決めることの大きさ» に釣り合っているか。**
5. 追加調査なしで決められたか。
6. **decision-board の書き手が自分で調べたり決めたりできた項目を、承認者へ残していないか。**残っていれば、decision-board の書き手が何を済ませるべきか。**判断 1 件ずつに «この選択で、利用者ができること・費用・戻せるかのどれかが変わるか» を当てる。**どれも変わらないなら、それは decision-board の書き手が決めるものである。**decision-board に推奨が書いてある判断は、とくに疑う。**
7. **この decision-board だけを読んで、この作業が何のために始まったか分かるか。前の版・前の会話・ticket を見ずに答える。**分からなければ、どこに何を書けば分かるかを示す。あわせて、**前回からの変化を語っている箇所**が本文にあれば名指しする。**前回の回答がある decision-board では、その指示に対して何を変えたかを書いた閉じた `<details>` が要る** — 無ければ「承認者が自分の指示の通り具合を確かめられない」と finding に書く。

同じ依頼で、上の「中身」の節の各項目も挙げさせる。

## finding への応じ方 — finding が指した場所は、直す場所ではない

reviewer の「足りない」に、**finding が指した節へ文言を足して応えない。**直す前に置き場所を決める。

1. **置き場所** — 承認の PDH-stage ごとのファイル（[ticket-gate.md](ticket-gate.md) / [close-gate.md](close-gate.md)）が定める本文の固定部を見て、その情報が本文・根拠・根拠の中の閉じた `<details>` のどこに属するかを決める。
2. **統合** — 同じ主張の既存の記述を検索し、足すのではなく 1 か所へまとめる。
3. **本文に足してよいのは、その節で承認者が判断に使う結論だけ。**decision-board の書き手が実行する操作の詳細（コマンド・確認手順・実行フロー）は閉じた `<details>` に入れる。

## 出す条件 — 修正を同じ reviewer に戻す

**合格は «欠陥ゼロ» ではない。**ゴールは 1 つだけ — **承認者が追加調査なしで判断を下せること。**

この規則の目的: 承認者が判断に使う decision-board で、指摘した欠陥の解消を同じ reviewer が確かめられること。

«決められなくする» finding が返ったら、その finding を最小に直し、元の指摘・直した箇所・関係する判断だけを同じ reviewer に渡して、解消を確かめる。構成を変えたとき（節の順序、判断の数、本文と根拠の切り分け、媒体を変えたとき）は、その影響範囲も渡す。毎回の網羅的な探索は繰り返さない。

修正を始めるとき、note の Checklist に `- [ ] decision-board: 指摘の解消を同じ reviewer が確かめた（対象の板の path）` を足す。解消の結果を progress に残して `[x]` にする。未了は close の `require_checklist` が数える。

**それ以外の finding は «直さずに出してよい»。**採らないと決めた finding は、**件数と 1 行理由を note に残す。**

**«決められなくする» finding とは、次のどれかである。**

- 承認者が選ぶ側の事実が間違っている（推奨と別案の得失が入れ替わる）
- 推奨がゴールに届くと decision-board から読めない、または別案のほうが届くと読める（問 2）
- 承認する対象（AC・契約）が decision-board 内で矛盾していて、どちらを承認するのか決まらない
- decision-board の書き手が調べれば分かることを、承認者に調べさせている（問 6）
- 読み手が復元作業をしないと、材料から推奨と理由までがつながって読めない（問 4）— 1 文に契約の全文を詰めた推奨、根拠の全文をそのまま本文に複製した節、指示対象の書かれていない語

**言い回しの好み・語順・同義の言い換えは、これに当たらない。数の不一致も、それが «規模の目安» の側なら当たらない。**

**finding が «互いに両立しない» 2 通りを含んでいたら、decision-board の書き手が決めて、決めた理由を decision-board に書く。**

**報告には、採らなかった finding の件数と 1 行理由、構成を組み直したかどうかを書く。**「レビュー済み」とだけ書かない。

## decision-board の書き手が決めてよいかの判定

迷ったら、次の 3 つを全部満たすかで決める。**満たすなら decision-board の書き手が決める。**満たさないものが 1 つでもあれば、判断として出す。

- **ticket が約束するものが変わらない**（Why の達成・AC・利用者が見る結果 — 画面・API の応答・出荷物 — が同じ）。
- **元に戻せる**（版管理に前の状態が残る）。
- **決めた理由を、後から探せる場所に残す**（note・記録用の文書）。

**「安いから」「小さいから」は基準にしない。**小さくても外から見える動きが変われば、それは承認者の判断である。

## 修正後の一貫性

数値、識別子、AC、判断範囲を直す前に、成果物内の出現箇所を**安定した識別子で全部出す**（文章全体ではなく数値、AC 番号、節 ID で検索する）。判断範囲を直したら、表題、決定サマリー、推奨、承認を求める見出し、返答文を確認する。**構造を一括置換したら、前後の見出し、節（スライドならスライドの枚数）、回答項目の数を比較する。**
