# Product Brief を書く

この skill の目的: Brief を書く人が、誰のどの問題を解き、どこまでの失敗を許すかを、ticket の判断に使える形で残せること。新規作成・変更・pdh-update での見直しのときに全体を読む。

## 節ごとの書き方

配布された product-brief.md の雛形と現在の Brief を読み、次を照合する。実装の事実はコード・仕様・テストへ置き、Brief には人の意思を書く。

| 節 | 書くこと |
|---|---|
| 冒頭 | 誰が何をできる製品かを 1 文で書く |
| Background | いま必要になった背景と、現在の手段 |
| Who | 利用者と使う場面。作る人と使う人を区別する |
| Problem | 利用者が困ることと、その被害 |
| Solution | 問題を解いた後に利用者ができること |
| Key User Journeys | J1 などの番号を付け、入口・操作・最後に得る結果を書く |
| Failure Tolerance | 下の 3 欄と数字を利用者と決める |
| Constraints | 外部の制約と、採用する運用の条件 |
| Architectural Invariants | どの ticket でも保つ約束を AI-1 などの番号で書く |
| Done | 利用場面が成立したと判断できる状態を書く |
| Open Questions（ある場合） | 未決の意思を明示し、決まったように書かない |

既存の節を名前だけで捨てない。Appetite や Non-goals があれば、使う予算や作らない範囲として上の意思と照らす。

## Failure Tolerance を決める

欄が存在するだけでは足りない。PM は次の 3 欄の中身を利用者と決める。

- `使う人と量:` 誰が、どれくらいの量で使うか。
- `許す失敗の目安:` 許せる具体的な失敗、その頻度（% か月の回数）、1 回のコスト（誰の何分）を数字で書く。`許す失敗:` でもよい。
- `許さない失敗:` 取り返しのつかない失敗（データの喪失・秘密の漏えいなど）と、利用者の操作を誤らせる失敗に絞る。

例:

```markdown
- 使う人と量: 本人 1 人が 1 日 20 回読む。
- 許す失敗の目安: 開き直すと直る表示の崩れは月 1 回以下、本人の作業 1 分以下。
- 許さない失敗: 保存済みの記録を失うこと、秘密の漏えい、送信先を誤認させて別の相手へ送信させる表示。
```

«表示の誤りを許さない» は、装飾の崩れまで必須修正にするので避ける。«どの表示がどの操作を誤らせるか» まで絞る。数字は PM が作らず、利用者の答えを根拠にする。

## 変更案と確認

変更する節と文を利用者へ示し、承認を得てから Brief に書く（承認の規則は PDH-AGENTS.md）。頻度・人の作業時間の両方が数字か、許さない失敗が上の範囲に絞られているかは PM が読む。

`bash [SKILLS_PATH]/pdh-brief-writing/scripts/check-brief.sh product-brief.md` は、Failure Tolerance の 3 行・空値・雛形・許す失敗の数字の有無だけを検査する。意味の照合の結果は、呼び出した stage の Checklist に残す。Brief だけを扱うときは note の Checklist に残す。
